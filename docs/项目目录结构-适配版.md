# 项目目录结构适配版（针对 JCROB 单人交付）

> 输入：`D:\Desktop\项目架构.txt`。它给的是一个通用 Monorepo 模板：Go 后端、Python 模型服务、串口/Protobuf 外设 SDK、前端、部署、测试。
>
> 结论：**保留它的目录纪律，不保留它的技术假设。** JCROB 是 HTTP/WS 协议，不是串口/Protobuf；本期没有 AI 模型服务；单人 6 周也不适合维护 5 个可部署包。
>
> 2026-10-20 评审后修订：豆包/GLM 都指出 `packages/*` 对单人 6 周是过度设计。本版压成**单仓库双应用**（`web/` + `server/`），只保留一个共享契约目录；`jcrob` 客户端收进 `server/app/adapters/jcrob`，不再单独发包。

## 1. 原结构哪些能用、哪些要改

| 原结构 | 问题 | 适配建议 |
|---|---|---|
| `packages/backend/main.go`、`go.mod` | 技术栈写成 Go，与 xlsx/我们的 FastAPI 或 Spring Boot 冲突 | 改成 `server/`；FastAPI 用 `pyproject.toml`，Spring Boot 用 `pom.xml` |
| `packages/model-service` | 本期没有 AI 推理，单独部署只会增加运维 | 先放 `server/app/adapters/ai/README.md` 占位，真有模型再拆服务 |
| `packages/device-sdk/proto`、`serial_driver.py` | JCROB 是 HTTP/JSON + WebSocket，不是串口/Protobuf | 改成 `server/app/adapters/jcrob`：token、超时、重试、WS ping、单位归一化 |
| `packages/common` | 只有一个后端时，过早抽公共库 | 先放 `server/app/core`；被 2 个以上应用引用再抽 |
| `packages/frontend` | 目录本身没问题 | 改成 `web/`，更符合“可部署应用”语义 |
| `tests/` | 方向正确 | 增加 `tests/fixtures` 存探针 JSON，集成测试直接复用 |
| `deploy/` | 方向正确 | 保留 `docker-compose.yml` + `nginx/` + `env.example` |
| `.github/`、`docs/`、`README`、`LICENSE` | 方向正确 | 保留；单人项目也要有 CI 和启动文档 |

## 2. 推荐目录（单人 6 周版，评审后）

```text
explosion-proof-robot-platform/
├─ web/                            # Vue 3 + TS + Vite + Arco Design Vue
│  ├─ src/
│  │  ├─ api/                      # 只调平台后端，不直连机器人
│  │  ├─ components/               # 状态条/视频卡/地图/告警弹窗/表格
│  │  ├─ layouts/                  # 深蓝控制台布局
│  │  ├─ pages/                    # 驾驶舱/任务/点位/监控/告警/设置
│  │  ├─ stores/                   # Pinia：设备、实时状态、告警
│  │  ├─ styles/                   # tokens.css：颜色/间距/字体
│  │  └─ main.ts
│  ├─ package.json
│  └─ vite.config.ts
├─ server/                         # FastAPI（默认）或 Spring Boot
│  ├─ app/
│  │  ├─ api/                      # REST 路由
│  │  ├─ core/                     # 配置/安全/日志/异常
│  │  ├─ models/                   # SQLAlchemy 实体
│  │  ├─ services/                 # 设备/地图/任务/告警/报表
│  │  ├─ adapters/
│  │  │  ├─ jcrob/                 # token/HTTP/WS/UDP/单位归一化/能力探测
│  │  │  ├─ hikvision/             # RTSP/ISAPI/PTZ/测温（按需）
│  │  │  ├─ bms/                   # 占位：接口规范 + README
│  │  │  ├─ fixed_devices/         # 占位：门/灯/空调/充电柜
│  │  │  └─ ai/                    # 占位：识别服务，不部署
│  │  ├─ realtime/                 # WebSocket 推送
│  │  └─ main.py
│  ├─ alembic/                     # 数据库迁移
│  ├─ tests/                       # pytest：Adapter/状态机/坐标换算
│  ├─ pyproject.toml
│  └─ .env.example
├─ contracts/                      # OpenAPI + 由它生成的 TS 类型
├─ deploy/
│  ├─ docker-compose.yml           # server + mysql + nginx（+ media 可选）
│  ├─ nginx/
│  └─ env.example
├─ docs/
├─ scripts/                        # probe_jcrob.py 等一次性工具
├─ tests/e2e/                      # Playwright：登录→看板→任务
├─ .github/workflows/ci.yml
├─ .gitignore
├─ Makefile
└─ README.md
```

规则只有三条：

1. **只有 `web/` 和 `server/` 两个可部署单元**，媒体网关是第三个容器，不是代码模块；
2. **只有 `contracts/` 是共享的**，不要提前抽 `common`/`ui`/`sdk` 包；
3. 外部设备适配器一律放在 `server/app/adapters/<name>/`，没有实现就返回 `EXTERNAL_UNAVAILABLE`，不要建空服务。

## 3. 为什么不用 `packages/backend` + `packages/frontend` 的“大 Monorepo”

- 单人项目只需要 **1 个前端构建 + 1 个后端进程 + 1 个媒体网关**；顶层 `web/`/`server/` 比 `packages/` 更能表达“可部署”。
- 只有 `contracts/` 值得共享；`jcrob-client` 只有一个消费者（后端），不需要单独发包。
- `model-service` 现在没有模型，不要先建空服务；否则你会花时间维护 Dockerfile、依赖和端口。
- `common` 先不抽；等第二个应用真的复用时再抽，避免“为了架构而架构”。

## 4. 如果是 Spring Boot

把 `server/` 换成：

```text
server/
├─ pom.xml
└─ src/main/java/com/example/platform/
   ├─ adapter/jcrob/              # HTTP/WS/token/单位
   ├─ adapter/hikvision/          # RTSP/ISAPI
   ├─ device/                     # 设备/能力
   ├─ map/                        # 地图/坐标/点位
   ├─ task/                       # 任务/巡航/状态机
   ├─ alarm/                      # 规则/去重/通知
   ├─ media/                      # 视频通道/抓拍
   ├─ system/                     # 用户/角色/日志
   └─ config/
```

`adapter/jcrob` 就是这个后端里的一个包；只有当脚本/测试也要用 Java 客户端时才抽模块。

## 5. 第一周就按这个顺序建

1. `server/` 起一个 `/health` 和 `/api/v1/devices`；
2. `web/` 起登录 + 深蓝布局壳；
3. `contracts/` 放第一版 OpenAPI：设备、地图、任务、告警；
4. `server/tests/fixtures/` 放探针 JSON，前后端都用它做 Mock；
5. `deploy/docker-compose.yml` 只放 server + mysql + nginx；视频确认后再加 media；
6. CI 只跑 lint + 单元测试 + 前端 build，不搞复杂流水线。

## 6. 不要做的事

- 不要为了“顶级开源项目风范”先建 5 个包、3 个服务、K8s 清单；
- 不要把 JCROB 的 HTTP 接口包装成 Protobuf/gRPC，除非以后真的有高频控制需求；
- 不要让前端直连机器人 `3546/3547`；所有请求走平台后端；
- 不要把外部设备的占位接口写成“已实现”，没有数据就返回 `EXTERNAL_UNAVAILABLE`。
