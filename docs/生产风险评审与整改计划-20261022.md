## 一、先说结论

如果明天就上线，最可能出的三个事故（两边 AI 一致，我也认）：

1. **撞机**：地图分辨率/原点填错 → 点位坐标错位 → 下发后机器人按错坐标走
2. **监控瞎火**：go2rtc 单点挂 / 磁盘满 → 现场告警时无画可查
3. **告警被吃掉**：静默期、阈值被清空、单进程重启窗口 → 真事故没报出来

前两条**我们本来就不允许发生**：写操作全锁着（等真机+授权签字），所以"错坐标下发"在当前版本物理上不可能；
但**这个保护是"不做"换来的，不是"做对了"**。真机联调时必须先做坐标校验再开写操作。

第三条是真问题，本轮已经动刀（见下）。

## 四、多机器人：现场到底是不是轮询？

**不是。** 行业标准做法是**机器人主动上报状态（pub/sub），平台订阅**：

- **VDA5050**（AGV/AMR 车队的国际标准）：状态走 MQTT `state` 主题，约 1Hz 发布；订单走 `order` 主题下发。
  没有"平台轮询车"这一说。
- **Open-RMF**（Open Robotics 开源车队管理）：Fleet Adapter 订阅机器人状态，按需下发任务；
  对只提供 HTTP 的厂商才退化成周期拉取。
- **国内巡检机器人厂商**：多数提供 SDK/WebSocket 推送；只有"老设备+私有 HTTP 接口"才被迫轮询。

所以我们的路线是：

```
现在：HTTP 轮询 1s（因为 JCROB 只给了 HTTP 3546）
真机到场：先接 WS 3547 做推送，HTTP 轮询降级为兜底
多机：每台设备一个轮询任务（asyncio）+ 一份缓存，按设备分库分表查询
```

**JCROB 本身有 WS 3547**，所以第一步不是"扩轮询"，而是"把 WS 用起来"。

## 五、AI 赋能要不要上 Qwen

服务器上有 **Qwen3-32B** 和 **Qwen3-8B(27B?)**。我的判断：

| 场景 | 现在需要吗 | 理由 |
|---|---|---|
| 告警文本解释 / 处置建议 | **可以试，但不是必须** | 规则引擎能覆盖 80%，模型只在"为什么报、该怎么办"上加解释 |
| 自然语言查数据（"上周告警最多的点位"） | 需要，但可以后置 | 要先把统计接口做全（已做一半） |
| 视频 AI 识别（跑冒滴漏/仪表读数） | **需要专用视觉模型，Qwen 文本模型做不了** | 这是另一条线，不是"接个大模型"能解决的 |
| 巡检报告自动生成 | 可以试 | 已有结构化数据，模型只负责组织语言 |

**结论：现在不接。** 接了以后页面多一个"AI 摘要"按钮，客户看到的还是同样的数据。
真要上，先在方案里写死三件事：输入（哪些字段给模型）、输出（必须带出处，不能编）、兜底（模型挂了页面照常用）。

已写进方案：`docs/AI赋能-方案占位.md`（下轮补）。
