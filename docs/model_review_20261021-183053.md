## 一、按钮「应该做什么」的判定标准

### 1. 判定规则
*   **必须实现**：
    *   **判定标准**：该操作是只读业务流的核心环节，且后端已有真实数据支撑，不写就断链。
    *   **示例1**：告警中心的「导出」按钮（必须真导 CSV，领导要拿去开会汇报）。
    *   **示例2**：任务管理里的「详情」按钮（必须真拉任务+动作序列 JSON，运维要看具体执行了什么动作）。
*   **必须禁用并说明**：
    *   **判定标准**：操作涉及设备写控制（有安全/合规风险），且当前因联调或授权未打通无法真写。
    *   **示例1**：巡检点位的「同步到机器人」按钮（未授权前必须禁用，防止误操作炸机）。
    *   **示例2**：设备管理中协议未实现的「测试连接」按钮（必须置灰，并 tooltip 提示缺少哪些协议字段）。
*   **应该直接删掉**：
    *   **判定标准**：操作背后完全没有后端逻辑支撑，且短期内（3个月内）没有明确业务流，纯占位。
    *   **示例1**：首页的「场站」下拉框（只有一个真实设备，假数据选个寂寞，直接删或改成固定文本）。
    *   **示例2**：首页可见光/热红外窗口的「点击跳转视频页」占位按钮（直接内嵌 go2rtc 视频流，不要让人多点一步）。

### 2. 现在的做法合格吗？
**不合格。领导验收时看到弹窗绝对是减分项。**
*   **原因**：领导点按钮是想看“平台能不能干活”，弹“未开放”说明平台**不能干活**。如果满屏都是这种按钮，领导会认为你是在拿半成品糊弄他。
*   **改进**：对于写操作，**绝对不要用弹窗**。应该用灰按钮（`disabled`），鼠标悬停时给个 Tooltip：“现场授权未开启/真机联调未完成”。领导一看就懂：“哦，平台做好了，就等现场签字，这是安全限制”。这是加分项。

## 二、换场地 / 导入地图设计

### 1. 地图数据从哪来？怎么进平台？
*   **机器人扫出来的（SLAM建图）**：由机器人在现场建图完成后，通过现有的只读接口或文件传输工具，将地图文件（通常是 `.pgm` + `.yaml` 或原生贴图包）传给平台服务器。平台解析后入库。
*   **客户给的 CAD / PDF 图纸**：平台提供上传入口。后端用 `potrace` 等工具将光栅图二值化/矢量化，或仅作为背景底图，由人工在平台上标定原点和比例尺。
*   **现场测绘（OSM/GeoJSON）**：极少数情况。提供 JSON 导入接口，平台解析坐标串生成多边形障碍物。

### 2. 平台侧最小数据模型（表：`maps`）
| 字段名 | 类型 | 说明 |
|---|---|---|
| `map_id` | UUID | 平台主键 |
| `robot_id` | UUID | 关联的设备 ID |
| `name` | String | 地图名称（如“A厂区1楼”） |
| `floor` | Int | 楼层号 |
| `image_url` | String | 切片后的 PNG 或大图路径 |
| `resolution` | Float | 分辨率（米/像素，如 0.05） |
| `origin_x` | Float | 原点 X 坐标（对应机器人的 map->odom 原点） |
| `origin_y` | Float | 原点 Y 坐标 |
| `origin_theta`| Float | 原点旋转角度（通常为 0） |
| `is_active` | Bool | 当前是否生效（换场地时切这个） |
| `created_at` | Timestamp | 导入时间 |

*(注：点位 `nav_points` 和相机位置直接关联 `map_id` 即可)*

### 3. UI 流程设计
*   **放在哪**：地图监控页右上角“地图列表”旁，加一个「导入地图」按钮。
*   **几步完成**（3步）：
    1.  **上传文件**：拖拽 PNG/PGM + YAML 参数文件（或手填分辨率/原点）。
    2.  **预览与标定**：前端渲染出底图，如果是纯图片无参数，让用户在图上点两点画一条线，输入实际物理距离（如5米）来自动算 `resolution`；点击设置原点。
    3.  **保存并激活**：提交后端，后端存图+切图+入库，并自动设为 `is_active=true`。
*   **失败怎么提示**：分阶段报。上传失败报“文件格式不支持/超大”；标定失败报“分辨率计算异常，请检查输入距离”；入库失败报“数据库写入失败，请查看日志”。

### 4. 与机器人自带地图的对应关系
*   **绝对不能同名依赖**：平台用 `map_id` 管理地图，机器人内部可能叫“map_001”。
*   **坐标系绑定**：导入时填写的 `resolution` 和 `origin` 必须严格对应机器人内部 SLAM 坐标系。平台下发任务时，带的是 `map_id` + `nav_points` 坐标，机器人端收到后需要自己映射。
*   **映射表**：如果机器人换场地换了内部地图，需要在设备管理里配一个映射：平台 `map_id` <-> 机器人内部 `map_name`。

### 5. 没有真机时，能先做什么（绝不能造假数据）
*   **能先做**：
    1.  导入地图的 UI 流程和文件上传机制。
    2.  PNG 切片算法和前端渲染展示。
    3.  人工标定分辨率和原点的数学计算逻辑。
    4.  平台侧 `maps` 表的 CRUD 和激活逻辑。
*   **必须等真机**：
    1.  把导入的地图下发给机器人并让其生效。
    2.  在新地图上打点并让机器人真实导航过去（闭环验证）。
    3.  验证平台算出的像素坐标转机器人物理坐标是否准确。

## 三、除了“没真机数据”，还有什么在挡着（阻塞项排序）

按“领导最容易点破”排序：

1.  **缺：导航点位的坐标系转换算法**
    *   **摆设按钮**：巡检点位「新增点位」
    *   **补齐**：前端点选地图像素坐标 `(px, py)` 转换为机器人物理坐标 `(x, y, theta)` 的数学公式没写。得写好公式，等真机来直接验算。
2.  **缺：与机器人任务接口的协议字段对齐**
    *   **摆设按钮**：任务管理「新建任务/下发」
    *   **补齐**：平台任务表的 JSON 结构和机器人能接收的 JSON 结构没对应。需要拉通协议文档，把动作枚举（如开门、拍照）写死对齐。
3.  **缺：真机 RTSP/MSE 视频流地址的动态获取逻辑**
    *   **摆设按钮**：首页可见光/热红外窗口占位
    *   **补齐**：现在可能是硬编码的 go2rtc 地址。缺设备状态上线后，自动拼接该设备真实视频流地址的逻辑。
4.  **缺：设备离线状态下的指令缓存与重发机制**
    *   **摆设按钮**：任务管理「暂停/取消」
    *   **补齐**：机器人离线时点了暂停怎么处理？缺一个“离线转在线自动重发”或“拦截提示”的中间件机制。
5.  **缺：平台与机器人的双向心跳保活**
    *   **摆设按钮**：设备管理「测试连接」（针对真机）
    *   **补齐**：TCP/HTTP 探测不够，需要补齐 ROS/自定义协议的心跳包，确保设备真实在线。
6.  **缺：云台控制的防抖/节流限流**
    *   **摆设按钮**：云台控制（上下左右）
    *   **补齐**：前端摇杆事件直接发指令会打爆机器人。缺前端的防抖（连续按只发一次/按间隔发）和后端的指令合并下发机制。
7.  **缺：多租户/多场站的业务隔离模型**
    *   **摆设按钮**：首页「场站下拉」
    *   **补齐**：只有一个设备，没有建场站树。需要补齐“组织-场站-设备”的三级数据模型，才能让下拉框有真数据。
8.  **缺：地图切片静态资源的 Nginx 代理配置**
    *   **摆设按钮**：地图监控「切换查看地图」
    *   **补齐**：虽然现在能点，但地图切片如果大了加载慢，缺 Nginx 的静态资源缓存和gzip配置，领导点大图会卡顿。
