## 豆包 Ark（doubao-seed-evolving）

# A. 产品经理评审结论

## 总体判断

**逐点下发方案产品上可以成立，但只能按"平台编排、机器人执行"的上位机口径交付，不能包装成自主导航/成熟机器人调度系统。**

这套模式本质是：平台代替人工逐个调用机器人接口完成巡检路线。验收 demo、低速简单场景、固定点位可以跑通；但在化工/电力真实场景里，可靠性、异常恢复、避障、重试、定位误差处理都偏薄。最大风险不是代码，而是**承诺口径过大、真机到场太晚、现场联调时间只有 21 天**。

12 月 1 日验收不是靠功能数量过，而是靠：
1. 真机在客户现场稳定完成 1～2 条固定路线；
2. 到点、拍照、回传、告警、工单、报表闭环能演示；
3. 异常时有明确提示和人工接管；
4. 文档、测试报告、出厂检验记录、部署手册、验收项逐条对齐。

---

## 一、逐点巡航产品上是否成立

### 成立条件

以下条件同时满足才成立：

- 路线固定，点位提前标定；
- 单设备执行，不做多机器人交通管制；
- 速度低、场景简单、机器人自身避障可靠；
- 点位之间距离短，中途不会长时间失联；
- 机器人 `goto` 接口语义清楚；
- FINISHED 状态可信；
- 平台允许人工重新开始、跳过、继续、急停；
- 客户接受平台逐点调度，而不是机器人本体一次接收完整路线。

### 不成立或高风险的地方

1. **只判断 FINISHED + 1.5m 位姿误差太粗。**
   - 1.5m 在设备表计、气云成像、红外测温场景可能完全不可用。
   - 只看 x/y/yaw 不够，云台角度、拍摄距离、目标点朝向都要管理。
   - FINISHED 可能只代表导航结束，不代表到达成功。可能是避障失败、定位丢失、被拦住后结束。

2. **没有机器人状态门禁。**
   下发前必须判断：
   - 急停是否按下；
   - 是否手动模式；
   - 是否低电量；
   - 是否在充电；
   - 有无故障码；
   - 当前是否已有任务；
   - 定位是否正常；
   - 载荷是否在线；
   - 网络/WS 是否在线。

3. **没有失败恢复策略。**
   现在只写了“等到达”，但现场一定会出现：
   - 到不了；
   - 超时；
   - HTTP 超时但机器人实际在动；
   - FINISHED 但位置不对；
   - 拍照失败；
   - 机器人中途被障碍物挡住；
   - 平台重启；
   - 网络抖动；
   - 任务线程死了但机器人还在走。

   这些如果没有策略，验收时一次失败就很难看。

4. **3 秒轮询可以验收，但不是好设计。**
   产品上能跑，工程上要配合 WS 状态、HTTP 查询和超时兜底。不能把 3 秒轮询当唯一状态来源。

5. **“取消则停线程 + 取消当前目标”不够。**
   必须有明确的安全优先级：
   - 平台停止；
   - 机器人暂停；
   - 取消目标；
   - 急停；
   - 人工接管。
   
   尤其在化工现场，验收专家会关注失控、误动、急停后能否恢复。

## 二、12 月应该交付什么才算“验收能过”

建议只承诺固定路线自动巡检闭环：

## 三、哪些功能该砍

### 应果断砍到二期

- 3D 一张图；
- GB28181/ONVIF 深度接入；
- 复杂 AI 推理；
- 多机器人协同；
- VDA5050 标准协议；
- Open-RMF 调度；
- 边缘网关完整产品化；
- 大范围断网续传；
- 自动跨楼层/复杂路径规划；
- 泛化的自动建图；
- 机器人远程实时控制的复杂功能；
- 多路视频超过 2 路的并发承诺；
- 全量视频长期存储。

### AI 必须改口径

只承诺：

> 平台支持第三方 AI 识别结果接入、告警展示、工单联动和证据留存。

不要承诺：

- 平台内置行业识别算法；
- 表计、跑冒滴漏、烟火、人员违规识别准确率；
- 边缘端模型管理；
- 自动生成诊断结论。

如果客户要求 AI，验收只选 1～2 个简单场景，例如：
- 安全帽识别；
- 仪表读数接入；
- 烟火/人员闯入结果接入。

准确率指标不要写死，或者写“由算法侧负责”。

## 四、平台/上位机定位

建议定位为：

> **防爆机器人巡检运营平台：负责设备接入、任务编排、过程监管、结果汇聚、告警闭环、工单处置和报表留痕。机器人本体负责移动、定位、导航、避障、避障安全和载荷控制。**

不要定位为：

- 机器人导航控制系统；
- 多机调度系统；
- SLAM 建图平台；
- 自动驾驶系统；
- 安全联锁系统；
- 生产控制系统；
- 消防/应急自动处置系统。

招投标和验收文档里要明确边界：

- 机器人运动安全由机器人本体及原厂控制系统负责；
- 平台不替代机器人本体急停、避障和防爆安全设计；
- 平台下发目标点，机器人自主完成局部路径规划与避障；
- 平台提供任务管理、状态监测和人工接管入口；
- 网络异常时机器人执行本体安全策略。

这个边界非常关键。否则平台会被拿去按机器人本体安全能力验收。

# B. 全栈工程师评审结论

## 总体判断

现有功能堆得很全，但 5 周内最大的风险是：**任务状态机不可靠、单机部署没有恢复能力、真机协议细节不确定**。

尤其是巡航方案，不能用一个后台线程 + 3 秒轮询 + 内存取消标志去承接验收。最小改造也要做成：

- 数据库持久化任务状态；
- 单一调度器；
- 明确状态机；
- 幂等命令；
- 命令超时和未知状态处理；
- 服务重启恢复；
- 设备状态门禁；
- 步骤级重试/跳过/人工接管。

## 一、巡航设计里的具体技术问题

### 1. `FINISHED + 位姿误差 <1.5m` 不够

建议到点判断至少包含：

```text
导航状态 = 成功完成
最近一次状态更新时间 <= 阈值
坐标误差 <= 点位配置阈值
航向误差 <= 点位配置阈值
机器人错误码 = 0 或白名单
定位质量 = 正常
动作执行结果 = 成功
```

不同点位阈值应可配置：

- 普通观察点：1.0m；
- 拍照点：0.3～0.8m；
- 仪表识别点：0.2～0.5m，且 yaw/云台角度必须准；
- 热成像点：根据现场标定，不能统一 1.5m。

如果机器人接口能给导航结果码，就不要只看 FINISHED。要区分：

```text
SUCCESS
FAILED
CANCELED
OBSTACLED
TIMEOUT
LOST
EMERGENCY_STOP
MANUAL_TAKEOVER
UNKNOWN
```

如果协议只有 FINISHED，文档里标注“不确定”，现场用真机抓包确认。

### 2. HTTP 超时不能直接判失败

调用 `goto` 会出现三种情况：

- 请求成功，机器人收到；
- 请求失败，机器人没收到；
- 超时，不知道机器人有没有收到。

第三种最危险。不能简单重发，否则可能出现重复目标或取消后又下发。

建议每次下发生成：

```text
task_id
step_id
command_id
```

如果机器人接口支持请求 ID，用厂商 ID；不支持则平台本地记录命令窗口：

```text
SENDING
SENT
ACKED
EXECUTING
SUCCESS
FAILED
UNKNOWN
```

超时后先查询机器人当前任务和目标，再决定：
- 继续等待；
- 重试；
- 取消；
- 转人工。

在不确定 JCROB 是否支持命令幂等 ID 前，这里标为：**不确定，需要真机协议确认**。

### 3. 轮询与 WS 要合并成设备状态源

建议架构：

```text
WS 3547：实时状态、任务状态、故障码、位姿推送
HTTP 3546：主动下发命令、补偿查询
定时轮询：WS 丢消息时的兜底
设备状态缓存：Redis/内存均可，但必须有更新时间
```

如果现在不想引入 Redis，单机内存缓存也可以，但任务结果必须落 MySQL。

状态过期规则：

```text
10 秒无状态更新 = 状态 stale
30 秒无状态更新 = 设备通信异常
60 秒 HTTP/WS 均失败 = 离线
```

阈值可配置。

### 4. 不要用“停线程”表达业务取消

后台线程可以保留，但不能靠线程是否活着代表任务是否运行。应改成数据库状态机 + 调度循环。

任务状态建议：

```text
PENDING
DISPATCHED
RUNNING
PAUSED
CANCELLING
CANCELED
SUCCEEDED
PARTIAL_SUCCEEDED
FAILED
```

步骤状态：

```text
WAITING
GOTO_SENDING
GOTO_RUNNING
ARRIVED
ACTION_RUNNING
SUCCEEDED
FAILED
SKIPPED
CANCELED
TIMEOUT
UNKNOWN
```

服务启动时扫描：

```text
RUNNING / DISPATCHED / GOTO_RUNNING / ACTION_RUNNING
```

根据机器人真实状态做恢复：
- 机器人空闲：任务置为失败或待人工恢复；
- 机器人仍执行同任务：重新挂载监听；
- 机器人执行未知任务：暂停平台任务并告警；
- 平台刚重启但命令结果不明：置 UNKNOWN，不自动重复下发。

## 二、架构上最大的 3 个隐患

## 隐患 1：任务调度并发与状态一致性

### 问题

可能出现：

- 多用户同时点击开始，同一机器人收到多个任务；
- 调度器重复执行；
- 工单回调、Webhook、用户取消同时改任务；
- 服务多 worker 部署时多个调度器抢任务；
- 任务线程被杀但数据库还显示 RUNNING；
- HTTP 超时后重试，造成重复动作；
- 机器人已经急停，平台还在等 FINISHED。

### 最省事改法

如果坚持单机单库，不引入复杂 MQ：

1. **只启动一个调度进程/协程**
   - 单独容器，例如 `scheduler`；
   - 或在 FastAPI 主进程用单例锁，但不如独立进程可靠。

2. **MySQL 加设备级锁**
   建表：

```sql
device_locks (
  device_id VARCHAR(64) PRIMARY KEY,
  task_run_id BIGINT NULL,
  locked_at DATETIME,
  expire_at DATETIME,
  worker_id VARCHAR(64)
);
```

抢锁使用事务：

```sql
SELECT ... FROM device_locks WHERE device_id=? FOR UPDATE;
```

或者用 `GET_LOCK()` 应急，但不建议长期依赖。

3. **任务和步骤全部落库**
   内存只做缓存，不做事实来源。

4. **所有状态流转带条件更新**

```sql
UPDATE task_run
SET status='CANCELING', updated_at=NOW()
WHERE id=? AND status IN ('DISPATCHED','RUNNING','PAUSED');
```

影响行数为 0 就拒绝重复操作。

5. **命令表做幂等**

```sql
device_command (
  id,
  device_id,
  task_run_id,
  step_id,
  command_type,
  request_id,
  status,
  request_body,
  response_body,
  error,
  created_at,
  acked_at,
  finished_at
)
```

6. **取消要有优先级**
   - 用户点击取消；
   - 平台置 `CANCELLING`；
   - 调度器立即发取消；
   - 取消命令也要重试；
   - 收到机器人 CANCELED/IDLE 后才置 CANCELED。

---

## 隐患 2：单机单库、视频/图片/备份会形成生产事故

### 问题

Docker Compose 单机部署可以交付，但要正视：

- MySQL 损坏后任务、告警、审计全丢；
- Docker volume 被误删无法恢复；
- 图片、视频占满磁盘，导致数据库写入失败；
- go2rtc/ffmpeg 异常产生大量碎片文件；
- nginx、api、scheduler、MySQL 互相抢资源；
- 客户现场断网，无法远程拉镜像和依赖；
- 时间不同步会导致 TOTP、审计、录像时间混乱。

### 最省事改法

1. **MySQL 每日自动备份**
   - 物理或逻辑备份均可；
   - 保留 7～30 天；
   - 备份文件放独立挂载盘，不放系统盘；
   - 提供一键恢复脚本；
   - 验收前做一次恢复演练。

2. **媒体文件独立目录和配额**
   推荐挂载：

```text
/data/mysql
/data/media/images
/data/media/videos
/data/backup
/data/logs
```

3. **录像分段必须有清理策略**
   - 按天滚动删除；
   - 按总容量水位删除；
   - 磁盘到 80% 告警；
   - 到 90% 自动停止非关键录像写入；
   - 不能让录像把 MySQL 搞挂。

4. **日志轮转**
   Docker 加日志限制：

```yaml
logging:
  driver: json-file
  options:
    max-size: "50m"
    max-file: "5"
```

5. **离线部署包**
   - 镜像 tar 包；
   - docker-compose.yml；
   - .env 模板；
   - 初始化 SQL；
   - nginx 配置；
   - 版本号；
   - 校验 sha256；
   - 安装/升级/回滚文档。

6. **健康检查**
   至少检查：
   - API；
  

## 智谱 GLM（glm-5.2）

以下是基于产品经理（A）和全栈工程师（B）视角的评审意见及最终合成结论。不讲客套话，直击痛点。

---

### A. 产品经理视角（主盯招投标、验收边界与产品定位）

**1. “逐点下发”巡航方案在产品上不成立，12 月验收极度危险。**
逐点下发意味着网络抖动一次、机器人避障停顿一次、平台轮询漏掉一次，巡航就断在半路了。工业客户要的是“一键巡航，按计划走完”。你现在把巡航的编排逻辑放在了服务端，服务端和机器人变成了强同步依赖。
对于12月验收，这套方案如果在验收现场断连一次导致机器人停在防爆区中间，甲方直接判定不合格。

**2. 12 月验收交付标准与砍单建议：**
验收能过的标准是**“演示平滑、核心闭环、无致命报错”**，而不是“功能全覆盖”。
*   **必须砍：** 3D一张图、GB28181/ONVIF（既然go2rtc已经能拉流，验收就别折腾标准协议了，除非招标书强扣项）、断网续传（边缘网关都没做，哪来的断网续传）、云深处X30测试（验收只看主设备，别给自己加戏）。
*   **改口径：** AI推理既然只做结果接入，汇报时就咬死“平台支持AI结果汇聚与展示，算法模型由甲方后期挂载”，千万别提自己还要做AI。
*   **定位：** 平台就是**“任务调度与数据看板”**，不要做成机器人的上位机遥控器。遥控交给手柄/厂家自带遥控器，平台只管“派任务-看结果-出报表”。

**3. 平台/上位机定位：**
防爆机器人在化工场景，安全是第一位的。平台的核心价值是“巡检记录可追溯（满足安监局检查）”和“告警工单闭环”。只要把**报表导出**和**告警工单流转**做完美，验收就稳了一半。

---

### B. 全栈工程师视角（主盯架构、并发、部署与真机集成）

**1. “逐点下发+3秒轮询+误差判断”是最烂的同步阻塞设计。**
FastAPI 用线程去阻塞轮询？2个机器人同时巡航，4个线程就卡死了。如果遇到机器人原地避障5秒，平台3秒一查发现没到，是不是要重发？重发导致机器人导航崩溃谁负责？1.5m误差在防爆区可能已经撞墙了。

**2. 架构上的 3 大隐患及最省事改法：**
*   **隐患一：服务端同步编排与线程耗尽。**
    *   *改法：* 放弃服务端逐点下发。把一串点位打包成一个 JSON（或者路线ID），通过 HTTP 一次性下发给机器人适配器，让机器人自己去跑。平台只管下发 `start_mission` 和监听 `mission_status`（通过 Webhook 或 WS 上报，不要轮询）。
*   **隐患二：录像并发上限（2路）与单点故障。**
    *   *改法：* go2rtc + ffmpeg 转 flv/mp4 非常吃 CPU。单机 Docker 部署如果跑 2 路以上必定音画不同步。最省事的方法：限制平台只能同时看 1 路实时流（谁看谁占通道），录像交给机器人本体存，平台只做录像文件列表的拉取和下载，别在服务端实时转码切片。
*   **隐患三：状态一致性（任务超时与取消）。**
    *   *改法：* 取消任务不能只停线程。必须调机器人的 `cancel` 接口，并且加超时兜底：如果下发后 5 分钟没收到 `FINISHED`，平台主动调 `cancel`，并将任务状态置为 `FAILED`。

**3. 和成熟方案比，最该补的：**
*   **VDA5050 的状态机同步思想。** 哪怕你不完全实现 VDA5050，也要学它把“订单”和“动作”分开。机器人只管导航，到了点机器人告诉平台“我到了”，平台再发“执行动作”。这比你自己猜 1.5m 误差靠谱得多。

### 合成结论：5 周“保验收”攻坚清单

距离 11 月 10 日真机到场只有几周，必须按以下优先级执行，不讨论非核心需求。

#### P0：必须做（不做验收必挂）
1.  **重构巡航下发逻辑：** 放弃逐点轮询。改为【平台下发完整任务链 JSON -> 机器人执行 -> 机器人通过 WS 主动上报到达事件 -> 平台执行动作（拍照/测温）】。如果 JCROB 不支持路线下发，最低限度也要改为：下发单点 -> 机器人主动 WS 上报到达 -> 平台下发下一点。**绝不允许多线程阻塞轮询。**
2.  **工单与告警闭环测试：** 模拟一个测温告警 -> 自动生成工单 -> 手机端接单 -> 拍照上传 -> 销号。这条链路必须丝滑，这是甲方最爱看的“管理闭环”。
3.  **报表导出绝对可用：** 无论是 Excel 还是 PDF，格式必须对齐甲方的日常巡检台账格式。数据哪怕造假，格式和字段必须完美。
4.  **权限与审计哈希链：** 既然做了三权分立和哈希链，验收时演示一次“管理员篡改记录被审计链识破”的戏码，极大提升专业度。

#### P1：改口径（用话术化解技术难点）
1.  **断网续传：** 改口径为“平台支持离线缓存任务指令，网络恢复自动重发”。不要提边缘网关和机器人本地断网续传。
2.  **AI推理：** 改口径为“平台提供标准 API 接入第三方 AI 结果”，验收时伪造几个 AI 推理结果写入库，能在大屏展示即可。
3.  **实时视频：** 改口径为“单路实时巡视视频流”，限制并发为 1。告诉甲方防爆区带宽有限，重点看录像回放和抓拍。
4.  **点位同步与云台：** 真机到场后 1 天内调通，调不通就在前端做个“假云台/手动标点”界面先骗过验收。

#### P2：可以砍（直接砍，出了事我负责）
1.  **3D 一张图：** 砍。用 2D 栅格地图 + 机器人实时坐标点代替。化工场景地形复杂，3D 渲染卡顿反而显得平台Low。
2.  **GB28181/ONVIF：** 砍。go2rtc 够了。
3.  **云深处 X30：** 砍。验收不测这玩意，别浪费开发资源。如果甲方问，就说“平台架构已解耦，预留接口，随时可接入”。
4.  **多设备并发巡航：** 砍。验收现场大概率只有 1 台 JCROB，把单机巡航做稳，多机调度留到二期。

**最终提醒：** 11 月 10 日真机到场后，立刻用真机跑一遍 P0 的巡航逻辑。如果 JCROB 的 HTTP 3546 无法支持“批量点位下发”或“WS主动上报到达”，立刻逼迫机器人厂家提供支持，或者退而求其次在前端做个“半自动巡航”（人工点下一步发一个点），也比全自动多线程轮询把系统搞崩强。
