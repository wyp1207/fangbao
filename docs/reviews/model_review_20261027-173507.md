## 1. 逐条挑毛病

### P0-1 订单幂等 —— 会翻车，翻在"时序"和"key 语义"上

**翻车点：**

1. **"下发前先查 external_id 是否有值，有就拒绝"在单 worker 下也防不住并发。**
   单 uvicorn worker 不等于单请求：async 事件循环里两个 HTTP 请求可以交错，`SELECT external_id` → await 网络下发 → 写回 external_id 这个窗口里，第二个请求已经进来了。车端会收到两单，`JC-{毫秒}` 还可能撞毫秒。
   - 触发：用户双击按钮 / 前端超时重试 / 巡检定时任务和人工补发同时触发。
   - 后果：两车（或同车）收到重复任务，现场乱跑。

2. **`external_id` 一个字段承载不了 attempt 历史。** 你重发时 attempt+1，车端新旧两个订单可能都活着（旧单车端没 cancel 成功），回报里带的是旧 orderId，你按 external_id upsert 会把新单状态覆盖掉，或者直接丢弃。
3. **"车端返回任务 id 才写 external_id"意味着下发请求 in-flight 期间崩溃，external_id 永远为空**，重启后不知道车端到底收没收到，补发就重复。这是经典的 "unknown commit" 问题，查一下没用。
4. **重复上报按 external_id upsert** —— upsert 哪张表？TaskRun 主表被乱序回报覆盖（比如 done 之后又来一条 running）会让状态倒退。状态回报必须带 **状态机守卫 + 序号（seq/ts）**，不能裸 upsert。

**正确做法（参考 VDA5050）：**
- 幂等键要在**发出去之前**落库，不是等车端回 ack。新增 `outbox/dispatch` 行，状态 `PENDING/SENT/ACKED/FAILED`，带 `order_key`、`attempt`、请求报文、车端 orderId（可空）、dispatch 状态。先 INSERT commit，再发网络。
- VDA5050 的幂等单元是 `orderId + orderUpdateId`：**同一逻辑订单复用同一个 orderId，变更才递增 updateId**，服务端（车端）按 `(orderId, orderUpdateId)` 去重（见 VDA5050 v2.0 §6.4 order handling；开源参考：`vda5050_connector` 的 `OrderManager`，[ipa320/vda5050_connector](https://github.com/ipa320/vda5050_connector)，以及 Open-RMF 的 `rmf_fleet_adapter` 里 `Task::Booking` 幂等思路）。
- 重发前必须先 **显式 cancel 旧 orderId 并确认终态**，再发新 attempt；新 attempt 应有新车端 orderId（映射关系落 dispatch 表）。
- 防并发：`TaskRun` 加 `dispatch_state` 列 + 唯一约束，或对 run 行 `SELECT ... FOR UPDATE`（MySQL）/ 事务 + `BEGIN IMMEDIATE`（SQLite）。
- 回报处理：状态只允许单调迁移，附带车端 seq/时间戳，旧序号丢弃。

### P0-2 exec_mode —— 方向对，但这个二值枚举撑不过一个月

1. **"整单 vs 逐点"不是能力，是两个正交维度的混合**：
   - 能否一次接收多节点（batch capability）；
   - 平台是否掌握逐点结果用于"到点做动作"（action placement）。
   JCROB 整单模式下，你的"到点→动作→下一点"（开门、拍照、检测）怎么办？车端支持节点动作回调吗？草稿没说。**真机未到，这里全是假设**——轮式机器人协议十有八九不支持在 sub_task 中间插平台侧动作，最后你还得拆成"每点一单"，exec_mode=order 变成废代码。
2. 巡航里 `if exec_mode == ...` 会到处复制。应抽成 `ExecutionStrategy`：`submit(segments) -> handle` + `poll() -> 段级事件流`，两种模式产出统一事件（`waypoint_reached(index, pose)`），业务逻辑只订阅事件。
3. X30 的 1003 逐点链路里，**前一个点的任务和后一个点之间车端可能有自动续跑/排队**，你以为的"逐点"未必是真的取消即停——确认 1003 的任务队列和取消语义。

**建议：** 定义 fleet capability 至少包含 `supports_batch`、`supports_in_order_actions`、`supports_pause`、`cancel_semantics`、`reports_segment_result`。参考 Open-RMF 的 fleet config：`rmf_fleet_msgs/RobotMode`、`fleet_config.yaml`（[open-rmf/rmf](https://github.com/open-rmf/rmf) 的 `rmf_demos` 配置），RMF 不区分"整单/逐点"，而是统一成 task + phase + event 模型，适配器做翻译。

### P0-3 七态状态机 —— 态太多，而且 `dispatched/accepted` 是噪声

1. **`accepted` 在单 worker 无 MQ 场景几乎不可观测或无意义**：X30/JCROB 的 HTTP 下发接口返回 200 时，大概率只是"收到请求"，并不等于"车端规划接受"；真正的 accepted 和 running 往往在同一个回报流里先后到达，中间没有任何业务决策依赖它。为它写状态、写守卫、写前端展示，纯属成本。
2. **`paused` 放哪了？** 草稿写的是线性流 `... → running → paused → done/...`，实际 pause 必须能 resume 回 running，且 pause 可以失败（车在窄道里不能停）。pause 是**平行状态**不是后继状态。
3. 七态 × 迁移矩阵 × audit，三天工期里这是最容易写出非法迁移 bug 的地方。
4. 反过来，**真正缺的态是 `cancelling`**：下发取消是异步的，running → cancelled 直接跳转会在"取消请求已发但车还在跑"的窗口期重复下发新任务。

**更简单的等价方案（单 worker 够用）：**
- 任务主状态保持 5 个：`planned / active / done / failed / cancelled`；
- 把 dispatch 细节放到独立字段：`dispatch_state: pending|sent|rejected`（甚至只做布尔 `acked`），不进主状态机；
- 加一个可选 `cancel_requested` 标志位（或 `cancelling`），取消确认后才落 `cancelled`；
- pause 如果现场没需求，**YAGNI 删掉**；要做就加 `paused` 且只允许 `paused ↔ active`。
- audit 照写，但 audit 是 append-only 事件表（`task_event(run_id, ts, from_state, to_state, reason, raw)`），不要依赖状态字段本身。

开源参考：RMF 的 task state 就是 `phase + Event` 模型（`rmf_task_msgs/TaskState`，status: Pending/Queued/Executing/Completed/Failed/Canceled），投递过程不算任务状态。

### P0-4 到点三值判定 —— 阈值有坑，suspect 会卡死流程

1. **"只加速度"远远不够**，速度在以下情况全是 0：
   - 车被卡住/堵人/绕障失败停在半路，导航状态不是 FINISHED——这条你能挡；
   - **FINISHED 是车端"任务结束"而不是"成功到达"**：很多协议里失败、取消、手动接管后任务也进入结束态。必须区分**成功结束原因码**（result/error code），不能只看状态字符串。先把 X30 1007 的状态枚举拉全：成功 / 失败 / 取消 / 手动接管 / 急停 / 规划失败 / 充电中终止，各是什么码。
2. 还要的信号：
   - **定位质量**：`/location_status` 必须参与到点判定！定位丢失期间到达的点，直接就是 suspect，不能只靠距离。
   - **目标坐标系与帧一致性**：距离用的 pose 是 map 系还是 odom 系？重定位瞬间 pose 会跳变，必须带 `map_id` 和时间戳，别拿 5 秒前的 pose 算。
   - **航向角**：1m 距离在对接充电桩、窄道口时毫无意义，需要 `xy + yaw` 双阈值（充电桩对接到点失败 90% 是 yaw）。
   - **稳定时长**：速度 < 0.05 只看一帧？机器狗停下的瞬间腿还在调整，机体速度抖动正常。要求"位置 + 速度连续 N 次（如 1s）满足"。
   - 手动接管/避障暂停标志：急停拍下时 v=0。
3. **1.0m 阈值在窄道场景太宽**，1m 可能已经堵在岔路中间；厂区宽一点的地方 1m 又太严。阈值按点位配置（waypoint 表加 `arrival_tol_xy/yaw`），充电对接点要到 0.1m/5° 量级。
4. **`arrived_suspect` 必然变"永远 suspect"**，因为你的策略是"不重试，提示重定位"——重定位之后呢？没有重新判定该点的闭环。如果 suspect 也算"放行并继续下一点"，那后面全程累积漂移，越跑越偏；如果不继续，任务挂住等人工，告警半夜刷屏无人理。
   - 正确流程：suspect → **自动触发一次重定位 → 重定位后重新评估当前点（必要时短距离重新导航一次）→ 仍不过则 failed 并挂起任务**。给重试次数（1 次）和整体超时，suspect 是瞬态不是终态。
   - 另外 suspect 判定里 FINISHED 但 1~2.5m，**先怀疑的是坐标点录错/图版本不一致**，告警里要带 map_id、点位坐标、车端 pose，否则现场只看到"漂移"两个字没法处理。

### P1-5 数据库资源锁 —— 能工作，但草稿有三个硬 bug

1. **"排序后逐个 INSERT，任一冲突整体回滚"——回滚后已抢到的锁是释放了，但 TTL 已经开始走没问题；真正的问题是没有等待/重试策略**，两个任务抢窄道必然一个直接失败，任务 failed。资源锁需要 `try-acquire → 等待/排队 → 死锁检测`，否则只是把"撞车"换成"任务莫名失败"。
2. **TTL 60s 续租 + finally 释放的组合在任务崩溃时必然留下脏锁**：finally 不覆盖 kill -9 / 掉电。15s 扫过期锁意味着**最长 60s（TTL）内资源被死任务占着**——如果续租线程还活着但任务逻辑卡死（车端无响应），锁会被无限续租，扫描线程永远清不掉它。要区分 **owner liveness**：续租必须带任务状态校验，run 不在 active 就不续租。
3. 更隐蔽的：**锁和车辆调度没有联动**。两辆车在窄道相向而行，A 拿锁进入、B 在锁外等待——B 停在哪？如果 B 停在窄道入口甚至窄道中段，A 出来时照样顶头。资源锁必须配 **holding point（等待点）**，没抢到锁时导航到锁外的等待点，这是 RMF traffic scheduling 的核心（`rmf_traffic` 的 schedule + blockade，[open-rmf/rmf_traffic](https://github.com/open-rmf/rmf_traffic)）。你们有窄道和充电桩，这是必做题不是加分题。
4. 充电桩还要防**车位级**和**会车区**两类 key；注意 key 粒度，整段走廊一把大锁会让并行度归零。

**SQLite 能不能工作：**
- 能，但默认隔离级别下要小心：SQLite 是库级写锁，"逐个 INSERT" 要放在一个 `BEGIN IMMEDIATE` 事务里，否则多连接并发时第一个 INSERT 后第二个连接直接 `database is locked`（ busy_timeout 调大）。主键冲突靠 `INSERT OR FAIL`/唯一索引即可，不需要 `SELECT FOR UPDATE`（SQLite 也没有）。
- 但注意：**MySQL 和 SQLite 的行为差异要在测试里覆盖**，别开发用 SQLite 上线 MySQL，锁等待语义不一样。

**单 worker 更简单的做法：**
- 你们单 uvicorn worker，资源锁**首先用进程内结构**：`dict[key -> (run_id, robot_id, lease_deadline)]` + 一个 asyncio.Limit，分配在调度核心函数里 `async with scheduler._gate`。简单、零延迟、无脏锁（进程没了锁自然没了，重启意味着所有 run 也都要重新接管）。
- 但有两个前提：(a) 永远单进程，且启动多 worker 时要有启动断言拒绝；(b) **车端失联恢复后要重新 reconcile 锁归属**。
- 建议折中：**进程内锁做热路径，DB 表做审计和跨重启恢复依据**（重启时把 active run 对应的锁全部置过期并重新确认车辆位置）。
- **什么时候升级 Redis：** 多进程/多实例部署、有独立调度器进程和 API 进程、续租和获取要跨节点；或者你们要让车端协议网关（可能多连接）也参与互斥。用 `SET NX PX` + Lua 释放（验 owner token）+ 看门狗续租（Redlock 是单实例不需要的，别上 Redlock 辩论）。在你们当前形态，Redis 是过度设计。

### P1-6 定位策略 —— 两个触发条件会误触发，校验闭环不完整

1. **"断电重启后首次连上"就重定位——危险。** 狗重启后如果自己有激光重定位能力（X300 这类一般有），上电即在正确位姿，你立刻 2101 重置 + 灌 initialpose，反而把正确定位带偏。正确做法：连上后**先观察 location_status 和匹配置信度 N 秒**，只有 located=false/低置信才触发；且 initialpose 给的初值从哪来？要有**持久化的最后已知良好 pose（LKG）**，而不是当前 odom 瞎猜。
2. **"located=false 持续 10s"阈值要和工况结合**：长走廊、进电梯、大面积空旷区激光退化时 10s 丢失很常见，车常常能自行重收敛。自动重定位在运动中做非常危险（重定位瞬间 pose 跳变，规划器可能突然甩出高速修正路径，窄道里直接撞）。**自动重定位前置条件：车已停稳 + 速度为 0 + 附近没有紧邻障碍**；运动中只告警、先减速停车。
3. **"被搬动：odom 位移 >5m 但定位未更新"在四足上不成立**（第 6 问细讲）。
4. **校验逻辑自相矛盾**："读回 pose 与目标误差 <0.5m"——重定位时还没导航，跟哪个"目标"比？应该是与 **initialpose 给定值 / LKG pose** 比；而且重定位成功后 pose 本来就会被设成你给的值，"读回一致"只证明设置生效，不证明定位正确。真正有效的校验是 **激光匹配置信度/粒子权重 + 静态环境一致性 + location_status 持续稳定**，然后做一次短距离试探移动或核对到已知地标（充电桩、反光板）的距离。
5. 2101 和 ROS `/initialvoice` 两条通道谁先谁后？发 2101 后车端 nav 栈是否需要重新发 initialpose？**双发可能打架**（一个重置到原点、一个设到 LKG）。真机到了先做矩阵测试：冷启动、热重启、丢定位恢复、手动拖走 10m 各 10 次。
6. 切图触发没问题，但切图后所有 active 任务必须**冻结/取消**，waypoint 坐标的 frame_id 要绑 map_id——否则旧图坐标新图用，全线 suspect。

### 1. 这 6 条里哪几条会翻车？逐条说清触发条件和后果。

**【P0-1 订单幂等】—— 必翻车**
*   **触发条件**：网络抖动导致平台下发请求超时，但车端实际已接收并开始执行。平台捕获 TimeoutException，触发重试或允许用户重新下发。
*   **后果**：因为你的前置检查是“查 `TaskRun.external_id` 是否有值，有就拒绝”，此时 `external_id` 还没来得及写入（或者正处在并发态），导致第二次下发成功。车端收到两个相同任务的请求。如果是 VDA5050 标准还会好点（有 orderId 幂等），但你们自定义链路直接乱套，两辆车或者同一辆车执行两个幽灵任务。
*   **改法**：前置检查必须是**基于 `order_key` 的唯一约束**，而不是查 `external_id`。利用数据库的唯一索引冲突来做防重。

**【P0-2 exec_mode】—— 概念错误，必翻车**
*   **触发条件**：任何需要中途暂停、取消或者插队的场景。
*   **后果**：你以为 `order` 和 `waypoint` 只是下发粒度的区别，错！这是**控制权**的区别。`waypoint` 模式下，平台是大脑，车是肢体；`order` 模式下，车端是大脑，平台只是个传话筒。如果采用 `order` 模式发了整单，当 AGV 突然遇到障碍物卡住 5 分钟，你的平台轮询状态根本无法感知“卡死”，也无法在中途插入新优先级任务。更严重的是，如果车端调度逻辑有 bug，整单下发会导致车端状态机错乱。
*   **改法**：不要搞非黑即白的 `exec_mode`。去看看 **Open-RMF 的 `rmf_traffic_ros2`** 或 **VDA5050 v2 的 `order` 结构**。标准做法是：永远以整单（Graph）下发，但在当前节点（Node）执行完后，平台可以通过 `cancelOrder` 或更新 `order` 来抢夺控制权。

**【P0-3 状态机】—— 状态设计有漏洞，会卡死**
*   **触发条件**：下发接口 HTTP 200 返回成功，但车端内部校验失败（比如目标点不可达），直接回了 `REJECTED`。或者车端网络断开。
*   **后果**：你的规则是“调用下发成功=dispatched”，然后等“车端首次回报=accepted”。如果车端永远不回报（拒绝或断网），任务永远卡在 `dispatched`，占用资源，前端转圈圈到天荒地老。
*   **改法**：增加 `rejected` 态。`dispatched` 必须带定时器，超时未收到 `accepted` 直接转 `failed`。

**【P0-4 到点三值判定】—— 机器狗上必翻车**
*   **触发条件**：X30 机器狗在充电桩或者窄道对接时。
*   **后果**：机器狗为了保持平衡，或者为了跨越微小的门槛，会有**原地踏步**或**微调姿态**的动作。此时速度可能 > 0.05m/s，但实际已到达。你的 `arrived` 判定直接失败，触发超时。另外，2.5m 的 suspect 判定在厂区太宽松，机器狗在 2.5m 外可能已经撞墙了。
*   **改法**：放弃自创判定，直接使用底盘原生上报的导航状态。VDA5050 里叫 `actionStates` 和 `nodeStates`，ROS 里叫 `/move_base/result` 的 `status.code`。如果你非要自己算，必须加入“底盘里程计总位移是否停止增加”的判据，而不是瞬时速度。

**【P1-5 资源锁】—— 极高并发下会死锁**
*   **触发条件**：多个任务并发申请交叉的锁组（如任务A锁 [R1, R2]，任务B锁 [R2, R1]）。
*   **后果**：虽然有“排序后逐个 INSERT”，但如果任务A插了R1，任务B插了R2，任务A插R2失败回滚，任务B插R1失败回滚，两者不断重试，形成活锁。且 TTL 60s 太短，如果遇到机器狗清理异常卡住 90 秒，锁被释放，另一辆车冲进去，相撞。
*   **改法**：参考 **VDA5055 的 `zone` 概念**或 Open-RMF 的 `Reservation` 系统。单 worker 下不要搞数据库行锁，直接用 Python 的 `asyncio.Lock` 字典。

**【P1-6 定位策略】—— 会把机器狗搞瘫痪**
*   **触发条件**：机器狗上楼梯、走斜坡、或者被人为抱起移动。
*   **后果**：腿式机器人里程计（odom）在 Z 轴和复杂地形下漂移极大。抱起移动 5m，odom 可能跳变 10m。触发你的“odom 位移 > 5m 但定位未更新”条件，系统疯狂告警甚至触发自动重定位，机器狗在楼梯上突然重定位导致姿态崩溃。
*   **改法**：机器狗的重定位只能依赖底盘自身的 `/location_status` (IMU + Lidar SLAM 状态)。绝对不要用 odom 去反推是否被搬动。

### 2. `order_key` 用 `run-{id}-a{n}` 有什么问题？更稳的生成方式是什么？

**问题**：
*   依赖数据库自增 `attempt` 字段，高并发下会有竞态条件，两个并发请求读到的都是 `attempt=1`，生成了相同的 key。
*   如果任务被 `cancelled` 后又想重发，这个 key 的历史记录还在，唯一约束会冲突。

**更稳的做法**：
*   `order_key` 必须是**无状态生成**的 UUID 或 ULID，保证全局唯一。
*   幂等不应靠 `order_key` 的后缀来区分，而应该靠业务层的前置查询。如果是要防网络重试，用 VDA5050 的标准做法：生成一个 UUID 作为 `order_key`（即 VDA5050 的 `orderId`），前端在发请求时带上这个 key，后端用 `INSERT IGNORE ON CONFLICT DO NOTHING` 处理。

### 3. 7 态状态机是否够用/多余？有没有更简单的等价方案？

**评价**：对于单 worker、无 MQ 的架构，7 态**太多且容易自相矛盾**。`dispatched` 和 `accepted` 在没有异步回调机制的情况下，非常容易导致状态悬挂。

**更简单的方案（4态）**：
*   `planned`：未下发或下发前。
*   `running`：下发成功且车端在执行（包含你的 dispatched, accepted, running）。怎么区分？用 `TaskRun` 表里的 `latest_report_time` 和 `progress` 字段，而不是状态机。如果下发后 10s 没有 report，直接转 `failed`。
*   `done` / `failed`：终态。
*   `paused`：不要作为主状态，用 `is_paused` 布尔字段表示。VDA5050 里 AGV 的 `paused` 是车辆级状态，不是任务级状态，混在一起会把你搞晕。

### 4. 到点判定只加"速度"够吗？还需要什么信号？`arrived_suspect` 会不会变成"永远 suspect"？

**评价**：远远不够。瞬时速度在机器狗上毫无意义。

**需要补充的信号**：
1.  **底盘导航包的终态结果**（最核心）：ROS 的 `actionlib` 或底盘 SDK 返回的 `SUCCEEDED` / `ABORTED`。这是唯一可信的到达标志。
2.  **剩余路径距离**：不仅看当前位置到目标的直线距离，要看 planner 计算出的 `remaining_distance`。直线 1m 中间隔着一堵墙，你判定 arrived 就撞上去了。

**关于 `arrived_suspect`**：
绝对会变成“永远 suspect”。一旦发生 SLAM 漂移，机器狗坐标在地图上乱跳，它永远满足 `1.0m < 距离 ≤ 2.5m`，而你的系统只是“产生告警不重试”，任务卡死在最后一步，现场人员只能去重启。

**建议**：废掉 `arrived_suspect`。导航结果只有 `arrived` 和 `failed`。如果底盘报 `SUCCEEDED` 但距离 > 1m，这说明地图或者坐标系建错了，这是工程部署问题，不是运行时该用状态机去兜底的。

### 5. 资源锁用数据库行锁，在 SQLite 下能不能工作？单 worker 下有没有更简单的做法？什么时候该升级 Redis？

**SQLite 下行锁**：
能工作，但非常脆弱。SQLite 的写锁是数据库级别的。并发写时会频繁遇到 `database is locked` 异常，你处理起来极其恶心。

**单 worker 的更简单做法**：
直接在 FastAPI 进程的内存里维护一个字典：`_locks = Dict[str, str]` (resource_key -> run_id)。使用 Python 的 `asyncio.Lock` 保护这个字典的读写。因为你是单 uvicorn worker，这绝对安全且极快。

**什么时候升级 Redis**：
1.  当你们从单 worker 变成多 worker（比如 `uvicorn --workers 4`）。
2.  当你们引入了第二个服务（比如一个专门算路径的服务也要抢资源锁）。
3.  当你们需要分布式部署控制台时。
在此之前，不要碰 Redis，徒增运维复杂度。

### 6. "odom 位移 > 5m 但定位未更新"在机器狗上成立吗？

**绝对不成立。**
*   腿式机器人没有轮子编码器，它的 odom 靠的是 IMU + 关节电机正运动学推算（State Estimator）。
*   当机器狗被抱起时，腿部悬空乱蹬，关节角度变化，但机身没动，odom 会**凭空向前飘移几十米**。
*   当机器狗走斜坡或不平路面时，足端打滑，odom 漂移极大。
*   如果机器狗自身的 SLAM 定位没更新（Lidar 被遮挡），它会持续信任 odom，odom 飘了 5m，你的系统判定“被搬动了”，触发重定位，结果 Lidar 依然被遮挡，重定位失败，机器狗彻底迷路。

**正确的重定位触发判据**：
只看机器狗底盘上报的 `located=false` (即你说的 `/location_status` = 1) 持续超过 10 秒。**不要自作聪明去算 odom**。底盘厂商的算法已经处理了这些，你只要信它就行了。参考 **VDA5050 的 `localizationParameters`**。

### 7. 如果只能在 3 天内做完 2 条，你选哪 2 条？为什么？

我选 **P0-1（改造订单幂等）** 和 **P1-5（资源锁改为进程内锁）**。

**为什么选这两个？**
1.  **保命优先**：P0-1 不改，网络一抖动，厂区两辆车乱撞或者重复执行动作，直接出安全事故。P1-5 不改，只要有一处窄道，死锁会把你系统的 worker 全部卡住，整个厂区瘫痪。
2.  **见效快**：这两个都是纯后端逻辑改造，不依赖真机调试（你们 JCROB 真机还没到）。3 天时间完全足够写完单测并上线。
3.  **其他可以延后**：P0-2（exec_mode）在单机、简单任务下可以先用 if-else 凑合；P0-3（状态机）和 P0-4（到点判定）没有真机实测改了也是盲改；P1-6（重定位）目前有手工按钮兜底，现场大不了人工介入。
