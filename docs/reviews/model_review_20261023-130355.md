## 豆包 Ark（doubao-seed-evolving）

# “场站-设备-外设-能力”数据模型与模块联动评审建议
## 总体结论
建议采用 **设备模板(Profile)做标准基线 + 外设实例(Peripheral)做真实挂载 + 能力从外设/模板派生** 的混合模型：
- **Profile** 解决“型号默认配置、出厂能力、推荐面板”的复用问题；
- **Peripheral** 解决“同型号实际外设不同、后期加装/替换”的现场事实；
- **Capability 不允许手工随意填写作为事实来源**，应派生生成，可允许 `enabled/override` 做人工禁用或参数修正。

12 月验收最小集建议：**现在必须做 peripheral、capability 派生、面板注册表、事件关联 ID；设备模板可先用 JSON/seed 配置顶住，不必做完整模板管理后台。**

# 1. 数据模型如何选

## 1.1 方案对比

### 方案 A：外设表 + 能力由外设派生

建议表：`peripheral`

```sql
robot_id
type            -- visible_ptz/thermal_ptz/dual_spectrum_ptz/sf6/gas/noise/temp_humidity/dust
vendor
model
channel_code
config_json
status
```

能力通过规则生成：

```text
visible_ptz          -> video.live, ptz.move, photo.capture
thermal_ptz          -> video.thermal, thermometry.capture
sf6_sensor           -> env.sf6.read, alarm.sf6.rule
speaker              -> audio.tts, audio.broadcast
```

**优点：**
- 最贴近现场实际；
- 一台机器人挂几个外设，就渲染几个面板；
- 新增外设主要新增注册项，不改首页主流程；
- 能解决“绝影 X30 Pro”和“JCROB-01”配置不同的问题。

**缺点：**
- 同型号批量录入时重复；
- 外设到能力的派生规则需要维护。

---

### 方案 B：设备模板 Profile + 实例覆盖

例如：

```text
robot_profile: jueying_x30_pro_station
默认外设：
- 海康双光云台：CH101 可见光、CH201 热红外
- SF6
- 温湿度
默认动作：
- navigate
- stand_up
- lie_down
```

实例机器人可以覆盖：

```json
{
  "disabled_capabilities": ["stand_up"],
  "peripheral_overrides": []
}
```

**优点：**
- 批量初始化方便；
- 型号能力清晰；
- 适合厂商机器人标准型号。

**缺点：**
- 如果把 Profile 当成真实配置，会出现“模板说有，但现场没接”的问题；
- 外挂传感器、后期改装、通道变化仍然需要实例表承载。

---

## 1.2 推荐：两者并存，但事实来源不同

推荐定位：

```text
robot_profile = 型号默认值/推荐配置，不是运行时事实
robot         = 机器人实例
peripheral    = 场站现场真实挂载的外设，是面板和驱动路由事实来源
capability    = 由 robot + profile + peripheral 派生出来的运行时能力
```

能力生成优先级：

```text
最终能力 = Profile 默认能力
        + Peripheral 派生能力
        + Robot 显式启用能力
        - 被禁用能力
        - 网关/通道不可用能力
```

建议不要继续让 `robot.capabilities_json` 成为唯一事实来源；它可以短期保留为缓存或兼容字段。

# 2. 参考开源做法：哪套最适合 1-20 台私有化设备

## 推荐优先级

```text
ThingsBoard Device Profile 的“模型分层思想”
+ Home Assistant Device/Entity Registry 的“实例注册思想”
+ 少量 AAS Submodel 的“能力分段思想”
```

如果只能选一套主参考，建议选：

> **Home Graph/Registry 风格：Device + Entity/Peripheral + Capability，Profile 只做初始化模板。**

---

## 2.1 Home Assistant device/entity registry

### 适合点

Home Assistant 的核心关系是：

```text
Device：物理设备，比如摄像头、传感器、机器人
Entity：可读写/可展示的能力实体，比如 camera.living_room、sensor.temperature
Registry：真实发现后的实例注册
```

映射到你们系统：

```text
robot/device      = 机器人或网关
peripheral        = 云台、气体传感器、扬声器
entity/capability = video.visible、sensor.sf6、action.stand_up
```

### 为什么适合你们

- 设备数量只有 1-20 台，实例数据量很小；
- 每台外设都可能不同，Registry 比重型 Profile 更可靠；
- 前端面板可以直接根据 entity/capability 动态生成；
- 支持后续加装设备；
- 私有化部署不需要复杂多租户和规则引擎。

### 不足

- 批量标准化不如 ThingsBoard Profile；
- 自动发现机制你们未必有，需要人工配置或适配器上报。

**结论：作为运行时主模型最合适。**

---

## 2.2 ThingsBoard Device Profile

ThingsBoard 强调：

```text
Device Profile：设备类型、默认规则、遥测字段、告警规则、队列
Device：具体设备实例
Telemetry：时序数据
Alarm：告警
Rule Engine：流转规则
```

### 适合点

- 设备型号标准化；
- 同一型号机器人批量入库；
- 遥测、告警、规则链概念完整。

### 不适合直接照搬的原因

- 对 1-20 台设备偏重；
- Rule Engine、Profile 管理复杂度较高；
- 你们的问题核心不是大规模设备接入，而是“同机型外设异构”和“页面动态渲染”；
- 如果 Profile 过强，反而容易掩盖现场真实挂载差异。

**结论：借鉴 Profile 做默认模板和初始化，不建议照搬完整平台。**

---

## 2.3 AAS Submodel

AAS，即 Asset Administration Shell，资产管理员外壳，把资产分成多个 Submodel：

```text
Asset：资产
Submodel：名称牌、技术参数、传感器、运动能力、维护记录、安全状态等
```

### 适合点

- 工业资产建模规范；
- 适合把机器人能力分成视频、运动、环境感知、安全、维护、文档等模块。

### 不适合作为主实现的原因

- 概念偏复杂；
- 对验收周期和中小团队落地成本高；
- 前端动态面板和工单联动并不会因为 AAS 自动变简单。

**结论：借鉴它的 Submodel 分类即可，不建议完整实现 AAS。**

---

## 最终建议

采用如下组合：

```text
ThingsBoard：
  用 robot_profile 表达型号默认能力和默认外设

Home Assistant：
  用 peripheral/entity/capability registry 表达现场真实设备和可渲染对象

AAS：
  用 domain/category 对能力做分段，例如 motion/video/environment/audio/maintenance
```

# 3. 面板注册表：有什么外设就渲染什么面板

## 3.1 设计原则

主页面不能写：

```text
if visible then VisiblePanel
if thermal then ThermalPanel
```

而应该：

```text
1. 获取当前 robot 的 panels/capabilities
2. 按 panel registry 找到组件
3. 按 layout 配置排序和分组
4. 动态渲染
```

新增粉尘仪时只做：

```text
1. 新增 peripheral type = dust_sensor
2. 注册 capability = env.dust.read
3. 注册 panel = DustMetricPanel
4. 后台给机器人挂载该外设
```

主页面 `DeviceDashboard` 不需要改。

### 1. 数据模型：外设派生 vs 设备模板，能否并存？

**结论：必须并存。** 
“设备模板”用于快速标准化初始配置（解决手填JSON导致的不一致）；“外设表+实例覆盖”用于应对现场硬件的临时变更和异构扩展。

**最小表结构设计（MySQL/PostgreSQL）：**

```sql
-- 1. 机器人模板表 (定义标准机型，如绝影X30 Pro)
CREATE TABLE robot_profile (
    id VARCHAR(50) PRIMARY KEY, -- 如 'x30_pro_standard'
    name VARCHAR(100),
    default_capabilities JSON, -- 标准能力声明 {'navigation': true, 'posture': true}
    default_peripherals JSON   -- 标准外设清单 [{'type':'ptz', 'model':'hik_ch101'}, ...]
);

-- 2. 机器人表 (实例表，保留旧字段以兼容)
CREATE TABLE robot (
    id VARCHAR(50) PRIMARY KEY,
    station_id VARCHAR(50),
    profile_id VARCHAR(50),    -- 关联模板
    name VARCHAR(100),
    adapter_type VARCHAR(50),  -- 适配器类型，如 'jcrob01', 'x30pro'
    ip VARCHAR(50),
    -- 废弃手填的 capabilities_json，改由外设和模板动态计算
    status ENUM('online', 'offline', 'error') DEFAULT 'offline'
);

-- 3. 外设表 (核心！统一收口 sensor 和 video_source)
CREATE TABLE peripheral (
    id VARCHAR(50) PRIMARY KEY,
    robot_id VARCHAR(50),       -- 所属机器人
    type VARCHAR(50) NOT NULL,  -- 外设类型：'ptz', 'gas_sensor', 'env_sensor', 'dust_sensor'
    model VARCHAR(100),         -- 具体型号：'hik_ch101', 'dahua_ptz', 'sf6_sensor'
    config_json JSON,           -- 实例级配置：通道号、波特率、鉴权信息等
    status ENUM('online', 'offline') DEFAULT 'offline'
);

-- 4. 能力视图 (不建物理表，通过配置或视图实现)
-- 能力本质是外设的聚合。后端提供接口时，通过 robot + peripheral 动态聚合返回：
-- GET /robots/{id}/capabilities 
-- 返回: {"navigation": true, "video_channels": 2, "sensors": ["SF6", "Temp", "Hum"]}
```

### 2. 参考开源做法选型

最适合你们 1-20 台设备私有化场景的是：**Home Assistant (HA) 的 Device/Entity Registry 模型**。

**为什么不用其他两个？**
*   **AAS（资产管理员外壳）**：太重。AAS 的 Submodel 设计是为了工业4.0全生命周期跨企业数据交换，对于巡检机器人内部系统来说，属于“杀鸡用牛刀”。
*   **ThingsBoard 的 device profile**：偏向于海量同类物联网设备的遥测数据接入和规则引擎，对“机器人+云台+多种气体传感器”这种强复合、强时序动作的设备建模不够灵活。

**为什么选 HA？**
*   **Device（对应 Robot）**：一个物理实体。
*   **Entity（对应 Peripheral）**：具体的数据源或执行器（如 `camera.visible`, `camera.thermal`, `sensor.sf6`）。
*   **能力隐式派生**：HA 从不强制 Device 必须有什么能力，而是通过枚举 Entity 来动态渲染 UI（Lovelace 仪表盘）。这完美解决了你“首页写死面板”的问题。系统发现有什么 Entity（外设），就渲染什么面板。

---

### 3. 面板注册表（前端解耦方案）

**目标：** 新增“粉尘仪”只需新增一个 Vue/React 组件并注册，主页面代码 0 修改。

**注册表结构示例（前端 TS）：**
```typescript
// panelRegistry.ts
interface PanelConfig {
  type: string;            // 外设类型，匹配 peripheral.type
  component: React.FC;     // 或 Vue 组件
  defaultProps?: object;
  dataParser?: (rawData: any) => any; // 适配不同厂家的数据解析
}

export const PanelRegistry: Record<string, PanelConfig> = {
  // 可见光云台
  'ptz_hik_visible': {
    type: 'ptz',
    component: HikPTZPanel,
    dataParser: (d) => parseHik(d)
  },
  // 大华双光云台 (新增)
  'ptz_dahua_dual': {
    type: 'ptz',
    component: DahuaDualPTZPanel,
  },
  // 粉尘仪 (未来新增，只需加这一段)
  'dust_sensor': {
    type: 'dust_sensor',
    component: DustMonitorPanel
  }
};

// 主页面渲染逻辑 (伪代码)
robot.peripherals.forEach(p => {
  const panel = PanelRegistry[`${p.type}_${p.model}`] || PanelRegistry[p.type];
  if (panel) {
    // 动态渲染对应组件，并传入 config_json 和实时数据流
    <panel.component config={p.config_json} dataStream={getStream(p.id)} />
  }
});
```

### 4. 模块联动事件流（文字时序图）

#### 4.1 传感器超限 -> 处置归档
1. `传感器` 采集到 SF6 数值超限 -> `采集网关` 上报数据至 `MQTT Broker`。
2. `告警服务` 订阅 MQTT 消息 -> 匹配阈值规则 -> 生成 `告警记录`，状态为“未处理”。
3. `工单服务` 监听新告警 -> 自动或由调度员手动生成 `工单`。
4. `通知服务` 将工单信息推送到 `手机APP`（WebSocket/极光推送）。
5. 人员 `手机APP` 现场处置 -> 提交处置结果及照片。
6. `工单服务` 更新状态为“已闭环” -> 同步更新 `告警记录`为“已归档”。

#### 4.2 任务 -> 报表
1. 系统定时下发 `巡检任务` -> `任务调度服务`拆分为多个 `动作点`（坐标+动作）。
2. `机器人控制服务` 逐点下发指令：`导航至点A` -> `到达` -> `打开云台` -> `抓拍` -> `读取气体`。
3. 机器人逐点上传结果（图片流、读数） -> `任务服务`存入 `任务明细表`。
4. 任务完成 -> `报表服务` 汇总任务明细 -> 生成可视化 `巡检报表`。

#### 4.3 告警/任务 -> 录像取证（时间窗联动）
1. `告警/任务` 状态变更为“发生时”。
2. `录像服务` 接收事件信号 -> 查询事件发生前 1 分钟至后 3 分钟的视频切片（时间窗）。
3. 将切片从 `流媒体临时存储` 迁移至 `对象存储`，与告警/工单 ID 绑定归档。

#### 4.4 设备上下线 -> 容量统计
1. 机器人 `心跳服务` 超过 30s 未收到心跳 -> 判定离线。
2. 更新 `robot.status` 和 `peripheral.status`。
3. `系统看板` 轮询/订阅状态变更 -> 统计场站在线率（在线台数/总台数）。

---

### 5. 迁移策略：平滑演进

**保留旧字段，使用中间层过渡。**
1. **保留：** `robot.robot_id`，`sensor.robot_id`，`video_source.robot_id` 不删。
2. **新增：** 引入 `peripheral` 表。
3. **数据同步：** 编写一个一次性脚本，将现有的 `sensor` 和 `video_source` 数据转换为 `peripheral` 表的记录。
   * 原 `sensor` -> `peripheral(type='gas_sensor', config_json={...})`
   * 原 `video_source` -> `peripheral(type='ptz', config_json={channel_id: ...})`
4. **API 适配层：** 前端接口从 `/sensors` 和 `/video_sources` 统一切换为 `/robot/{id}/peripherals`。后端在 `peripherals` 接口中做一层映射，如果查不到新表，再去查旧表兜底。
5. **最终形态：** 12 月验收后，前端完全不再直接请求 sensor/video_source 接口，后端逐渐废弃旧表。

### 6. 12 月验收的最小集

**必须现在做（物理表/代码结构改变）：**
1. **外设表 建立**：必须建立，这是解耦的核心，否则前端面板永远写死。
2. **面板注册表机制**：前端必须重构，根据接口返回的外设列表动态渲染面板组件。
3. **模块联动联动（1-3项）**：告警->工单->手机端闭环；任务->结果->报表。这是验收刚需。
4. **录像取证时间窗**：必须与告警/任务绑定，作为验收证据。

**可以先用 JSON 配置顶住（延迟到二期）：**
1. **设备模板表**：一期先不用物理表，通过代码里的 JSON 配置文件（或 robot 表里暂存一个字段）顶住。只要保证能生成 `peripheral` 表的数据即可。
2. **录像切片精准秒级对齐**：可以先用整段录像下载代替精准时间窗切片，只要文件能和工单挂钩即可。
3. **设备上下线容量统计的大盘**：可以先只显示在线状态，不做过复杂的趋势统计图表。
4. **前后端协议无关化重构**：如果时间极紧，前端先做好组件注册表，但数据来源可以暂时通过原 `sensor` 接口拼装后塞给新组件。但 12 月后必须切底。

**不确定项：**
1. 现场不同厂家云台的控制协议是否已经在底层网关抹平差异？如果网关层没抹平，前端面板解耦了，后端控制层依然会爆炸。这取决于你们的网关适配器现状。
