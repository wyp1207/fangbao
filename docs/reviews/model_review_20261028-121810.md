## 2. 程序化 3D 具体做法

### 网格与分辨率
- **不要**把 900×600 全量建高度场（54 万顶点，核显必崩）
- **地面**：1 个 PlaneGeometry，分割 100×66（约 1m 一格），6500 三角形
- **墙体**：对占据栅格非 0 的像素，每个生成 1 个 Box（0.05×0.05×高），用 **InstancedMesh**，1 个 draw call
  - 900×600 地图占据像素通常 5000-15000 个，按 8000 算 = 9.6 万三角，可接受
  - 如果超 2 万实例，做一次膨胀腐蚀去噪，压到 1 万以内
- **总三角形预算**：地面 1.3 万 + 墙体 10 万 + 机器人 2000 + 告警 2000 + 轨迹 1000 ≈ **12 万**，核显 30fps 安全区

### 材质——怎么不像灰色方块
这是 A 方案成败关键，3 小时就能拉开档次：

| 对象 | 做法 |
|---|---|
| 墙体 | MeshStandardMaterial，color #1a2a3a，emissive #0a1a2a 强度 0.15，roughness 0.8，metalness 0.2。**半透明 opacity 0.65** |
| 墙体描边 | EdgesGeometry + LineBasicMaterial #00d4ff opacity 0.7。**这一步让方块变"全息线框"，颜值 +50%** |
| 地面 | 暗底 #050810 + GridHelper 青色网格 #00aaff（主格 5m，次格 1m）+ 中心十字 #ff8800 |
| 告警柱 | CylinderGeometry r=0.08 h=2.5，MeshBasicMaterial 透明红 + 自定义 shader 脉冲 `emissive = 0.5+0.5*sin(time*4)` |
| 告警底环 | RingGeometry r=0.5，红色光环，扩散动画 |
| 机器人 | 程序化拼：body box 0.6×0.3×0.4 + 4 腿小 box，颜色橙 #ff6600，**比 GLTF 还科技感**，且朝向天然好控制 |
| 点位标签 | CSS2DRenderer（HTML overlay），不要用 Sprite——200 个 sprite 会糊 |

### 光照
- 1 个 HemisphereLight（sky #1a3a5a, ground #050810, intensity 0.6）
- 1 个 DirectionalLight（#ffffff, intensity 0.8，侧顶 45°，**只给机器人开阴影**，墙不开）
- **不要** AmbientLight，会发灰

### 科技感后处理
- EffectComposer 顺序：Render → UnrealBloom（threshold 0.7, strength 0.5, radius 0.4, **半分辨率**）→ FXAA → 扫描线 ShaderPass → Output
- 扫描线：`gl_FragColor.rgb += 0.04 * sin(vUv.y * 800.0 + time * 2.0)`，全屏叠加
- 雾：`scene.fog = new FogExp2(0x050810, 0.015)`，远处自然消失
- 色调统一：暗蓝底 + 青色高光 + 橙色机器人 + 红色告警，四色足够

## 3. 坐标对齐

### A 方案为什么天然对齐
所有数据（地图、点位、位姿、告警）都已是 SLAM 米制坐标，Three.js 世界坐标直接用，无需标定。转换公式：

```
// 像素 -> SLAM 世界坐标
x_world = origin_x + (col + 0.5) * resolution     // -10 + (col+0.5)*0.05
y_world = origin_y + (img_h - row - 0.5) * reso   // -8 + (600-row-0.5)*0.05  ← 注意翻转

// SLAM -> Three.js (Y-up)
three.x = x_world
three.y = 0            // 地面
three.z = y_world      // SLAM 的 y 映射到 three 的 z

// 朝向
robot.quaternion.setFromEuler(new Euler(0, -theta, 0))  // 符号要实测
```

### 必踩的坑（按出现频率排）
1. **y 轴翻转**：PNG 行号从上往下，SLAM y 从下往上。必须 `img_h - row`。90% 的 bug 在这。
2. **像素中心偏移**：占据值代表"该像素区域"，墙中心在 `col+0.5, row+0.5`，不是左上角。差 0.025m，叠墙时会错位。
3. **origin 定义**：ROS 的 origin 是地图**左下角**像素中心的世界坐标，不是左上角。和后端确认一次，别假设。
4. **theta 符号**：ROS yaw 逆时针正（从 +x 到 +y），SLAM y 映射到 three.z 后，Three.js Y 轴旋转方向可能反。**实测**：让机器人原地转，看大屏方向对不对。
5. **resolution 来源**：不要硬编码 0.05，从后端接口拿，或者从 YAML 读。不同地图可能不同。

### B 方案 3 点标定
**算法**（Kabsch + 各向同性缩放）：
1. 收集 3 对对应点：(SLAM 坐标 p_i) ↔ (模型坐标 m_i)，选分散的物理位置（如"大门左柱""储罐中心""路口"）
2. 中心化：q_i = p_i - centroid_p，r_i = m_i - centroid_m
3. H = Σ q_i · r_iᵀ（3×3）
4. SVD：H = UΣVᵀ，R = V·Uᵀ（若 det(R)=-1 则 V 最后一列取反）
5. 缩放：s = (Σ|r_i|) / (Σ|q_i|)
6. 平移：t = centroid_m - s·R·centroid_p
7. 最终 4×4：`[sR, t; 0, 1]`

**UI**：
- 左侧 2D 栅格图（可点击），右侧 3D 模型三视图（俯视为主）
- 用户各点 3 个同名点，配对高亮
- 实时显示残差（每对点对齐后误差），> 0.2m 标红
- **要求标 4 个点**：3 个求矩阵，第 4 个验证，最大误差 < 0.1m 才允许保存
- 导出 `transform.json`：`{matrix4: [...], scale, residual_max, residual_mean}`

**误差来源**：模型本身比例不准（最常见）、点位选了非刚性位置（如门会开合）、模型坐标原点不在地面。

## 4. 性能与兼容

### draw call 预算（目标 ≤ 10）
| 项 | draw call |
|---|---|
| 地面 | 1 |
| 墙体 InstancedMesh | 1 |
| 机器人 | 1 |
| 告警柱（≤10 个，合 1 个 InstancedMesh）| 1 |
| 轨迹 Line2 | 1 |
| GridHelper | 1 |
| 后处理 Composer | 3-4 |
| **合计** | **9-10** |

### 显存
- 地图纹理 900×600 RGBA：2MB
- RenderTarget（1080p, half-res bloom）：8MB
- GLB 模型（B 阶段）：控制在 50MB 以内
- 总计 < 100MB，核显无压力

### 核显（Intel UHD 620 级别）优化清单
- `renderer.setPixelRatio(Math.min(devicePixelRatio, 1.5))`，**不要**用 2
- 阴影只给机器人，mapSize 1024×1024
- Bloom 用半分辨率 RenderTarget
- 抗锯齿用 FXAA，**不用** MSAA
- `powerPreference: 'high-performance'`
- 实测预期：12 万三角 + 上述配置，UHD 620 稳定 30-40fps

### 兼容
- Three.js r150+，WebGL2 优先
- 浏览器：Chrome/Edge 90+（内网工控机大概率是这俩）
- **内网无 CDN**：所有依赖本地化，`npm install three` 后 `vite build` 打包进 dist

## 5. 产品与汇报

### A 能不能说服领导
**能，但话术要换。** 不要说"我们做了 3D 孪生"，要说：

> "参考图是静态渲染图，我们做的是**实时数字孪生**——大屏上机器人位置、告警、轨迹全是真机实时数据驱动，不是贴片动画。3 天能做出这个动态效果，是因为我们复用了已有的 SLAM 坐标系，没花时间在假模型上。"

演示时**现场操作**：
1. 让机器人走一步 → 大屏同步动（延迟 < 200ms）→ 客户会"哇"
2. 触发测试告警 → 红柱 + 光环 + 列表 → 客户会"哇"
3. 拖动时间轴看历史轨迹回放 → 强化"真"

这三点是 B 方案（假模型）3 天内做不到的。

### 验收指标（写进合同）
| 指标 | 值 | 备注 |
|---|---|---|
| 帧率 | ≥30fps（核显）/ ≥60fps（独显） | 用 stats.js 实时显示 |
| 位姿端到端延迟 | <300ms | 机器人发 → WS → 前端渲染 |
| 点位显示误差 | <0.05m（1 像素） | 对比 2D 地图同名点 |
| 告警响应 | <1s | 触发 → 3D 显示 |
| 轨迹回放 | 24h，拖动响应 <500ms | |
| 同时在线机器人数 | ≥2 | 为多机预留 |

**不要写**"看起来像参考图"——主观指标无法验收，会被扯皮。

## 7. 只允许改一处

**把位姿推送从 HTTP 轮询改成 WebSocket，10Hz 推送 + 前端插值。**

理由：3 天演示成败在于"实时感"。1Hz 轮询的位姿，机器人像瞬移，再炫的 3D 也救不了。10Hz + lerp 插值，机器人丝滑移动，就算 3D 是方块拼的，客户也觉得"真"。

FastAPI 加 WebSocket 是 30 行代码，前端原生支持，半天能上。

**如果限定只能改 3D 相关的一处**：把墙体从纯色 Box 改成 **半透明 + EdgesGeometry 青色描边**。2 小时工作量，从"积木"变"全息投影"，颜值 +50%。
