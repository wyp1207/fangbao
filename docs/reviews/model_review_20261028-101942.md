### 二、 10个最该补的联调用例（可直接复制执行）

**1. 背景循环阻塞测试（验证单worker无MQ的死穴）**
*   **前置:** 登录系统获取Cookie，本地模拟器在线。
*   **步骤:** 
    ```bash
    # 终端1：发起一个极慢的HTTP请求（模拟慢SQL或长计算），卡住唯一的worker
    curl -X POST http://localhost:8000/api/slow_task -b "Cookie..."
    # 终端2：在慢请求处理期间，立刻发起获取设备状态请求
    time curl http://localhost:8000/api/devices/status -b "Cookie..."
    ```
*   **断言:** 第二个请求不应等待第一个完成，应在 < 200ms 内返回。
*   **失败意味着:** 单 worker 架构下，慢请求会阻塞全局心跳和轮询，设备会大面积掉线。必须把耗时任务改为 `BackgroundTasks` 或限流。

**2. 审计哈希链与业务并发冲突（验证SQLite锁/MySQL事务）**
*   **前置:** Python 脚本引入 `requests` 和 `concurrent.futures`。
*   **步骤:** 并发 20 个线程同时调用 `/api/巡检任务下发` 接口。
*   **断言:** 返回中无 500 错误（SQLite "database is locked" 或 MySQL 死锁），查询审计表 `hash_chain` 字段无重复、无断裂。
*   **失败意味着:** 审计哈希计算逻辑未加行锁或乐观锁，高并发下哈希链断裂，系统安全合规性归零。

**3. 轮询与WS状态竞态（验证状态同步）**
*   **前置:** 前端打开WS连接，后端设备轮询周期设为 2s。
*   **步骤:** 脚本瞬间向模拟器发送 5 次状态变更（如 空闲->巡检->报警->空闲->报警）。
*   **断言:** 查后端 DB 最终态为 "报警"；前端 WS 收到的事件流包含中间态，且最终落点为 "报警"。
*   **失败意味着:** 轮询覆盖了事件驱动状态，存在状态机翻转 bug。

**4. 任务看门狗接管测试**
*   **前置:** 模拟器在线，下发一个巡航任务。
*   **步骤:** 在模拟器代码中 `time.sleep(100)` 模拟设备卡死不回传坐标。
*   **断言:** 看门狗线程在规定时间（如 10s）后触发工单升级，DB 中任务状态变为 `超时/异常`，并触发通知分发。
*   **失败意味着:** 看门狗逻辑失效，真实场景中设备卡死会导致任务永远挂起。

**5. 磁盘监控与保留期清理冲突**
*   **前置:** 测试环境磁盘留 5% 空间。
*   **步骤:** 触发保留期清理任务（清理大量历史遥测数据）。
*   **断言:** 清理任务正常完成，不因磁盘空间不足导致 SQLite/MySQL 写入崩溃；磁盘监控告警发出但未阻断清理。
*   **失败意味着:** 磁盘满时系统直接宕机，且无法自愈。

**6. CSRF 双提交校验（绕过尝试）**
*   **前置:** 获取合法 JWT Cookie。
*   **步骤:** `curl -X POST http://localhost:8000/api/devices/reboot -b "jwt=xxx"`（不带 X-CSRF-Token 头）。
*   **断言:** 返回 403 Forbidden。
*   **失败意味着:** CSRF 防护失效，存在越权操作风险。

**7. 离线设备任务下发补偿**
*   **前置:** 模拟器网络断开（端口不通）。
*   **步骤:** 调用接口下发巡航任务。
*   **断言:** 接口返回 `202 Accepted` 或 `409 Conflict`（看业务定义），DB 生成任务记录。模拟器重连后，轮询/调度线程自动下发该任务。
*   **失败意味着:** 设备离线时下发任务直接 500 报错，或重连后任务丢失。

**8. WS 重连与鉴权**
*   **前置:** 前端建立 WS 连接。
*   **步骤:** 后端重启 uvicorn；前端脚本断线重连，重连时携带过期 JWT。
*   **断言:** 前端识别 401 关闭 WS，不陷入死循环重连；JWT 正确时重连成功并补发期间漏掉的心跳。
*   **失败意味着:** 弱网环境下前端会耗尽浏览器资源，或引发安全问题。

**9. 传感器UDP高频打流（防UDP丢包与锁库）**
*   **前置:** Python 脚本 `socket` 连接传感器网关 UDP 端口。
*   **步骤:** 以 50ms 间隔发送 1000 个模拟温度报警数据。
*   **断言:** 后端聚合线程正确累加，DB 写入无死锁，前端 WS 推送频率被限流（不会打爆浏览器）。
*   **失败意味着:** 遥测聚合逻辑在真实传感器高频上报时会拖垮 DB。

**10. 通知分发降级测试**
*   **前置:** 配置通知接口为无效的钉钉/企微 URL。
*   **步骤:** 触发告警（如设备离线）。
*   **断言:** 通知分发线程捕获 HTTP 错误，记录失败日志，但不影响主业务流程（工单升级、审计记录正常）。
*   **失败意味着:** 外部通知 API 宕机会阻塞系统内部线程。

### 三、 我们这套架构的 5 个 "联调必翻车点"

1.  **单 Uvicorn Worker + 无 MQ 的请求阻塞（极高危）**
    *   **翻车点:** FastAPI 虽是异步，但如果你们在巡航、清理、聚合等背景循环里用了同步的 SQLAlchemy 操作（或 `time.sleep`），会直接卡死事件循环。此时所有 HTTP 请求和 WS 推送都会超时。
    *   **提前发现:** 用上面的用例1，强行制造慢请求，看系统是否瘫痪。
2.  **SQLite 并发写锁与 MySQL 的语法兼容性盲区（高危）**
    *   **翻车点:** 你们双支持 SQLite/MySQL。SQLite 极度怕并发写（哪怕有 WAL），而 MySQL 怕长事务。如果联调时多个后台线程同时写审计表/工单表，SQLite 必然 `database is locked`。此外，如果代码里用到了 MySQL 特有的 `ON DUPLICATE KEY UPDATE` 或 SQLite 特有的 `INSERT OR REPLACE`，切换环境必崩。
    *   **提前发现:** 跑用例2的并发测试，并全局搜索 SQL 语句，确认 ORM 层用的是通用方言。
3.  **轮询式状态同步 vs WS 事件驱动的竞态（中危）**
    *   **翻车点:** 设备轮询每 3s 写一次 DB，WS 又在实时推状态。如果某次轮询由于网络延迟晚回了 2s，而设备在这 2s 内已经改变了状态，晚回的旧数据会覆盖 DB 里的新数据，前端 WS 也会收到状态回退。
    *   **提前发现:** 用用例3，高频打状态变更，查 DB 是否出现时间戳倒流。
4.  **10 个背景循环的资源争抢（中危）**
    *   **翻车点:** 轮询、清理、聚合、看门狗等 10 个死循环跑在一个进程里。如果它们共享一个数据库连接池（比如 size=5），一旦清理任务大批量删除数据占满连接，设备轮询拿不到连接，设备全掉线。
    *   **提前发现:** 人为往 DB 塞 100 万条遥测数据，触发保留期清理，同时观察设备在线状态是否闪断。
5.  **X30 设备 TCP/UDP 的粘包与乱序（隐患）**
    *   **翻车点:** 本地模拟器可能用的是简单的 JSON 文本帧，但 X30 真机用 TCP 30000 + UDP 43893。TCP 必然存在粘包/半包问题。如果后端解析是按 `recv(1024)` 直接当完整包处理，真机一接必崩。
    *   **提前发现:** 模拟器发包时，把两个报文拼在一个 UDP 包里发，看后端解析是否报错。

### 四、 做不了的部分怎么诚实地讲

**1. 必须真机/HIL/压测集群才能测的：**
*   **真机通信适配度:** JCROB（HTTP/WS）和 X30（TCP/UDP）的具体报文端序、心跳机制、断连重连策略。现在两台都不通，纯靠模拟器，存在"模拟器能通，真机接上就废"的风险。
*   **高并发全链路压测:** 单 worker 无 Redis/MQ 架构，不用集群压测，无法评估超过 50 台设备同时上线时的系统承载能力。
*   **防爆与物理环境:** 机器人的防爆认证、传感器在危险环境的实际响应延迟。

**2. 替代方案与覆盖度：**
*   **协议挡板:** 用 Python 写死 X30 的报文结构（含包头、校验和、长度域），注入网络抖动（`netem`）和粘包，能覆盖 **80%** 的后端协议解析逻辑。
*   **故障注入:** 通过 `tc` 命令断网、`cgroups` 限制 CPU/内存、`dd` 塞满磁盘，能覆盖 **90%** 的系统级容灾自愈逻辑。
*   **并发模拟:** 用 `locust` 在本机打 50 个并发用户，能暴露 **60%** 的数据库锁和单 worker 阻塞问题（因为受限于本机网卡和 CPU）。

**3. 验收材料表述话术（不吹牛）：**
> "本项目已完成基于本地模拟器的全链路业务联调，覆盖 6 大核心模块与 10 个边界异常场景。在无真机接入条件下，采用协议挡板与网络故障注入技术，验证了后端服务在单点部署架构下的状态一致性、看门狗自愈能力及数据库并发安全性。**暂未覆盖**真实硬件协议握手与集群高可用压测，此项待厂区网络打通后作为二期验收节点。"
