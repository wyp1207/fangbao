# 产品视角评审

## 1. 数据模型：直接绑 robot_id 即可，暂不需要能力中间表

**建议：直接在 `sensor` 和 `video_source` 表加 `robot_id`，不要一期就上"设备能力模型"。**

两种方案的代价差：

| 维度 | 直接 `robot_id` | 能力/外设清单中间表 |
|---|---|---|
| 改造成本 | 加 1 个字段 + 索引，1~2 天 | 抽象 capability/device_peripheral 模型，3~7 天 |
| 页面取数 | 按 robot_id 直接查三张表 | 要先查能力清单，再反查实体，接口更绕 |
| 适合场景 | 外设种类固定：相机、传感器、动作 | 同一种外设多实例、可热插拔、跨设备模板复用 |
| 风险 | 动作能力无处安放，需要单独处理 | 容易过度设计，12 月交付风险高 |

**动作不要硬塞 sensor 表。** 建议一期在 `robot` 表加一个能力字段：

```json
// robot.capabilities，JSON 字段
["navigate", "ptz", "stand_up", "lie_down"]
```

或者更明确：

```json
{
  "motion": ["navigate", "stand_up", "lie_down"],
  "ptz": true
}
```

产品上控制面板直接按这个字段渲染：
- 绝影 X30 Pro：显示【起立】【趴下】【导航】【云台控制】
- JCROB-01：只显示【导航】【云台控制】，不显示或置灰【起立/趴下】

**推荐不显示**，而不是置灰。用户当前只操作这台设备，长期置灰会制造困惑；可在设备详情里说明“不支持该动作”。

中间表可以二期再做，例如：

```text
robot_peripheral
- id
- robot_id
- peripheral_type：camera / sensor / ptz
- entity_type：video_source / sensor
- entity_id
- status：online / offline / disabled
- installed_at
```

一期判断标准很简单：如果只是“页面按设备展示不同相机、传感器、动作”，`robot_id + capabilities` 足够。

## 2. 页面形态：动态渲染面板，不按设备类型做模板

建议采用 **“一个设备巡检页骨架 + 面板内部动态渲染”**，不要按“四足设备页 / 轮式设备页”分别写模板。

原因：
- 现场差异来自“外设和能力不同”，不一定来自设备类型。未来可能有两台同型号机器人，但挂载不同传感器。
- 按设备类型做模板，会把“四足、轮式”误当成差异来源，后续增加轨道机器人、轮式巡检机器人会产生多套页面。
- 当前设备数量不多，动态组件复杂度可控。

推荐页面结构：

```text
DeviceInspectionPage
├── DeviceHeader：设备名、在线状态、当前点位、电量/网络
├── VideoPanelGroup：按 video_source 动态生成
│   ├── VideoPanel：可见光 CH101
│   └── VideoPanel：热红外 CH201
├── EnvironmentPanelGroup：按 sensor 动态生成
│   ├── SensorCard：SF6
│   ├── SensorCard：温度
│   └── SensorCard：湿度
├── ControlPanel：按 capabilities 动态生成
└── Alarm / TaskPanel：按 robot_id 查询
```

但不建议做“完全无规则的拖拽式动态页面”。产品上应固定面板区域和排序规则：

1. 视频区固定在最上方。
2. 环境传感器在中部，按传感器类型排序：气体类 → 温湿度类 → 噪声类。
3. 控制区固定在右侧或下方，按动作风险排序：导航、云台在前，起立/趴下等本体动作分组放置。
4. 没有数据的区域展示空状态，例如“该设备未配置 SF6 传感器”，而不是整个页面错乱。

**组件建议：**

```text
<DeviceInspectionPage robotId="xxx">
  <DeviceHeader />
  <VideoPanelGroup channels={videoSources} />
  <EnvironmentPanelGroup sensors={sensors} />
  <ControlPanel capabilities={capabilities} />
</DeviceInspectionPage>
```

相机不要只按“可见光/热红外”写死两个槽位，而应按通道列表循环渲染；UI 上可根据 `channel_type` 选择播放器组件。

## 3. 切换设备时要重新拉什么，如何避免串台

切换设备时，不能只换页面标题，至少重新拉：

```text
GET /api/robots/{robot_id}/inspection-overview
GET /api/robots/{robot_id}/video-sources
GET /api/robots/{robot_id}/sensors/latest
GET /api/robots/{robot_id}/capabilities
```

```text
GET /api/robots/{robot_id}/inspection-overview

    { "action": "stand_up", "name": "起立", "danger_level": "medium" }
  ]

```

切换时前端流程建议：

1. URL 必须带设备 ID：`/inspection/robots/{robot_id}`，保证刷新、分享、浏览器前进后退都正确。
2. 切设备前停止旧设备的实时订阅：
   - 销毁旧视频播放器。
   - 关闭旧 WebSocket 频道。
   - 清理旧定时器和 MQTT 订阅。
3. 发起新 robot_id 的接口请求。
4. 请求返回前：
   - 保留页面框架；
   - 内容区显示 Skeleton；
   - 不清空整个页面到白屏。
5. 数据返回后一次性替换 `currentRobotState`。
6. 所有实时消息必须校验 `robot_id`，不是当前设备的消息一律丢弃。

防闪烁建议：

```text
切换中：
- Header 显示新设备名 + 小 loading
- 视频区显示通道级骨架屏
- 环境卡显示旧值缓存或骨架屏，二选一

推荐：
- 已访问过的设备展示缓存数据，同时后台刷新
- 新设备展示骨架屏
- 视频流必须等新 play_url 返回后再重建播放器
```

防串台要做三层：

```text
1. 请求防串：使用 requestId / robotId 校验，过期响应不写入状态。
2. 实时消息防串：message.robot_id !== currentRobotId 直接丢弃。
3. 视频防串：先 destroy 旧 player，再用新 source_id 初始化。
```

伪代码：

```ts
const currentRequestId = ref("")

async function switchRobot(robotId: string) {
  const requestId = crypto.randomUUID()
  currentRequestId.value = requestId

  unsubscribeRealtime(currentRobotId.value)
  destroyAllVideoPlayers()

  const data = await fetchInspectionOverview(robotId)

  // 防止用户快速切换 A -> B -> A，旧请求覆盖新数据
  if (currentRequestId.value !== requestId) return

  currentRobotId.value = robotId
  pageState.value = data

  subscribeRealtime(robotId)
  initVideoPlayers(data.video_sources)
}
```

## 4. 旧数据迁移：先“零损迁移”，再逐步绑定

不建议直接把没有 `robot_id` 的历史数据物理删除，也不建议让未绑定数据继续出现在所有设备页。

推荐迁移分四步：

### 第一步：表字段先加，允许为空

```text
sensor
- robot_id varchar(64) null
- bind_status enum：unbound / bound / invalid

video_source
- robot_id varchar(64) null
- bind_status enum：unbound / bound / invalid
```

加索引：

```sql
CREATE INDEX idx_sensor_robot_id ON sensor(robot_id);
CREATE INDEX idx_video_source_robot_id ON video_source(robot_id);
```

### 第二步：新页面只查已绑定数据

设备页接口必须严格限定：

```sql
SELECT * FROM sensor
WHERE robot_id = :robot_id
  AND bind_status = 'bound';

SELECT * FROM video_source
WHERE robot_id = :robot_id
  AND bind_status = 'bound';
```

历史未绑定数据不能作为全局数据继续展示在某台设备下，否则还是会串台。

### 第三步：提供“设备外设绑定/迁移管理页”

最小管理能力：
- 查看未绑定传感器列表；
- 查看未绑定视频通道列表；
- 按场站、设备筛选；
- 将传感器/通道绑定到具体设备；
- 支持批量绑定；
- 绑定后预览设备页数据是否正确。

列表字段建议：

```text
未绑定传感器：
- sensor_id
- 原始名称
- sensor_type
- station_id
- 最近上报时间
- 最近值
- 候选设备

未绑定视频：
- source_id
- 通道编码
- 相机厂商
- 通道类型
- station_id
- 最近在线时间
- 候选设备
```

如果现场能确认“实验室”当前只有两台设备，可以先按场站和通道编码辅助迁移，例如：
- 海康 CH101 / CH201 → 绝影 X30 Pro
- 大华通道 → JCROB-01

但**不建议纯靠名称自动迁移**，尤其不能用“海康=某台设备”这种弱规则直接改生产数据。最多生成“推荐绑定”，由实施人员确认。

### 第四步：历史数据分区处理

这里要区分“外设配置数据”和“历史采样数据”。

外设表可以直接绑定：

```text
sensor.robot_id
video_source.robot_id
```

历史传感器数据量如果很大，不一定要立刻回填每一条历史记录。可采用两种策略：

**省事方案：推荐一期**
- `sensor_latest` / 当前配置绑定 robot_id；
- 历史时序表通过 `sensor_id -> sensor.robot_id` 关联查询设备；
- 不批量改历史数据表。

**彻底方案：二期或数据量小时做**
- 在 `sensor_data`、`video_snapshot`、`alarm` 等历史表冗余 `robot_id`；
- 分批回填，按时间片迁移；
- 每次迁移限制 5 万~10 万行，避免锁表。

历史数据迁移时还要考虑设备换挂传感器的问题。严格来说，一条历史数据属于“当时安装在哪个设备上”。如果未来传感器会拆卸换设备，需要二期增加绑定关系流水：

```text
robot_peripheral_binding
- id
- robot_id
- sensor_id / video_source_id
- bound_at
- unbound_at
- created_by
```

一期如果传感器不频繁拆装，可以先不做。

## 5. 12 月交付的最小可行方案与二期范围

### 一期必须交付：MVP

目标：**不再串台，每台设备看到的就是自己的视频、传感器和动作。**

必须做：

1. **数据模型**
   - `sensor.robot_id`
   - `video_source.robot_id`
   - `robot.capabilities`
   - 所有查询按 `robot_id` 隔离。

2. **设备页接口**
   - 一个聚合接口：
     ```text
     GET /api/robots/{robot_id}/inspection-overview
     ```
   - 或三个简单接口：
     ```text
     GET /api/robots/{robot_id}/video-sources
     GET /api/robots/{robot_id}/sensors/latest
     GET /api/robots/{robot_id}
     ```

   12 月时间紧，推荐聚合接口，前端渲染和联调更简单。

3. **前端页面**
   - `/inspection/robots/{robot_id}`
   - 一个设备巡检页模板；
   - 视频、环境、控制三个区域动态渲染；
   - 无传感器/无视频时有空状态；
   - 不支持的动作不展示。

4. **实时隔离**
   - WebSocket / MQTT 消息带 `robot_id`；
   - 前端只订阅当前设备；
   - 切设备先退订旧频道，再订阅新频道。

5. **旧数据处理**
   - 字段先允许为空；
   - 提供简单绑定页面或后台脚本；
   - 实验室两台设备的传感器和通道必须在上线前人工确认绑定；
   - 未绑定数据不进入设备页。

6. **埋点或校验**
   - 接口返回的每个传感器、相机都必须带 `robot_id`；
   - 前端收到非当前设备消息时打印 warning 并丢弃；
   - 测试用例覆盖：
     - 打开 X30 Pro，只看见海康 CH101/CH201、SF6、温湿度；
     - 打开 JCROB-01，只看见大华通道、噪声、气体；
     - 快速连续切换两台设备，不出现旧设备数据；
     - JCROB-01 不显示起立/趴下；
     - 刷新页面后仍停留在正确设备。

### 可以二期做

1. 标准“设备能力中心 / 外设清单”：
   ```text
   robot_peripheral
   peripheral_model
   robot_capability
   robot_peripheral_binding
   ```

2. 面板拖拽布局、自定义首页、设备页面布局模板。

3. 外设热插拔自动发现和自动注册。

4. 传感器拆装历史、设备挂载关系时间线。

5. 动作权限、二次确认、危险动作联动，例如起立前检测周围空间。

6. 视频多设备巡墙、全局总览页。

7. 历史数据全量回填 `robot_id`。

8. 设备型号到默认能力/默认外设的模板化配置。

## 智谱 GLM（glm-5.2）

以下是对"按设备分页面"信息架构设计的评审与落地方案，分为产品与后端架构两大部分。

---

### 一、 产品侧设计（交互、信息架构与前端）

**1. 页面架构选择：动态渲染面板 vs 设备类型模板？**
**结论：动态渲染面板（组件化）更好维护，且是本需求的唯一正解。**
不同设备的外设组合是"排列组合"（如绝影有可见光+热红外+SF6，而JCROB只有单通道+噪声），如果用"设备类型模板"，每新增一种设备型号就要写一个新页面，前端会爆炸。
*具体实现建议*：
将页面定义为"插槽"布局。设备接口返回 `capabilities` 数组，前端按数组顺序渲染对应组件。
```json
// 绝影 X30 Pro 的页面渲染配置
{
  "device_id": "X30-001",
  "layout": {
    "video_panels": [
      {"component": "VideoPlayer", "channel": "vis", "props": {"src": "rtsp://...CH101"}},
      {"component": "VideoPlayer", "channel": "thermal", "props": {"src": "rtsp://...CH201"}}
    ],
    "env_panels": [
      {"component": "GasSensorCard", "type": "SF6"},
      {"component": "TempHumiCard", "type": "TH"}
    ],
    "control_panels": [
      {"component": "RobotActionPad", "actions": ["stand_up", "lie_down", "navigate"]},
      {"component": "PTZController", "vendor": "hikvision"}
    ]
  }
}
```

**2. 切换设备时的数据加载与防串台/防闪烁**
*   **应该重新拉取的数据**：设备详情（含外设清单）、各通道视频流地址（RTSP/WebRTC）、最新一帧环境数据、当前云台状态。
*   **避免串台（核心痛点）**：
    *   切换设备时，前端必须为所有异步请求生成一个全局递增的 `requestId`（或使用设备ID作为命名空间）。
    *   在 Axios 响应拦截器中判断：如果响应的 `requestId` 小于当前最新的 `requestId`，直接丢弃响应（不作任何状态更新）。
    *   WebSocket 订阅同理：切换设备前先 `unsubscribe` 旧设备的 topic，再 `subscribe` 新设备，且收到的消息需校验 `device_id` 是否与当前激活的设备匹配。
*   **避免闪烁**：前端状态机引入 `loading | loaded | error` 三个状态。切换设备时，保留旧页面骨架，叠加半透明 Loading 遮罩，新设备数据全部 `loaded` 后，一次性替换整个页面状态（类似 React 的 `Suspense` 机制）。

**3. 迁移旧数据的最稳方案**
**结论：在后端做数据兜底与清洗，前端无感切换。**
对于没有 `robot_id` 的历史数据，不能让前端去猜。
*   如果旧系统只有一台设备在场站：后端写迁移脚本，将该场站的历史 `sensor_data` 和 `video_sources` 强行绑定到该场站的默认设备上。
*   如果旧系统有多台设备但没记录：基于时间线做"隔离"。新数据严格走带 `robot_id` 的新接口；历史数据提供独立的"历史回放"只读接口，在页面上打上"历史数据（未绑定具体设备）"的标签。

**4. 12月交付：最小可行方案（MVP）与二期规划**
*   **一期（12月交付 MVP）**：
    *   后端直接在 `sensors` 和 `video_sources` 表加 `robot_id` 字段，硬编码设备与外设的关系（不做中间表）。
    *   前端写死两个布局配置（四足模板、轮式模板），根据设备型号加载对应模板。
    *   实现"切换设备时取消请求"的防串台机制。
*   **二期（后续迭代）**：
    *   引入"设备能力模型"（后端中间表），实现完全动态的面板渲染。
    *   抽离所有控制面板、视频面板为独立微件，支持用户自定义拖拽布局。

### 二、 后端架构侧设计（数据模型与接口）

**1. 数据模型定夺：直接绑设备 vs 能力中间表？**
**结论：12月交付选"直接绑设备"（省事），长期演进选"引入中间表"（低耦合）。两者代价差一个数量级。**

*   **方案 A：直接绑字段（`sensor.robot_id` / `video_source.robot_id`）**
    *   **代价**：表结构存在冗余。如果某天"绝影X30"全量换装新型温湿度传感器，你要去改 `devices`、`sensors` 关联的代码逻辑。
    *   **适用场景**：设备种类极少（<5种），外设极少变动的早期项目。
*   **方案 B：设备能力/外设清单中间表（推荐架构）**
    *   **模型设计**：
        1.  `devices` (设备表): `id`, `station_id`, `device_type` (四足/轮式), `vendor_model` (X30 Pro)
        2.  `peripherals` (外设表): `id`, `device_id`, `ptype` (camera/sensor/ptz), `vendor_model` (海康CH101/大华PTZ/SF6), `meta_data` (JSON, 存通道号、RTSP地址、量程等)
        3.  `telemetry` (时序数据表): `id`, `device_id`, `peripheral_id`, `metric_name` (温度/SF6浓度), `value`, `ts`
    *   **代价**：查询时需要 Join 或多次查询，组装页面数据的逻辑变复杂。
    *   **收益**：设备换相机/传感器，只需增删 `peripherals` 表记录，代码零修改。

**2. 接口设计建议**
为了支撑前端的动态渲染，后端需提供一个聚合接口 `GET /api/v1/devices/{device_id}/manifest`：
```json
{
  "device_id": "X30-001",
  "station_name": "实验室",
  "capabilities": {
    "video_streams": [
      {"stream_id": "vis_1", "name": "可见光", "url": "rtsp://...", "proto": "rtsp"}
    ],
    "sensors": [
      {"sensor_id": "s_01", "type": "SF6", "unit": "ppm", "current_value": 0.1}
    ],
    "controls": [
      {"action_id": "stand_up", "name": "起立", "api": "POST /api/v1/robots/X30-001/actions", "params": {"cmd": "stand_up"}},
      {"action_id": "ptz", "name": "云台控制", "api": "wss://.../ws/ptz/X30-001"}
    ]
  }
}
```
**控制动作的下发**：前端不应根据设备类型写死调用哪个接口。应采用统一的指令通道，如 `POST /api/v1/devices/{device_id}/commands`，Body 中带 `{"cmd": "stand_up"}` 或 `{"cmd": "ptz_move", "args": {"direction": "left"}}`，由后端网关分发给具体设备的 SDK。

**3. 不确定的部分**
*   **不确定**：贵司现有的视频流架构是否支持动态通道注册。如果视频流是固定拉流再转码分发的，切换设备时不仅前端要换地址，后端的流媒体网关可能也要动态销毁旧拉流任务、新建新拉流任务。这部分需要评估网关（如 ZLMediaKit/SRS）的动态接口开销，可能成为12月交付的性能瓶颈。
