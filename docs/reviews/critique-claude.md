## 总判断

**这不是一个已经成立的“防爆巡检平台”，而是一个“以第三方机器人为被控对象、以只读监控/告警/工单为主、核心巡检闭环尚未打通”的上位机软件。**

它有两个半闭环：

- **管理闭环成立**：告警 → 自动工单 → 通知/升级 → 手机接单 → 拍照完成；这是真代码、真数据，现场可复现。
- **监控闭环成立，但对象是模拟器**：设备/位姿/地图/视频/驾驶舱都能跑，当前在线的是本地模拟器，不是真机。
- **巡检闭环不成立**：任务 → 真机导航 → 到点 → 执行拍照/测温/气体检测 → 证据 → AI → 报表，缺的正是“真机导航”和“到点执行动作”两段。

## 最硬的五条代码证据

1. **模板下发直接 501**：`task_templates.py:195-205`。
2. **执行下发默认 403，且订单没有坐标**：`task_dispatch.py:38-52`、`:66-84` 只放 `pointId/pointName`；X30 会去 `(0,0,0)`，JCROB 只收到拍照动作。
3. **JCROB 真机巡航不会移动**：`cruise.py:126-135` 的回退 action 没有 `actionType`，`http_adapter.py:148` 默认按 `photo` 处理，导航变成拍照。模拟器有 `goto()`，所以演示能动；真机没有。
4. **到点不执行巡检动作**：`cruise.py:82-112` 完全没读 `step.action`，结果只写 `point/x/y`（`:107`）。
5. **到达判定不可靠**：只看 `FINISHED`，不看订单号/位姿（`cruise.py:149-153`）；JCROB 任务列表为空时直接返回 `FINISHED`（`http_adapter.py:182-190`）。另外前端“取消”调的是通用 `/cancel`，不会停巡航线程（`TaskRuns.vue:146-155`、`task_runs.py:346-371`），可能继续下发下一个点。

## 与成熟系统的差距

- **行业标配、我们缺**：GB28181/ONVIF/PTZ/NVR、标准订单/状态协议（VDA5050/Open-RMF）、车队队列/交通管制/充电调度、本体自主恢复、到点动作编排、AI 推理、3D/点云、功能安全/防爆系统集成、等保/灾备/断网续传。
- **我们有、但行业也一般**：告警工单手机闭环、人工巡检扫码拍照、通知重试/HMAC、RBAC/审计/TOTP、地图点位校验、私有化轻部署、UI 清晰。这些是加分项，不是护城河。

市场位置建议：12 月走 **“JCROB 配套上位机（单机版）”**，不要叫“平台”；“机器人无关的 supervisory layer”放 2027；全栈平台路线 12 月不可能。

## 巡航模型判断

“平台逐点下发、等到达、再下一点”作为**单机 fallback 是成立的**，但作为产品架构不成立：它把订单降级成 RPC，把“到达”当成“完成”，没有动作、没有 orderId 绑定、没有并发语义。更标准的做法是：

1. **12 月首选**：JCROB 原生整单（`nav_action + image_action`），平台只做状态轮询和证据回收；
2. **多厂商方向**：VDA5050 的 `order/state/instantActions`；
3. **多机方向**：Open-RMF；
4. **本体侧**：ROS2 Nav2 的 `NavigateToPose/FollowWaypoints` + behavior tree 恢复。

当前代码只是借了 VDA5050 的字段名，不是 VDA5050。

## 三个最致命的产品问题

1. **卖的与交的不是一个东西**：64 项承诺仅 4 项完成；交付说明写“一期做下发”，代码是 501/403。
2. **只监不检，核心价值不成立**：到点不拍照、不测温、不读气体，AI 只接入不推理；客户用“摄像头 + 人工 + 工单”就能得到大部分价值。
3. **把集成项目当产品卖，关键路径不在自己手里**：真机 11/10 到、12/01 验收；JCROB 写协议未确认、token 未接、暂停/继续厂商不支持；传感器/通知/防爆认证都不由软件团队控制。

### 1.6 干不了 ①：真机巡检闭环 🔴

这是最核心的结论。把“下发 → 导航 → 到达”逐段拆开，每一段都有断点：

| 环节 | 代码事实 | 真机后果 |
|---|---|---|
| 模板下发 | `POST /task-templates/{id}/dispatch` 直接 501（`server/app/api/v1/task_templates.py:195-205`） | 模板不能下发 |
| 执行下发 | `robot.write_enabled` 默认 false，403 `WRITE_LOCKED`（`server/app/services/task_dispatch.py:10-11`、`:38-52`） | 默认不能用；现场授权后才开 |
| 下发订单内容 | 订单只有 `pointId`/`pointName`，**没有 x/y/yaw**（`task_dispatch.py:66-84`） | JCROB 只会收到拍照动作；X30 会导航到 `(0,0,0)` |
| JCROB 真机适配 | `dispatch` 把 `photo/video/thermal` 都映射成同一个 `image_action`，没有 `goto`（`server/app/adapters/jcrob/http_adapter.py:143-167`） | 订单里没有动作类型时默认按 `photo` 处理，不会走导航 |
| 巡航回退 | `_goto` 找不到 `goto` 就调 `dispatch`，合成参数里**没有 `actionType`**（`cruise.py:126-135`） | JCROB HTTP 把这一步当拍照，巡航不移动 |
| 到达判定 | 只看 `state == "FINISHED"`，不看订单号/位姿（`cruise.py:137-155`） | 旧任务的 FINISHED、空任务列表都可能被当成“到了” |
| 到点动作 | `step.action` 在巡航循环里完全没被使用；结果只写 `point/x/y`（`cruise.py:82-112`） | 到了也不拍照、不测温、不检测 |
| 暂停/继续 | JCROB 明确 `NotSupported`；X30 的 pause=cancel、resume 是 no-op（`http_adapter.py:169-173`、`deeprobotics/adapter.py:141-146`） | 没有真正的暂停/继续 |
| 并发 | 每条 run 一个线程，没有按机器人加锁；`robot_id` 为空默认 1（`cruise.py:41-49`、`task_runs.py:229-235`） | 两条任务可同时抢一台机器人 |
| 鉴权 | `ensure_token()` 只有定义、没有任何调用；`JC_JCROB_TOKEN` 默认空（`http_adapter.py:57-59`） | 真机 HTTP 请求可能不带 token，直接 401 |

**一句话**：**“模板下发”是 501，“执行下发”默认 403，订单没有坐标，“巡航”在 JCROB 上发的是拍照，到了也不做巡检动作。** 这四条任意一条都足以让“真机巡检闭环”不成立。

### 1.7 干不了 ②：到点“检”与巡检证据链 🔴

巡检的价值不是“机器人动起来”，而是“每个点位留下可复核的证据”：可见光照片、热成像、气体/局放/声纹读数、时间、位姿、设备编号、置信度、人工复核结论。

当前代码：
- 巡航到点只写 `{"point": name, "x": x, "y": y}`（`cruise.py:107`），**没有图片、没有传感器读数、没有 AI 结果**。
- JCROB 的 `image_action` 只是向 ROS 话题 `/camera_node/image_raw` 发一个动作名（`http_adapter.py:148-150`），平台**没有取回图片**的调用。
- AI 只有“结果接入”：`POST /ai/results` 接收 base64 图片/置信度，超过阈值建告警（`server/app/api/v1/ai.py:102-154`）；**没有任何推理代码**。当前唯一一条 AI 结果 `has_image:false`；买家评审还记录过 8 字节的假原图。
- 环境传感器只有 1 个气体传感器、7.6 %LEL，来源是 `127.0.0.1:15020` 的本地模拟器；没有标定证书、没有多类型、没有与巡检点位的绑定。

**结论**：即使明天机器人能走到点位，平台也拿不出“这个点位、这个时刻、这台机器人、这张照片/这个读数”的证据链。**“巡检”在产品上仍然是空的。**

### 1.8 干不了 ③：标准视频/存量摄像头/规模录像 🔴

- 接入只有 RTSP 手工添加；没有 GB/T 28181 信令/媒体、ONVIF 发现、NVR/平台级联、PTZ 控制、预置位、视频墙。
- 录像最多 2 路（`recorder.py:34`、`:94-95`）；没有中心存储、没有边缘转存、没有断网续传。
- 没有“视频巡检”联动：告警不能自动调取前 N 秒/后 N 秒、不能自动转到预置位、不能把视频片段附到工单。
- 50 路 × 1 年的容量与 1.9 TB 本地盘之间的矛盾没有解（见容量核对文档）。

**客户现场一句话就能问倒**：“我们已经有海康 NVR 和 200 路摄像头，你能接吗？”当前答案是“不能，只能逐路 RTSP，而且最多录 2 路”。

### 1.9 干不了 ④：多机调度/离线自治/高可用 🔴

- 没有车队概念：没有任务队列、没有按机器人排队、没有交通管制/互锁、没有充电调度、没有跨机器人交接。
- 没有离线自治：断网后机器人侧是否继续、平台恢复后如何补传，均未实现；只有“事后再 ingest”的接口，不是断网续传。
- 没有高可用：单 uvicorn worker（`deploy/entrypoint.sh:16`），进程内线程做轮询/巡航/录像/网关；重启即丢线程状态。
- 没有多实例/多租户/灰度/限流（nginx 有 20r/s，但应用层没有全局限流）。
- 遥测默认只保留 7 天（`server/app/api/v1/telemetry.py:31`），30 天报表实际只有约 1 天数据（实测 `data_coverage.telemetry_days=1.0`）。

### 1.10 干不了 ⑤：安全合规/防爆/等保/数据治理 🔴

- **防爆**是机器人本体的认证（IECEx/GB 3836），软件平台不持有、也不应宣称持有；当前没有把本体证书、铭牌、区域划分、温度组别纳入系统。
- **功能安全**没有：没有安全 PLC/急停回路/安全继电器集成；平台的“停止”不是安全停止。`command_gateway.precheck()` 只是纯函数（`server/app/services/command_gateway.py:13-27`），**下发和巡航都没有调用它**；电量 <20%、急停按下、已有运动命令这些前置条件，在真实写路径上不生效。
- **等保 2.0 三级**没有：没有测评报告、没有堡垒机/日志外送/双因子强制/入侵检测/数据分类分级/灾备；默认 `admin/admin123`、`/docs` 默认开（`config.py:36,40`）、内网 HTTP 默认（`deploy/nginx/default.conf` 监听 80）。
- **审计链**当前 `verify=false`；没有外部锚定/WORM/时间戳服务。

## 二、和成熟系统比：差在哪，哪些不是差距

### 2.1 先对齐比较对象

拿“一个 3 周后要验收的单机器人项目”去对标“海康 iVMS/综合安防”“申昊/亿嘉和巡检平台”“Open-RMF/VDA5050/ROS2”，本身要分层：

| 层 | 代表 | 它解决什么 | 本平台对应物 |
|---|---|---|---|
| 视频/安防集成层 | 海康 iVMS/Infovision、大华 DSS | 摄像头、NVR、GB28181、PTZ、视频墙、报警联动 | RTSP + go2rtc + 2 路录像 |
| 机器人本体+巡检应用 | 申昊、亿嘉和、国网系厂商 | 本体、SLAM、自主充电、云台、热成像、局放、气体、巡检平台、项目交付 | JCROB/X30 适配器 + 监控/告警/工单 |
| 车队/任务标准 | Open-RMF、VDA5050 | 多机任务分配、交通管制、订单/状态互操作 | 平台侧点对点线程 |

**本平台既不是视频平台，也不是机器人本体厂商，也不是车队标准实现。** 它更像“机器人上位机/巡检业务外壳”。这不是贬义——如果定位准确，这个生态位是存在的；但如果对外叫“平台”，就会被拿去和上面四类逐项对比，然后每一项都输。

### 2.3 “行业标配但我们没有”的 10 项

按“验收/投标最容易被问”排序：

1. **GB/T 28181 / ONVIF / NVR 接入**：存量摄像头接不进来，视频只能当“单路 RTSP 播放器”。
2. **PTZ/预置位/视频联动**：告警不能自动转向、不能抓取告警前后片段，视频和业务是两张皮。
3. **标准订单/状态协议**：VDA5050 的 `order/instantActions/state/connection`，或厂商原生任务单；当前只是“VDA5050 形状的 JSON”。
4. **车队任务队列/交通管制/充电调度**：两台机器人会抢路、抢任务、抢充电桩。
5. **本体自主导航/恢复行为**：重定位、避障脱困、路径重规划、到点精度、失败回退；平台全依赖厂商，且没有验收手段。
6. **到点动作编排**：拍照/测温/读表/气体/声纹/局放，一个点位多个动作、动作结果回传；当前只有“导航到点”。
7. **AI 推理/算法仓/样本闭环**：现在是“别人算完推给我”，没有模型、没有训练、没有误报闭环。
8. **3D/点云/地图版本管理**：2D 图片+手打点，换地图/换楼层/地图偏移没有版本概念。
9. **功能安全/防爆系统集成**：安全急停、安全 PLC、区域联锁、防爆认证台账；当前只有“软件停止”。
10. **等保/灾备/断网续传/中心存储**：单机 SQLite、7 天遥测、2 路录像、无异地备份。

### 2.4 “我们有但行业也一般”的 7 项

这些是加分项，但不能当护城河：

1. **告警→工单→手机闭环**：很多安防/巡检平台都有，且做得更重（流程引擎、SLA、多级审批）。本平台胜在轻、清楚、真能用。
2. **人工巡检 + 扫码 + 拍照**：行业标配，技术门槛低；反而证明“没有机器人也能巡检”。
3. **通知重试 + HMAC 签名**：细节好，但客户不会为这个签单；且当前真实通道未打通。
4. **RBAC/审计/TOTP/CSRF**：等保项目的基础项，不是差异化；审计链还有硬伤。
5. **地图点位越界校验/Excel 导入导出**：体验好，但不解决“到点做什么”。
6. **私有化/轻量部署**：对中小园区是优点；对大型客户，单进程反而是减分项。
7. **UI 清晰、空状态诚实**：在同类里少见，值得保留；但 UI 不能替代巡检能力。

### 2.5 市场位置建议

三条路，选一条，不要混着说：

**A. 全栈巡检平台（本体+平台+AI+视频+车队）**
- 12 月不可能；需要 12–24 个月、硬件团队、算法团队、防爆认证、项目交付体系。
- 不要用当前版本去投标这类标；会被海康/申昊/亿嘉和按项碾压。

**B. 机器人无关的“巡检业务 supervisory layer”**
- 卖点：接不同厂商机器人，统一告警/工单/报表/视频/权限，私有化，便宜。
- 前提：至少要支持一种标准（VDA5050/Open-RMF）或 3 家以上厂商适配器；要有真实到点动作与证据链；否则只是“某厂商的上位机”。
- 这是 2027 年的方向，不是 12 月验收的方向。

**C. JCROB 配套上位机（最现实）**
- 卖点：单机、单站、监控/告警/工单/报表/手机端，随机器人一起交付。
- 命名不要叫“平台”，叫“防爆巡检机器人监控与作业管理系统（单机版）”。
- 报价按“软件配套”而不是“平台 license”；验收范围写清楚“不含多机调度/GB28181/AI 推理/3D”。
- **12 月验收应该走 C**；B 作为后续演进；A 不讲。

## 三、巡航/导航模型成立吗？

### 3.1 代码实际怎么跑

`POST /api/v1/task-runs/{id}/cruise` →
`CruiseRunner.start()` 起一个 daemon 线程（`server/app/services/cruise.py:41-49`）→
对每个 step：

1. 取点位坐标（没有坐标直接 failed）；
2. `_goto(adapter, x, y, yaw)`：优先 `adapter.goto`，否则 `adapter.dispatch`，合成一个只有 x/y/yaw 的 action（`cruise.py:126-135`）；
3. `_wait_arrival()`：每 3 秒 `adapter.get_order()`，只有 `FINISHED` 算到达，`FAILED` 算失败，240 秒超时（`cruise.py:137-155`）；
4. 标记 step `ok`，结果只写点位名/x/y（`cruise.py:107`）；
5. 下一个点；全部结束写 run `done/failed/cancelled`。

### 3.2 五个硬伤（按严重度）

**硬伤 1：在 JCROB 真机上，巡航不会移动。**
`_goto` 的回退 action 没有 `actionType`（`cruise.py:129-131`），JCROB 的 `dispatch` 用 `a.get("actionType", "photo")` 取默认值（`http_adapter.py:148`），于是这一步变成 `image_action`，x/y 被丢掉。**模拟器有 `goto()`，所以演示能动；真机 HTTP 没有 `goto()`，所以真机不动。** 这是“演示通过、现场翻车”的典型结构。

**硬伤 2：执行下发不是导航。**
`task_dispatch._order_payload()` 的 action 只有 `pointId/pointName`（`task_dispatch.py:66-84`），没有坐标。JCROB 收到后只会按 `photo` 处理；X30 取 `actions[0]`，x/y 缺省为 0，直接导航到 `(0,0,0)`（`deeprobotics/adapter.py:124-135`）。**“下发成功”在真机上等于“拍一张照”或“去原点”。**

**硬伤 3：到达判定不是“到达”。**
- 只看 `FINISHED`，不看 `orderId`、不看位姿、不看距离（`cruise.py:149-153`）。
- JCROB `get_order()` 在任务列表为空时直接返回 `FINISHED`（`http_adapter.py:182-190`）——刚下发、列表还没注册时，平台可能立刻认为“到了”，然后发下一个点。
- X30 的 `Status` 为空时映射成 `UNKNOWN`，巡航只能等到 240 秒超时（`deeprobotics/adapter.py:151-155`）。
- 没有“到位误差 < 0.5m”的验收口径；地图坐标和机器人坐标是否同一坐标系、原点/朝向如何变换，代码里没有处理；`robot_map_name` 在执行路径里没被使用，X30 的 `MapID` 硬编码为 1（`deeprobotics/protocol.py:155-162`）。

**硬伤 4：到点没有“检”。**
`step.action` 在循环里完全没读（`cruise.py:82-112`）；`result_json` 只有点位名和坐标（`:107`）。即使机器人真的到了，平台也不会拍照、不会测温、不会读气体、不会把证据挂到 step 上。**“巡航”只是“移动”，不是“巡检”。**

**硬伤 5：并发/暂停/取消都不安全。**
- 每条 run 一个线程，没有按 `robot_id` 的互斥/队列；`robot_id` 为空默认 1（`task_runs.py:229-235`）。两条任务可以同时向一台机器人发目标。
- 巡航循环不检查 run 是否被暂停；`/pause` 对 JCROB 直接 `NotSupported`，对 X30 是 cancel；即使 pause 成功，线程到了下一个点仍会继续。
- 前端“取消”调用的是通用 `/cancel`（`web/src/pages/TaskRuns.vue:146-155`），它只调 `task_dispatch.cancel()`，**没有设置巡航线程的 stop 事件**；线程会继续循环，`get_order()` 在取消后可能返回空列表 → `FINISHED` → 标记当前点成功 → **继续下发下一个点**。真正能停线程的 `/cruise/cancel` 在 UI 里没被使用。
- 看门狗 `WATCHDOG_STUCK_S=30`（`task_dispatch.py:154`），但巡航只在每个点完成后更新 `last_progress_at`（`cruise.py:108-112`）。**任何超过 30 秒的行走段都会触发“任务卡住”严重告警**——真机上会变成告警风暴。

### 3.3 模型判断

**“平台逐点下发、等到达、再下一点”作为一种 fallback 是成立的**：
- 当厂商只暴露“去 x,y”这种单目标 API，平台侧做闭环、记录每点状态，是合理的；
- 对单机、单站、低速、点位少的场景，够用；
- 它把“任务编排”留在平台，换机器人时业务层不用重写。

**但作为产品架构，它不成立**，原因不是“点对点”本身，而是：
1. **它把“订单”降级成了 RPC**：没有 orderId 绑定、没有 orderUpdateId、没有节点/边/动作图、没有幂等/重试/状态机；网络抖动、重复下发、旧状态都会造成错乱。
2. **它假设“到达 = 完成”**：巡检的完成不是到达，是“动作执行 + 证据回传”。当前模型没有“动作”这一等公民。
3. **它把机器人当成“可轮询的远程函数”**：3 秒轮询、240 秒超时、30 秒看门狗，都是平台侧拍脑袋的时序，不是机器人本体状态机的一部分。
4. **它没有并发语义**：没有“一台机器人同时只能有一个订单”的约束，也没有队列/抢占/取消传播。
5. **它绕过了适配器里已经按协议组装好的更优接口**：`http_adapter.dispatch()` 会把订单转成 `sub_tasks: nav_action + image_action + sleep_action`（`http_adapter.py:143-167`），**一个订单就能“走到点 + 拍照”**（字段仍需厂商确认）；平台却把导航和动作拆开，还没把坐标放进订单。

### 3.4 更标准的做法（按 12 月可行性排序）

**方案 1：厂商原生整单（12 月首选）**
- 用 JCROB `/task` 下发一个订单：`nav_action(x,y,theta)` + `image_action` + `sleep_action`，一个点位一个订单或一条任务多个 sub_task。
- 平台只做：订单 ID、状态轮询、超时/失败、证据回收、人工确认。
- 优点：最少代码、最贴近厂商能力、现场最容易调；缺点：绑定 JCROB，换厂商要重写。

**方案 2：VDA5050（多厂商/车队方向）**
- Master control 通过 MQTT 下发 `order`：`nodes[]`（nodeId/sequenceId/released/nodePosition/actions[]）+ `edges[]`；`instantActions` 做暂停/取消；订阅 `state`（1 Hz）拿 `nodeStates/edgeStates/actionStates/agvPosition/errors`；`connection` 做在线判定。
- 优点：标准、可换厂商、天然支持动作和状态；缺点：JCROB 不一定支持，12 月前落地风险高。
- 注意：当前 `task_dispatch.py` 只是借了 `orderId/orderUpdateId/actions` 的字段名，**不是 VDA5050**（没有 nodes/edges、没有 MQTT、没有 state/connection）。

**方案 3：Open-RMF（多机/楼宇集成）**
- 每个厂商写 fleet adapter；RMF 做任务分配、交通协商、门/电梯/充电桩集成；适合多机器人、多楼层、跨品牌。
- 12 月不现实；作为 2027 年“机器人无关平台”的技术底座。

**方案 4：ROS2 Nav2（本体侧）**
- 本体用 `NavigateToPose` / `FollowWaypoints` action，platform 只发目标；Nav2 的 behavior tree 做恢复（重规划、清代价地图、旋转、后退），SLAM Toolbox/AMCL 做建图/定位。
- 这是“机器人自己会走”的标准做法；平台不该重复实现导航，但应验收“到点精度/恢复行为/失败原因”。

**结论**：12 月不要继续打磨平台侧巡航线程。**优先把 JCROB 原生整单跑通**；平台巡航只保留为“厂商只支持单点”的 fallback，并修掉硬伤 1/3/5。多机/标准协议放到二期。

### 3.5 12 月前的最小修正（如果必须保留平台巡航）

1. `_goto` 的回退 action 加 `actionType: "nav"`，或在 `http_adapter.dispatch` 里对“有 x/y 无 actionType”的 action 显式按 `nav_action` 处理。
2. 到达判定加三件事：`orderId` 绑定、位姿距离阈值（如 <0.5m）、`FINISHED` 后二次确认；空任务列表不得直接 `FINISHED`。
3. 巡航循环每步执行 `step.action`（photo/thermal/gas），把图片/读数写进 `result_json` 或独立的 evidence 表。
4. 按 `robot_id` 加互斥/队列；`robot_id` 必填；取消必须调 `/cruise/cancel` 或设置 stop 事件；pause 要在循环里检查。
5. 看门狗阈值改为“最长单段行走时间 + 余量”，或只在“长时间无任何状态变化”时告警。
6. 坐标系：平台地图点 → 机器人地图点的变换必须显式配置/校验；`robot_map_name` 参与执行；X30 的 `MapID` 不能硬编码 1。

## 四、三个最致命的产品问题

### 4.1 致命问题一：卖的与交的不是一个东西

**证据链**：
- PPT/投标承诺 64 项，自查 ✅4（6.3%）、🟡23（35.9%）、❌32（50.0%）、⛔5（7.8%）（`docs/PPT承诺对标-投标自查-20261022.md`）。
- `docs/交付说明-一期范围.md` 写“一期包含任务下发/暂停/继续/停止”，代码里模板下发是 501、执行下发默认 403。
- 对外叫“防爆机器人巡检平台”，实际是单机上位机；对外暗示“多机器人/3D/AI/GB28181/等保”，实际都没有。
- 买家评审的结论是“不买当前版本”；按钮验收发现菜单缺失、分页/站点切换/热成像按钮等 P1/P2 问题（虽然后续修了 9 项）。

**为什么致命**：这不是“功能少”，是**承诺与交付的基线不一致**。验收时客户不会按“你做了什么”打分，而是按“你说过什么”逐条核对。64 项里 32 项 ❌，任何一条被拿到会上，都会把“平台”叙事击穿。

**怎么破**：不要试图在 6 周内把 32 项补完。**主动缩范围、改口径、把验收标准写成“本期范围”**，并把未做的明确列为“二期/不含”。诚实缩范围比硬撑全量更可能通过验收。

### 4.2 致命问题二：只监不检，核心价值不成立

**证据链**：
- 巡航到点不执行动作（`cruise.py:82-112`）；
- 订单没有坐标（`task_dispatch.py:66-84`）；
- JCROB 真机巡航不移动（`cruise.py:126-135` + `http_adapter.py:148`）；
- AI 只接入不推理（`ai.py:102-154`）；唯一结果无图；
- 传感器 1 个、模拟器、无标定；
- 报表的数据覆盖只有 1 天（实测 `telemetry_days=1.0`）。

**为什么致命**：客户买“巡检机器人”是为了**替代/减少人工巡检**，不是为了多一个看板。如果平台不能证明“每个点位、每个班次、每个异常都有机器采集的证据”，那它的价值就退化成“告警工单 + 视频查看”，客户完全可以不买机器人、只买摄像头和工单系统。**“只监不检”是产品定位问题，不是功能问题。**

**怎么破**：12 月只做一个“真闭环样板”：
- 1 台真机、3 个真实点位、每个点位 1 张可见光照片（有热成像就加 1 张）；
- 每张照片带时间、点位、机器人、位姿、任务 ID；
- 20 次连续运行，成功 ≥18 次；
- 报表能按点位/班次追溯这些照片。
这比“64 项里再补 10 项 UI”有价值得多。

### 4.3 致命问题三：把集成项目当产品卖，关键路径不在自己手里

**证据链**：
- 真机 11/10 才到，验收 12/01（`docs/真机联调预案-20261022.md`）；只有约 3 周。
- JCROB 写协议“字段未确认”（`http_adapter.py:1-5`、`:142`）；`ensure_token` 没接；没有 WebSocket；暂停/继续厂商不支持。
- X30 是测试设备，默认停用；地图列表为空、MapID 硬编码；`/devices/{id}/status-probe` 有 `AttributeError`。
- 传感器、通知通道、防爆认证、等保测评都不在软件团队控制内。
- 单进程 + 进程内线程 + SQLite 默认：不是可交付的产品架构，是 POC 架构。

**为什么致命**：产品的核心体验（机器人能不能动、到点能不能拍、告警能不能外发）全部依赖第三方到场、协议确认、现场授权、硬件到货。任何一环延迟，软件团队无法单独兜底；而销售/投标已经按“平台”承诺出去了。**这不是研发风险，是交付模型风险。**

**怎么破**：
- 把项目定义成“机器人配套软件交付”，不是“平台产品交付”；
- 关键路径上的第三方事项（协议、token、任务单格式、传感器、通道）写成**客户/厂商责任清单**，带日期和签字；
- 软件侧只承诺“在给定接口/硬件到位后 N 天完成联调”，不承诺“无条件 12/01 全功能”；
- 保留一个“降级验收”方案：若真机/协议延迟，按“监控/告警/工单/报表 + 模拟器演示”验收，巡检闭环转二期。

## 五、如果 12 月验收：必须补 / 可以砍 / 必须改口径

> 前提：真机 11/10 到场、协议可联调、至少 1 种真实传感器和 1 个真实通知通道到位。若前提不成立，直接走“降级验收/延期”，不要赌。

### 5.1 必须补（P0，按优先级）

| # | 必须补 | 最小验收标准 | 预估 |
|---|---|---|---|
| P0-1 | **真机单点闭环** | 平台下发 → 机器人走到点位 → 到点拍照 → 图片回传 → 平台可见；3 个点位各 1 次 | 3–5 人日（依赖厂商） |
| P0-2 | **多点连续 + 证据链** | 3 点 × 20 次连续运行，≥18 次成功；每次每个点有图/时间/位姿/任务 ID；失败有原因 | 3–5 人日 |
| P0-3 | **真实环境传感器** | ≥3 种（可燃气/烟感/温湿度等），至少 1 台真实 Modbus/MQTT；阈值可配；超限 <10s 告警；24h 稳定 | 2–4 人日（依赖硬件） |
| P0-4 | **真实通知通道** | 1 个企业微信/钉钉/Webhook 真实可达；测试按钮成功；告警触发→收到；失败重试/升级可见 | 0.5–1 人日 |
| P0-5 | **数据/审计/保留** | 清 demo 数据；生产库 `audit verify=ok`；遥测/录像保留≥合同要求；备份恢复演练 1 次；改默认口令、prod 关 `/docs` | 2–3 人日 |
| P0-6 | **执行正确性** | 每机器人互斥/队列；订单号绑定到达；位姿阈值；pause/cancel 真生效；看门狗不误报；重启不出现“假 running” | 2–3 人日 |
| P0-7 | **验收证据包** | 20 次运行记录、3 点视频、传感器曲线、告警→工单→通知→手机闭环录屏、审计 verify、数据覆盖说明 | 1–2 人日 |

**合计约 12–23 人日**。11/10–12/01 约 15 个工作日；两人并行有希望，但**没有 buffer**。P0-1/P0-2 必须优先，P0-3/P0-4 可并行，P0-5/P0-7 最后做。

**P0-1 的具体技术选择（建议）**：
- 不要再走“平台巡航线程”作为主路径；用 JCROB 原生 `/task` 整单：`nav_action` + `image_action`，平台只轮询订单状态、回收图片。
- 如果厂商只能单点：保留巡航，但先修 `actionType`、到达判定、按机器人锁三件事。
- 无论哪条路，**订单里必须有坐标和动作**；没有这两样，不叫“巡检下发”。

### 5.2 可以砍（写进“本期不含”，不要默默消失）

| 可砍项 | 理由 | 怎么处理 |
|---|---|---|
| 3D/数字孪生/点云 | 与本期验收无关，工作量大 | 明确“二期”，UI 不放假 3D |
| 六类 AI 算法/训练舱/算法仓 | 没有推理代码、没有样本、没有算力 | 只保留 `POST /ai/results` 接入；算法由第三方算法盒提供 |
| GB28181/ONVIF/PTZ/NVR/视频墙 | 存量视频接入是独立工程 | 本期只承诺 RTSP；国标网关二期 |
| OPC UA/DCS/EHS/园区平台对接 | 每个现场不一样，项目制 | 单独立项报价 |
| 多机器人车队调度/交通管制/充电调度 | 单机都没闭环，多机是伪需求 | 从投标话术删除 |
| 原生 App/小程序 | 手机 Web 已够用 | 不做 |
| 区块链/存证 | 与巡检价值无关 | 从 PPT 删除 |
| 50 路 × 7×24 录像 | 存储/带宽/架构都不成立 | 明确“事件录像，最多 2 路”；容量另算 |
| 任务日历/绩效排名/预测性维护 | 没有数据基础，做出来也是空壳 | 隐藏或标“未接入” |
| 平台侧巡航编排（若厂商整单跑通） | 重复造轮子、风险高 | 降级为 fallback，不对外承诺 |
| 多租户/SaaS | 本期私有化单站 | 不做 |

**砍的原则**：每砍一项，必须在验收范围/合同/PPT 里同步删掉；**不能“代码没有、PPT 还留着”**。当前最大的风险不是功能少，是承诺多。

## 附录 C：验收现场必问的 12 个问题（按当前状态回答）

1. **“现在能真机巡检吗？”**
   不能。模板下发 501；执行下发默认 403；订单无坐标；JCROB 巡航发的是拍照；到点不执行动作。

2. **“演示里机器人不是会动吗？”**
   动的是 `MockJcrobAdapter`，它有 `goto()`；真机 HTTP 没有 `goto()`，回退路径会把导航变成拍照。

3. **“任务下发为什么是 501？”**
   代码明确“真机联调 + 现场授权后开放”（`task_templates.py:195-205`）。这不是 bug，是刻意的闸门；但对外不能说“已实现”。

4. **“到点拍的照片在哪？”**
   没有。巡航只写点位名/x/y；`step.action` 未使用；JCROB `image_action` 没有图片回传。

5. **“AI 识别准确率多少？”**
   没有推理，只有 `POST /ai/results` 接入；唯一结果无图。不能承诺 98%。

6. **“能接我们现有的海康摄像头吗？”**
   只能逐路 RTSP；不支持 GB28181/ONVIF/PTZ/NVR；最多 2 路录像。

7. **“50 路存一年要多少盘？”**
   192–385 TB；本机 1.9 TB。当前架构不成立，需中心存储/边缘转存另算。

8. **“两台机器人能协同吗？”**
   不能。无队列/锁/交通管制；两条任务可抢同一台；`robot_id` 为空默认 1。

9. **“断网了怎么办？”**
   没有断网续传；只有事后 ingest。机器人侧是否继续、恢复后如何补传，未实现。

10. **“等保三级过了吗？防爆认证呢？”**
    没有等保测评；防爆是机器人本体认证，平台不持有，也不应宣称。

11. **“审计能防篡改吗？”**
    当前 `verify=false, broken_at=1`；哈希链代码在，但生产库需 rechain 并通过校验。

12. **“12/01 能验收什么？”**
    按本期范围：监控/告警/工单/手机端/视频（1 路）/报表/权限 + 真机单点闭环（若 G2 通过）。多机/GB28181/AI 推理/3D/等保不在本期。

## 最后一句

这套系统最可惜的地方，不是它“什么都没有”——它有的东西（告警工单、手机闭环、权限审计、UI 克制）在同规模项目里算扎实。**可惜的是它把“巡检”最值钱的那一段（真机到点、执行动作、留下证据）留在了 PPT 里，把大量精力花在了“看起来像平台”的外围。** 12 月前最值得做的，不是再加功能，而是把“一台真机、一个点位、一张照片、一条可追溯证据”做实；然后诚实地把其余部分标成二期。
