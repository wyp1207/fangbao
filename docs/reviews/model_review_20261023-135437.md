## 1. 第一次演示必翻车的三个点（具体到操作步骤）

### 翻车点①：真机一走，"实时"就露馅（链路延迟 + 命令空转）
现场操作：
1. 甲方要求：让狗从 A 点走到 B 点，首页"实时消息—巡检 tab"和轨迹面板同步看。
2. 你们通过平台下发（或现场用遥控器走），狗已经开始动了。
3. 实际会发生：
   - **TCP 30000 状态刷新不是事件驱动，是你们自己轮询/拉取再转发到前端**，前端面板位置、姿态、速度会有几百毫秒到数秒卡顿，狗都转弯了地图还停在原地；
   - 网络一抖（化工厂区 WiFi/专网很常见），你们**没有重连补偿、没有序列号乱序处理、没有"最后更新时间"置灰**，前端还显示 5 秒前的状态当"实时"；
   - 最致命：让平台"停"或"起立"（UDP 43893），**UDP 根本没有送达保证**，现场 AP 丢一个包狗没反应，讲师再点一次——要么没反应，要么不知道哪包后到导致状态错乱。你们没有命令 ACK、没有超时、没有幂等令牌。
4. 甲方一句："**我怎么知道屏幕上这个位置是不是狗现在的位置？指令它收到没有？**"——当场死机。

应验证（现在就该测）：断网 5 秒恢复后行为；拔网线时前端是否显示"设备离线"；UDP 指令丢 1 次/重复 2 次/乱序各发生什么；从点按钮到狗动作的端到端 P99 延迟。

### 翻车点②："自动巡航"是 PPT 功能——真机没跑过 + 拍照没接
现场操作：
1. 甲方随机指一块表/一个阀门："加个点位，现在巡一圈给我看，到这个点把表拍清楚。"
2. 你们走：模板→执行记录→巡航，平台**逐点下发 + 轮询 1007/HTTP 状态判断到点**。
3. 必翻：
   - "真机巡航没跑过、到点拍照接口没对接"是你们自己招的。**到点不拍照 = 巡检的核心交付物（带点位、带时间、带读数的证据链）不存在**，这不是小 bug，是主流程没闭环；
   - "轮询状态判断到点"在定位有漂移时（化工厂 GPS/北斗遮挡、激光定位重定位），会出现**狗已经走过点位、平台还没判定"到达"，或者反复横跳判定到点**。没有到点容差、没有最小驻留、没有失败重试策略；
   - 逐点下发意味着平台是"大脑"，**平台一卡，狗就站在路中间**，没有 onboard 任务缓存、没有断点续巡、没有"平台失联时机器人自主完成/安全悬停"的降级；
   - 现场大概率要靠工程师拿遥控器兜底，甲方一看："**合着自主巡航是后面有人遥控？**"

应验证：3 点以上真机连续巡航成功率（要敢说 50 次成功几次）、定位漂移 0.5–2m 时到点判定、平台 kill 掉之后狗的行为、拍照照片里是否含点位/时间/GNSS 水印。

### 翻车点③：告警在现场是"狼来了"，阈值根本没标定
现场操作：
1. 甲方凑近一个真实气体/噪声探头，或拿热源对热成像："你报一个看看，准不准？"
2. 你们阈值来自"外设规则优先"，但：
   - 外设本身是模拟器或真机未标定，**量纲、采样率、零点漂移、温度补偿一概没有**。气体 ppm 和 mg/m³、噪声 A 计权、粉尘 PM 通道对不对都未必清楚；
   - 去重 + 5 分钟升级 + 自动恢复，听着完整，但现场**传感器抖动/瞬时尖峰**会让告警疯狂产生又恢复，或者真超标的慢漂移被"去重"压掉。你们没有滞回（hysteresis）、没有持续 N 秒才触发、没有和工况（检修/标定/旁接状态）联动抑制；
3. 更尴尬的：告警→工单双向可查，但**现场触发一条真实告警，手机 H5 接单这一步依赖厂区外网/互联网**（企业微信、钉钉），化工生产区往往是专网物理隔离，推送根本到不了手机。讲师连自己手机热点演示，甲方安保脸就黑了。

应验证：每种外设真机读数和标准表偏差；同一尖峰下告警条数；**专网/断外网环境下通知链路**（这一条大概率直接不可用）。

## 2. "看起来有、实际不能用"的功能

- **写开关默认关**：这等于承认"我能控制设备，但我不敢开"。甲方验收看的就是闭环控制。默认关本身不是问题（安全设计），问题是**开关背后没有任何安全护栏**：没有电子围栏、没有速度/倾角/电量/失联保护、没有控制权限二次确认、没有急停优先级高于一切。开关一打开就是裸奔，所以你们只能关着演。这是"控制能力"伪装，不是安全设计。
- **JCROB 模拟器**：HTTP 3546 全是模拟，意味着多机型接入、协议适配这一层**只在文档里存在**。模拟器返回的是你们自己定义的"理想世界"，真机的心跳、错误码、断连、非预期状态一个没碰。"支持两类机器人"实际是"支持一类半，那半类是我自己"。
- **能力派生（peripheral → capability）**：这是典型的**程序员自嗨建模**。现场设备的能力不是静态表里派生出来的：热成像有没有测温、云台支不支持预置位、气体是哪种气体，都是**型号 + 固件 + 当前配置**决定的，会变、会缺、会故障。你们把"装了什么外设"等同于"具备什么能力"，一个摄像头离线/故障，面板还照常渲染 live 入口，点进去转圈。应验证：拔掉一个外设后，能力是否实时撤销、面板是否降级。
- **录像最多 2 路**：化工/电力一个站所动辄十几个点位、多机器人多载荷。go2rtc + ffmpeg 单机 2 路，**这是家用 NVR 水平**。没有码流协商（弱网降码率）、没有 GB28181/ONVIF 对接（公安/集控平台基本强制 GB28181）、录像检索靠文件、没有抽帧/AI 复核。"视频能力"实际是"能录两段文件"。应验证：第 3 路会怎样（崩？排队？静默丢？）、断流恢复、录像时间戳和告警能否精确关联。
- **单机 Docker Compose**：这是开发环境拓扑，不是生产部署。MySQL、go2rtc、ffmpeg、ffmpeg 录制 IO、应用、推流全挤一台：
  - **没有高可用**，宿主机一重启巡检就停；
  - **没有历史数据分层**（实时库/时序库 vs 关系库），状态高频写 MySQL，三个月后查询和写入互相拖死；
  - 备份脚本≠灾备，没演练过恢复的备份等于没有；
  - 化工/电力等保/网络分区要求 DMZ、生产网、管理网隔离，**一台机器一个 compose 连网闸/防火墙策略都没法画**。
- **审计哈希链**：单机 + 库就在同台机器上，DBA/root 拿到机器，哈希链连库一起改，"防篡改"是纸面的。没有上链/异地/硬件（HSM）或至少异机签名，这就是个面试题答案。
- **报表（覆盖度/闭环率/PDF）**：底层数据是模拟器和未闭环的巡航产生的，**报表越精美越危险**——等于把不可信数据做成 KPI 给领导看。垃圾进、精装垃圾出。
- **三权分立/7 角色/TOTP**：功能列表好看，但现场真正要的是**等保 2.0 三级**（或国网/南网硬件证书、堡垒机、4A 对接、操作双人复核），TOTP 和登录锁定不等于合规，大概率过不了测评。

一句话概括这一类：**你们把"能配置/能演示"当成了"能运行"，把"表结构里有"当成了"系统具备"。**

## 3. 对比海康/申昊/亿嘉和/ThingsBoard/Open-RMF，最致命的架构缺陷

最致命的一条，单独拎出来：

> **缺少一个独立的、设备无关的"机器人边缘网关 + 实时控制/调度内核"。设备协议、实时状态、任务执行、安全急停全部寄生在单机 Web 后端里，平台既是业务系统又是控制器。**

具体对比，差距是分层的：

- **vs 海康（威视）/大华一类**：人家是**视频物联中台**，GB28181/GA1400 视图库、设备级联、流媒体集群、AI 算法仓是底座。你们的 go2rtc+2 路 ffmpeg 在它面前不是竞品，是个插件 demo。在"接得进公安/集控平台、存得下海量视频、看得清"这件事上存在代差。
- **vs 申昊 / 亿嘉和**：这两家的核心资产是**机器人本体 + 现场工艺 Know-how + 边缘自主导航**，巡航任务在机器人端/边缘站执行，平台负责调度和结果，弱网可自治，带自动充电、表计识别、红外双光、局放检测等电力专用载荷算法。你们"平台逐点下发 + 轮询判到点 + 平台挂了狗停路中间"，等于把最不该集中的实时控制强行中心化，**架构上就不适合任何网络不稳定的现场**。
- **vs ThingsBoard**：TB 的价值是**规则引擎 + 设备影子 + 时序存储 + 多租户 + 协议适配栈（MQTT/CoAP/LwM2M/OPC-UA）**，是可水平扩展的 IoT 平台。你们设备直连 TCP/UDP 写死在应用里，没有设备影子（断网后 desired/reported 无法对齐）、没有规则引擎（阈值写在业务代码/规则表里，加一种判据要改代码）、状态点塞进 MySQL，**接入量和灵活性都不是一个量级**。
- **vs Open-RMF**：RMF 解决的是**多厂商、多机器人的 fleet 互操作、交通管制、地图共享、任务协商（fleet adapter）**。你们目前是"一只狗的私有协议 + 一个没接的 HTTP 机器人"，没有任何 fleet 抽象、没有多机任务分配与避碰。叫"平台"，但**平台最核心的'多设备协同'语义是 0**。

三个由该根缺陷派生的硬伤：
1. **协议耦合**：云深处 X30000/UDP、JCROB HTTP 直接散在后端，没有 adapter 抽象层和统一物模型，加一个机型等于改一遍核心。
2. **实时性与可用性错配**：用 Web 技术栈（FastAPI 同步轮询、MySQL）承载需要确定性和安全联锁的控制链路，没有 MQTT/消息总线、没有 edge autonomy、没有 SIL/功能安全概念。
3. **无法规模化**：单机 + 关系库 + 2 路视频，注定是"单站、单狗、演示级"，离"园区/片区多机器人调度"差一个数量级。

## 智谱 GLM（glm-5.2）

作为甲方技术总监兼竞品产品经理，我看了你们的“自述”，只觉得满纸荒唐。你们把一堆未联调的脚手架包装成了“巡检平台”，这种东西拿去骗科研经费可以，想进化工/电力生产网？做梦。

以下是不留情面的拆穿：

### 1. 第一次演示就会翻车的三个点（具体到操作步骤）

**翻车点一：演示“巡航任务”时机器人装死**
*   **操作步骤**：甲方领导在首页点击“执行巡航任务A”，期望机器人开始移动。
*   **翻车现场**：因为你们“真机巡航没跑过”，平台下发指令后，机器人根本不动。前端那个“逐点下发 + 轮询 1007/HTTP 状态”的逻辑会一直转圈圈，直到前端请求超时返回 500。领导问“怎么不动？”，你们连个应急手动控制按钮（PTZ/底盘控制没做）都拿不出来。
*   **验证证据**：去现场拔掉机器人网线，看你们前端轮询是秒级报错卡死，还是默默转圈让领导干瞪眼。

**翻车点二：演示“到点识别设备表计”**
*   **操作步骤**：机器人在某点停下，系统要求进行“到点拍照并识别温度/读数”。
*   **翻车现场**：你们“到点拍照接口没对接”。平台通过云深处 UDP 43893 让机器人起立了，然后呢？采集不到图像，前端实时消息面板一片空白，告警规则（阈值）连触发的前提都不存在。整个巡检业务链直接断链。
*   **验证证据**：查看数据库 `task_execution` 和 `peripheral` 表，看看有没有真实的图片二进制块或 OSS 链接，绝对只有几个干瘪的状态码。

**翻车点三：演示“发现异常自动生成工单并推送到企业微信”**
*   **操作步骤**：手动改一下模拟器的温度阈值，触发告警，期望企业微信收到工单卡片。

### 2. 哪些功能是“看起来有、实际不能用”的？

*   **真机巡航（假的）**：模板->执行记录->巡航，这套模型建得再漂亮也是壳子。没跑过真机，意味着坐标偏移、底盘通信丢包、机械臂干涉这些物理世界的问题你们一个都没解决。这不是软件 Bug，是业务空白。
*   **写开关（假的）**：“写开关默认关”纯属掩饰无能。巡检平台如果不能通过写开关去复位硬压板或启停设备，它只是个“监控大屏”，根本不是“控制平台”。
*   **能力派生（空中楼阁）**：`peripheral` 表里定义了 `ptz.move`，但实际上“PTZ 控制没做”。你们是在用数据库表自己骗自己，前端按能力渲染了 PTZ 摇杆面板，一点就报 404。
*   **录像 2 路（极度过家家的设计）**：`go2rtc + ffmpeg 分段录制（最多 2 路）`。化工现场一个防爆摄像头几十万，几十路视频上来，FastAPI 单机内存瞬间爆满，磁盘 I/O 直接打满。这根本不是商用方案，是大学毕业设计的极限。
*   **单机部署（灾难级架构）**：Docker Compose 单机部署。化工/电力现场要求 99.99% 可用性。单机意味着主板烧了、MySQL 表空间损坏了，整个厂区立马变成瞎子。没有高可用，连入围资格都没有。

### 3. 对比海康/申昊/亿嘉和/ThingsBoard，最致命的架构缺陷是什么？

**最致命的架构缺陷：缺乏分布式边缘网关（Edge Gateway）架构，单体架构强耦合底层设备。**

*   **对比海康/申昊**：成熟方案一定是“云端控制平面 + 边缘执行平面”。你们用 FastAPI 直接去 TCP/UDP 轮询底层机器人硬件，这是工业控制的大忌。现场网络抖动一次，你们的 Python 进程就要处理一堆超时异常，甚至直接 OOM。成熟方案是边缘网关在现场做协议转换和断点续传，云端只管调度。
*   **对比 ThingsBoard**：TB 有强大的规则引擎和多租户/多边缘节点管理。你们把所有逻辑（轮询、告警、任务调度、视频转码）全塞进一个 FastAPI 进程里。只要 ffmpeg 录制吃满 CPU，你们的 1007 状态轮询就会延迟，机器人就会撞墙。
