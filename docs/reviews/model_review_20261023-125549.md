# 实时消息模块：交互与功能设计

## 0. 前置约定（统一字段口径）

所有 tab 共用行模型（前端归一化）：

```
FeedItem {
  id: string              // 后端稳定唯一 id（见各 tab 去重规则）
  ts: number              // 毫秒时间戳，排序主键
  text: string           // 主文本
  level: 'critical'|'warn'|'info'
  badge: '未确认'|'正常'|'异常'
  link: string           // 已含 focus 参数
  deviceId?: string      // 设备过滤依赖；若后端当前不返回 → 标“不确定”，需补
  deviceName?: string
  extra?: Record<string, any>  // tab 专属字段
}
```

关键不确定项：**当前接口未声明 `deviceId/deviceName`**。按设备过滤必须由后端在 item 上返回设备标识（并支持 `?deviceId=`），前端无法从 `text/link` 可靠解析。下文按“后端会补 `deviceId/deviceName`”设计；若不补，第 5 条只能降级为全局流。

## 1. 三个 Tab 的准确定义

### 1.1 巡检消息（patrol）= 巡检任务的**执行实例结果**
- **数据源**：巡检任务执行记录（task run / 巡检结果表），不是任务定义本身。一条 = 一次任务对某个对象的一次执行结果。
- **字段映射**：
  - `id` = `runId`（去重主键 = `runId`；若一次 run 拆多条设备结果，则 `runId + deviceId`，**此规则不确定，需后端确认粒度**）
  - `ts` = 执行完成时间（无完成时间用开始时间，需后端明确，建议完成时间）
  - `text` = `任务名 + 对象/设备 + 结果摘要`，例：`夜温巡检 · 1号大棚 · 温度 34.2℃ 超上限`
  - `level`：结果异常→warn/critical（按是否越限），正常→info
  - `badge`：`正常` / `异常`（巡检一般无“未确认”；若后端给未确认，说明是异常待处置）
  - `link` = `/task-runs?focus=<runId>`
  - `extra`：`taskName, deviceId/deviceName, metric, value, threshold, duration?`
- **排序**：`ts DESC`。同 run 多设备时是否折叠：**默认不折叠**（设备过滤需要），但前端可对同 `runId` 连续行做轻量合并显示（可选，非必须）。
- **去重**：以 `runId(+deviceId)` 去重；同一 run 状态更新（running→done）用同 id **就地更新**，不插新行。

### 1.2 告警消息（alarm）= 设备/指标**越限或状态异常事件**
- **数据源**：告警事件表，一条 = 一次告警（含 active/ack/recovered 生命周期）。
- **字段映射**：
  - `id` = `alarmId`（去重主键）
  - `ts` = 告警**触发时间**（首报）。恢复/确认事件是否各产生一条：**建议同 alarmId 就地更新 badge/text，不新增行**（需后端确认是否单独事件流）
  - `text` = `设备 + 测点 + 当前值/阈值 + 持续`，例：`2号冷库 · 压缩机电流 18.2A > 15A（持续 6 分钟）`
  - `level`：critical/warn（由告警等级），info 仅用于“恢复”提示（若分开）
  - `badge`：`未确认`（active 未 ack）/`异常`（已确认未恢复）/`正常`（已恢复）。**三态映射需后端给 status 字段，badge 枚举可能不够，建议加 status：active/acked/recovered —— 不确定现有 badge 是否够用**
  - `link` = `/alarms?focus=<alarmId>`
  - `extra`：`deviceId/deviceName, point, value, threshold, status, ackedBy?, recoveredTs?`
- **排序**：`ts DESC`；可选次级排序未确认优先（但会破坏时间线，**默认纯时间序**，未确认用样式强调而非插队）。
- **去重**：以 `alarmId` 去重；重复触发（同一未恢复告警再上报）做计数/防抖，不新增行，可在 text 后加 `×n`。

### 1.3 控制消息（control）= **谁、何时、对哪个设备、下发了什么指令、结果如何**
- **数据源**：操作日志 / 指令下发记录（oplog），一条 = 一次控制指令（含执行结果）。
- **字段映射**：
  - `id` = `opId`（去重主键）
  - `ts` = 下发时间（建议含执行结果时展示完成时间，主键仍为下发时间）
  - `text` = `操作人 → 设备: 动作 参数 → 结果`，例：`张三 → 1号大棚卷帘: 关闭 [已执行]`；系统自动指令用 `系统/规则名`
  - `level`：失败→warn/critical，成功→info
  - `badge`：`正常`（执行成功）/`异常`（失败/超时）/`未确认`（**语义不贴，控制通常是“待执行/执行中”；建议后端用 status=pending/success/fail，badge 仅做展示兜底 —— 不确定**）
  - `link` = `/oplog?focus=<opId>`
  - `extra`：`operator, deviceId/deviceName, command, params, result, source(manual/rule/api)`
- **排序**：`ts DESC`。
- **去重**：以 `opId` 去重；一条指令的 pending→success/fail 同 id 就地更新。

> 边界一句话：**告警 = 发生了什么异常；巡检 = 定时任务查到了什么结果；控制 = 谁主动做了什么操作**。三者可能描述同一设备，但事件来源不同，允许跨 tab 重复出现（不在 tab 间去重）。

## 2. 表格列设计与点击落点

不再两列，采用 **5 列（在窄面板可降级为 4 列）**。左侧模块宽度有限，给出建议宽度（基于 ~420–520px 容器）。

| 列名 | 宽度 | 内容/字段 | 省略策略 |
|---|---|---|---|
| 状态 | 56px | `level` 色点 + `badge` 小标签 | 不省略；badge 用色块+短字（未确认/正常/异常） |
| 时间 | 64px（桌面 84px 显示完整） | `ts` 相对时间 `14:32` / 悬停全称 | 今日只显示 `HH:mm`；非今日 `MM-DD HH:mm`；`title` 显示完整 `YYYY-MM-DD HH:mm:ss` |
| 设备 | 96–120px | `deviceName` | 单行省略，`title` 全名；无设备显示 `-`（控制/巡检必有） |
| 内容 | flex（min 0） | `text`（含指标/操作人/结果摘要） | 单行省略 `ellipsis`；`title` 或 popover 显示全文 + extra 关键字段 |
| （可选）来源/操作人 | 72px，仅 control tab | `operator` 或 `source` | 单行省略；也可不单列，直接并入 text |

实现要点：
- 表格用固定表头 + 行 `min-width:0` 保证 flex 省略生效；行高紧凑（32–36px）。
- 内容列把“主体”和“数值”做成结构化片段而不是纯字符串（后端给 extra 时）：正常色显示文本，异常值（超阈值/失败）用 level 色高亮。若只能拿到 `text`，就整串纯文本省略。
- level 视觉：critical 红、warn 橙、info 灰/蓝；仅靠颜色不够，critical 行左侧加 2px 色条。

**点击落点与高亮**
- 整行可点击（`cursor:pointer`），跳转 `link`（新标签还是当前页？**建议当前页跳转**，dashboard 是入口；按住 cmd/ctrl 时新标签，交给默认行为用 `<a href>` 最省事）。
- 目标页通过 query `focus=<id>` 定位：
  - `/alarms?focus=<id>`、`/task-runs?focus=<runId>`、`/oplog?focus=<opId>`。
- **高亮方式（三页统一）**：目标页读取 `focus` → 找到对应记录（不在当前页则先按 id 拉取/翻页定位，做不到就仅提示，见下）→ 行背景短暂高亮 `#fff7e6` 并 2s 闪烁一次 + 滚动入视口（`scrollIntoView({block:'center'})`）+ 若该行有“详情/展开”，自动展开右侧抽屉或行内详情。
- 高亮 3–4s 后淡出；`focus` 参数读取后可用 `history.replaceState` 清掉，避免刷新仍强制滚动。
- 降级：目标页列表分页/过滤导致该 id 不在当前数据集 → 显示顶部轻提示 `正在定位记录 #id…`，失败则 `未找到该记录，可能已被过滤`。**是否支持按 id 直接取详情不确定（需详情接口）**；没有详情接口时，至少保证默认未过滤状态下能在前几页找到。

## 3. 未读/新消息提示（不引入 WebSocket，最省事）

**推荐：轮询 + “顶部新消息条”，不做已读持久化（v1）。**

机制（纯前端，后端零改动，除了支持 `?since=` 更好）：
1. 进入 tab 时首屏拉 30 条，记录 `maxTs = 第一条.ts`（或 `maxId`，优先用服务端游标，**不确定接口是否支持 since**；不支持就用 ts 比较）。
2. 每 **30s** 轮询当前 kind 第 1 页（同设备过滤条件），只取返回里 `ts > maxTs` 的条数 `n`。
   - 不把新数据直接插进列表（避免列表跳动/打断阅读），而是在表头顶显示横条：`▲ 有 n 条新<告警/巡检/控制>`，点击 → 重新拉第一页并滚到顶部，清除提示。
3. **Tab 角标**：非当前 kind 也轮询（或在一次请求里加 `?unread=1` 聚合，**后端没有就分别轻量轮询**），在 tab 标题显示红点 + 数字。为省事，v1 可只对**当前 tab**做“新消息条”，tab 角标放二期（仍轮询三次成本也低）。
4. “未读”定义简化为“自上次查看/停留该 tab 后新增”，**不落库、不按用户已读**；切到该 tab 即视为已读（清角标、更新 maxTs）。刷新页面后未读重置——可接受，明确告知是“本次会话新消息”。
5. 页面不可见时停轮询（`document.visibilitychange`），可见时立即拉一次，省请求。
6. 告警类 critical 可在新消息条用红色，但**不做浏览器 Notification/声音**（打扰且要权限，二期）。

为什么最省事：无需已读表、无需长连接；复用现有 list 接口；状态只存在前端内存。
若后端能加：`GET /feed?kind&since=<ts/Id>&limit=1` 仅返回计数或最新游标，轮询更轻——作为可选优化，**当前不确定是否提供，先用现有接口比较 ts**。

轮询间隔/去抖：30s 默认；窗口失焦暂停；连续失败指数退避（15s→30s→60s 封顶）。

## 4. 分页方式：选“加载更多（增量分页）”

**结论：用“加载更多 / 滚动到底自动加载”，页大小 30，最多保留最近 N（如 150 条），不做传统页码分页，也不只固定 30。**

理由：
- 这是**时间线信息流**，用户目标是“往下翻历史”，不是跳第 7 页；页码分页在这里认知成本高、还会被新插入数据打乱偏移。
- 固定 30 条会漏掉半天前历史，问题 4 明确要更多；但无限渲染所有历史会 DOM 膨胀，所以设上限。
- 接口是 `limit=30`，天然适配游标/偏移加载。

实现：
- 请求参数：优先游标 `?kind=&limit=30&before=<oldestTs 或 id>`（**接口当前只有 limit，需后端加 before/cursor；不确定则退而用 offset 分页**）。
  - 偏移降级：`?limit=30&offset=30/60…`，缺点是新数据插入会导致偏移错位（重复/漏一条），用前端按 `id` 去重兜底。
- 列表底部放“加载更多”按钮（同时支持滚动距底 200px 自动触发），显示 `加载中…`；返回 <30 条显示 `没有更多了`。
- 前端缓存上限 150 条：超过后丢弃最旧 DOM/数据（提示“仅展示最近 150 条，完整记录请进入对应页面”），避免长列表卡顿。**150 为建议值，可调。**
- 切换 tab / 切换设备：重置列表回第 1 页（保留各 tab 已加载内容可做内存缓存，v1 可不保留，切回重新拉）。
- “有新消息条”点击是**回到最新（第一页）**，与“加载更多（往过去）”方向相反，两套不冲突。

## 5. 按设备过滤放哪里

**推荐：模块顶部放“设备筛选器”，默认“全部设备”，并与全局当前设备上下文联动；不与“今日任务状态”冲突，但要定好主次。**

具体：
- 在 tab 行右侧（或表头工具行）放一个 `Select 设备：全部设备 ▾`（支持搜索，设备多时用远程搜索/`showSearch`），选中后三个 tab 都带 `deviceId`，**每个 tab 独立分页但共享当前 deviceId**。
- 参数：`/feed?kind=&deviceId=<id>&limit=30`（**需后端支持过滤并在 item 返回 deviceId/deviceName，当前不确定，强依赖**）。
- 与“当前设备”的关系（二选一，建议 A）：
  - **A（推荐）**：若系统有全局“当前设备”上下文（顶栏/布局已选设备），dashboard 默认跟随它（自动选中该设备），但保留切回“全部设备”和改选的能力。即“默认跟随、可手动覆盖”。
  - B：模块完全独立筛选，不跟随全局。简单但多设备时要重复选。
- **与右侧“今日任务状态”是否冲突**：不冲突，但要统一口径：
  - “今日任务状态”通常是**全局/当前范围的汇总卡片**（今日任务总数、完成、异常数）。建议让它**响应同一个 deviceId**：选了设备，左侧消息和右侧任务状态都收敛到该设备，避免“左边过滤了、右边还是全部”的割裂。
  - 若右侧卡片短期内无法按设备过滤，则**默认状态下两者都显示“全部”**，一旦用户在消息模块选了具体设备，在右侧卡片标题加 `范围：全部设备` 灰色标注并给提示，明确范围不一致；尽快对齐。**右侧是否可按设备统计不确定，需确认其数据接口。**
- 设备列表来源：用现有设备列表接口；按权限过滤；包含离线设备（历史消息仍可查）。
- URL 同步：把 `deviceId` 同步到 dashboard query（`?deviceId=`），便于刷新保持和分享。

## 智谱 GLM（glm-5.2）

这份设计基于你现有的后端接口和页面布局，针对「信息密度低、语义模糊、缺乏反馈」三个核心问题给出具体方案。

### 1. 三个 Tab 的准确定义

消除语义歧义，明确各自的数据边界和取值：

*   **巡检消息**
    *   **定义**：自动巡检任务的执行结果反馈。
    *   **数据源**：`GET /api/v1/dashboard/feed?kind=patrol`
    *   **关键字段映射**：`text` 展示任务名称；`badge` 为「正常/异常」；`link` 提取 `runId`。
    *   **去重/排序**：按 `runId` 去重（同一个任务短时间内多次重试只留最新一条）；按 `ts` 倒序。
*   **告警消息**
    *   **定义**：设备触发的实时告警。
    *   **数据源**：`GET /api/v1/dashboard/feed?kind=alarm`
    *   **关键字段映射**：`text` 展示告警内容；`level` 决定行背景色或左侧色条（critical 红/warn 橙/info 蓝）；`badge` 强制为「未确认」。
    *   **去重/排序**：同设备同类告警在 1 分钟内仅保留最新一条（防抖）；按 `ts` 倒序。
*   **控制消息**
    *   **定义**：人工下发的控制指令及执行回执。
    *   **数据源**：`GET /api/v1/dashboard/feed?kind=control`
    *   **关键字段映射**：`text` 需拆分为「操作人 + 动作 + 目标设备」（要求后端在此字段补全，或前端按固定正则解析）；`badge` 为「成功/失败」；`link` 提取 `opId`。
    *   **去重/排序**：按 `opId` 去重；按 `ts` 倒序。

### 2. 表格列设计与落点

将两列改为三列，利用 `link` 字段做跳转：

*   **列1：时间 (15%, 约 120px)**
    *   展示：`HH:mm:ss`（hover title 展示完整 `YYYY-MM-DD HH:mm:ss`）
*   **列2：内容 (65%, 自适应)**
    *   展示：`text` 字段，`text-overflow: ellipsis` 单行省略。
    *   **视觉锚点**：行首加 4px 宽的竖线色条，颜色对应 `level`（critical红/warn橙/info蓝/默认灰）。
*   **列3：状态 (20%, 约 100px)**
    *   展示：`badge` 字段，用小号 Tag/Pill 组件渲染（异常/未确认用实色底，正常/成功用描边底）。

**点击落点与高亮**：
*   **落点**：整行可点击，依据 `kind` 跳转到对应页面的查询参数（`/alarms?focus=<id>` 等）。
*   **高亮方式**：目标页面加载时，读取 URL 中的 `focus` 参数，在表格列表中匹配对应行 ID，给该行 DOM 加上 `background: var(--highlight-bg)` 且持续闪烁 2 秒，随后自动滚动到该行视口中央。

### 3. 未读/新消息提示（省事方案，无 WS）

利用 **「角标 + 轮询对比」** 机制：

*   **机制**：前端每 30 秒轮询当前激活 Tab 的接口。比对最新一条消息的 `id` 与本地记录的 `lastReadId`。
*   **提示表现**：
    *   如果有新消息，在当前非激活 Tab 的标题旁显示红点（或数字角标，如 `+3`）。
    *   如果用户切换到该 Tab，清空角标，并更新 `lastReadId`。
*   **增量更新**：轮询拿到新数据后，采用 **Prepend（头部插入）** 策略。列表头部出现一条带「淡蓝色背景」的新消息行，2 秒后背景渐变消失，保持列表条数上限不变。

### 4. 翻页策略：固定 30 条 + 首屏增量

*   **决策**：保持固定 30 条，不加翻页和加载更多。
*   **原因**：这是 Dashboard 模块，不是日志检索页。用户在此只关注「当下最新动态」。轮询新消息 Prepend 进来即可，老消息自然溢出被挤掉。如果用户真需要看历史，应通过点击进入 `/alarms` 或 `/oplog` 的独立列表页去做复杂检索。

### 5. 设备过滤的位置与冲突处理

*   **放置位置**：放在 Tab 栏同一行的右侧，作为一个全局下拉筛选 `<Select>` 组件（选项包含“全部设备”及当前用户权限下的设备列表）。
*   **交互细节**：切换设备时，在请求 URL 上拼参数 `&deviceId=xxx`。
*   **冲突处理**：**会冲突**。「今日任务状态」通常展示所有管辖设备的任务概况。如果按设备过滤，左侧表格只剩该设备消息，右侧仍是全局任务，会导致认知割裂。
*   **解法**：过滤组件只向左侧 Feed 模块下发 `deviceId` 参数，**不改变**右侧「今日任务状态」的数据。在筛选下拉旁加极小号提示文案「仅过滤消息流」，明确告知用户作用域。

### 6. 状态文案设计

*   **加载态**：展示骨架屏（3 行灰条），文案不需要。
*   **空状态**：
    *   巡检：「暂无巡检记录，最近一次任务完成后将在此展示」
    *   告警：「暂无告警消息，设备运行平稳」
    *   控制：「暂无控制指令记录」
    *   *（如果有设备筛选）*：「当前筛选设备暂无消息」
*   **错误态**：「消息获取失败，<a onClick={retry}>重试</a>」

### 7. 最小可行改动清单（按投入产出排序）

1.  **扩充列与视觉标记**：将两列改为三列（时间/内容/状态），并在行首添加代表 `level` 的竖向色条。（产出：信息密度和辨识度立竿见影提升）
2.  **行点击跳转**：给表格行包一层 `<a>` 或加 `onClick`，提取 `link` 参数执行 `router.push`。（产出：打通从消息到详情的闭环）
3.  **新消息轮询与角标**：加 30s 定时器，比对首条 `id`，给非激活 Tab 加红点角标，切换 Tab 时清除。（产出：解决无反馈痛点，改动仅限前端状态管理）
4.  **新消息 Prepend 动画**：轮询到新数据时插入列表顶部，加 2s 背景渐变 CSS 动画。（产出：形成动态实时感）
5.  **顶部设备筛选器**：在 Tab 栏右侧加一个全局 `<Select>`，把选中的 `deviceId` 拼入 Feed 接口请求参数。（产出：解决多设备消息混杂问题）
