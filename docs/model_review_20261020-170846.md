# B. 产品经理视角

## B1. 12/01 观众是谁、必问三问

**【判断】** 参考图是“给客户/领导看过的”，所以现场观众八成是：甲方安全/生产部门负责人 + 我方领导，可能有运维班长。他们不关心技术栈，只关心三件事：

## B4. 验收 13 条里客户大概率不认的

注：题面只列了 6 条示例，按这 6 条评：

1. **“登录 2s 内看到状态”——客户大概率不认“2s”这个数字本身，但会认“打开就能看到”。【判断】** 风险在首屏状态来源：如果首屏靠 1s 轮询冷启动，最坏要等 1s+请求耗时，内网够用。真正风险是 token 冷启动串行：登录→拿机器 token→拿状态，**首屏要做并发预热，否则首启 3–5s**。建议口径改成“登录即见最新状态（页面显示数据时间戳）”，把新鲜度交给 UI 上的时间，而不是秒表。
2. **“3 点位姿一致”——客户不认“一致”，认“差多少”。【判断】** 必须给量化口径，比如“平台显示位置与机器人实际位置偏差 < 1m / 一个栅格”。像素坐标、地图坐标、前端缩放三层换算，没有肉眼“一致”这回事。提前在真机上用激光标尺或地标点测三个点，录视频留证。
3. **“不支持接口不弹成功”——客户根本看不懂这条，这是给自己的工程纪律，别放进客户验收文本。【事实】** 放进验收反而被问“什么叫不支持的接口”。
4. **“Mock 不进生产”——同上，客户不关心。** 但甲方 IT 审计可能关心配置项，改成“生产环境配置清单经双方确认”。
5. **“拔网线显示失联”——客户认，但演示时要设计好。【判断】** 要确认失联判定时延口径（建议：HTTP 连续 2 次失败 + WS close，约 3–5s 内标灰），否则现场拔了网线 10 秒还绿着就尴尬。恢复后自动重连也要演，这是加分项。
6. **“3 点任务能跑 / 告警产生确认导出”——这两条是硬通货，客户一定认，务必作为演示主线。**

## B5. 30 分钟演示脚本

**顺序：**

1. **（0–3min）登录 → 驾驶舱**：状态条、电量、在线。先让它“活着”。
2. **（3–10min）地图主页：实时位置跟随 → 当场下发去 1 号点**，看箭头动、看任务状态从 WAITTING→WORKING→COMPLETE 流转。这是全场最高潮，放前面，趁观众注意力最好。
3. **（10–18min）三点巡检验证完整任务流**，同时讲点位是可配置的，当场 CRUD 一个点（或提前准备好）。
4. **（18–25min）告警闭环**：提前布好低阈值或直接按急停 `driver_port`，告警弹出→确认→填处理意见→导出 Excel。
5. **（25–30min）拔/插网线失联恢复 + 历史轨迹回放 + 主动讲二期（视频/3D）规划**，收尾。

**坚决不演：**

- 不演“停止全部任务”（危险操作，万一机器人不停或停错）；
- 不演需要现场签字授权的首次运动指令（提前签好纸质单放在旁边，有人问再展示）；
- 不演任何未在真机上连续成功 20 次的功能；
- 不演暂停/恢复在真机上的边界（任务状态机最容易在 PAUSED 后 resume 行为不符）——除非真机验过；
- 不用生产唯一一台真机演“机器人重启后对账”，录屏备播。

**【判断】 准备一条 5 分钟的录屏兜底**，演示网络/机器人出问题时放。这不是丢人，是工业现场演示的标配。

# C. 全栈工程师视角

## C1. 单进程 asyncio 的风险与拆分触发条件

**【事实】** 单 worker 内跑 4 个后台循环 + WS 长连 + Web 服务，共享一个事件循环。

**风险点：**

1. **任何一个同步阻塞调用冻结全部循环**。Pydantic v2 / SQLAlchemy 2 大多 async 友好，但：MySQL DNS 解析、`PIL.Image.open` 读 PNG（地图换算读像素高）、requests 误用、大 Excel 导出（openpyxl 同步且吃 CPU）、ECharts 服务端截图——任何一个忘了 `run_in_executor`，WS ping 断、状态变“过期”、全站一起抖。【事实+判断】
2. 一个未捕获异常杀掉 task 后没有自动重启 = 后台循环静默死亡（比如 ws_listener 挂了只剩 HTTP，没人发现）。**所有循环必须包 supervisor 重启 + 自身存活指标上报。**【判断】
3. 进程重启窗口期（部署/崩溃）WS 断、轮询停，状态出现几十秒空洞。可接受，但 UI 必须显示“采集中断”而不是假装连续。【判断】

**必须拆的触发条件（量化）：**

- Web P95 响应 > 500ms 且后台循环占用可证实（加 `/debug/loop-lag` 指标，事件循环 lag > 100ms 持续 10min）；
- 第二台机器人接入（WS 连接数、轮询量翻倍只是小事，**调度语义才是大事**，单机器人写闸门直接失效）；
- status_poller 周期实际抖动 > 30%（计划 1s、实际经常 1.5s+）；
- uvicorn 重启导致取消中的运动任务对账错乱（任务执行中重启 = 镜像状态悬空）；
- 多人并发使用 > 10 在线或导出大报表开始拖慢实时接口。

**【判断】 在这些触发前，单进程是正确决定，别上 Redis。** 但现在就要把“后台任务入口”收敛成一个独立模块（一个 `BackgroundServices` 类），拆的时候只改启动方式，不改业务。

## C2. HTTP 轮询 + WS 双源一致性

**【事实】** `/system/galileo_status`（HTTP）与 WS `/galileo/status` 大概率同源同结构；环境量只在 WS。

**口径建议：**

1. **位姿/速度/电量：WS 为主源，HTTP `/galileo_status` 每 1s 作为心跳与纠偏**，不是平等双写。理由：WS 推送频率通常 ≥1Hz 且延迟低；HTTP 1s 是离散快照，双源平等写必然抖动。【判断】
2. **统一时钟归一**：机器人报文里的时间不可信（电池设备 NTP 状态未知），**平台收到时打 `recv_ts`（服务端 monotonic + wall clock）入库入缓存**。所有新鲜度判定（口径 13 的 3s）用 `recv_ts`，不用设备时间。【事实+判断】
3. **去重与乱序**：WS 重连后可能与 HTTP 快照重叠。缓存层按 `(字段组, 源, 序号/recv_ts)` 做 latest-wins，但只接受比当前更新的数据（防重连旧帧覆盖新帧）。【判断】
4. **UI 防抖**：箭头位置不要逐帧硬设。机器人速度字段有了（`currentSpeedX/Theta`），**用轻量插值（线性补间 200–500ms）而不是死点位**；角度走最短弧插值。但 `angle`（度）与 `nav_action.theta`（弧度）、`currentAngle`（单位未定，口径 5）三套角度必须在 Adapter 层**全部转成弧度并归一中枢**，UI 只见一个字段。这是必踩坑。【事实】
5. WS close → 立即标“链路中断”但**不立刻标机器人失联**（WS 断不等于机器人离线）；HTTP 连续 2 周期失败才标灰。两层状态分显：`链路:WS/HTTP`、`设备:在线/失联`。【判断】

## C3. Canvas 自绘地图的坑

**【事实】** 200 点位 + 2000 轨迹点对 Canvas 2D 毫无压力（万级 primitive 才需要优化），真正的坑在别处：

1. **坐标系三层转换是头号 bug 源**：像素 PNG → 地图坐标（`x0+px*res`、`y0+h*res-py*res`，注意 **Y 翻转**）→ 屏幕坐标（平移缩放）。所有鼠标事件必须走同一个 `screenToMap()`，点位 CRUD 的拾取和保存共用它。**写成三个独立函数的项目最后都对不齐。**【事实】
2. **`h` 依赖 PNG 像素高**：换图、重导地图后 h 变，历史轨迹和点位全部错位。**PNG 拉取后立即读一次 `(width,height)` 与地图元数据一起入库**，坐标换算永远用库存值；历史点位绑定 `map_id + map_version(md5sum)`，换 md5 后旧数据只读展示并提示。【事实+判断】
3. **高清屏模糊**：记得 `canvas.width = cssW * devicePixelRatio` + ctx.scale，否则在 4K 屏/领导的高分屏上糊成马赛克——演示事故级。【判断】
4. 轨迹 2000 点用一条 `Path2D` 单次 stroke；不要逐点画圆。告警光圈/呼吸动画用固定几个 DOM overlay 或离屏 canvas，别每帧全量重绘底图：**底图（PNG）画到离屏 canvas，交互帧只重绘动态层**（分层：底图层/静态层/动态层三个 canvas 叠放）。【判断】
5. 拾取 200 点位不要每点距离计算配 React 响应式：纯数学命中检测（矩形包围盒粗筛）在 canvas 内完成，hover 状态用节流 mousemove（~30Hz）。
6. 缩放要以鼠标位置为锚点（否则缩放飞走），设 0.5–4 倍钳制；PNG 内存：一张大场站 PNG decode 后是 `w*h*4` 字节，5000×5000 ≈ 100MB/张，**真机拉到图先看尺寸**，超限要服务端降采样。【未验证】
7. 虚拟墙/忽略区编辑（多边形增删顶点、撤销）是这个页面真正的工时黑洞，**建议 W3 只做矩形/多边形展示 + 简单绘制，复杂编辑推二期**。【判断】

## C4. 任务状态机 + 2s 对账在异常下怎么坏

**【事实】** 机器人状态：WAITTING/WORKING/PAUSED/CANCELLED/ERROR/COMPLETE；`stop` 无 id 取消全部；控制 GET。

**坏法清单：**

1. **下发后超时（3s）**：不自动重试（口径 11 正确），但超时那一刻任务可能已在机器人侧创建 → 平台显示“下发失败”、机器人却在跑。**超时后的唯一正确动作是立即 GET `/task` 对账，而不是让用户重试。** 现在方案里没写这个对账分支，要补。【事实+判断】
2. **丢包 / 平台重启**：平台库里 WORKING 的任务，机器人侧已 COMPLETE。reconciler 用机器人列表回灌：以机器人状态终态为准写镜像，并对“平台有、机器人没有”的在途任务置 `UNKNOWN/需人工确认`，**不能自作主张置成功或失败**。【判断】
3. **机器人重启**：内存任务队列可能清空也可能保留（PDF 未保证）【未验证】→ 平台在途任务全部进“未知”态，靠人工在现场确认。UI 必须有这个状态，别只有六个机器人态。
4. **状态翻转抖动**：WORKING 与 PAUSED 在网络抖动下可能瞬时跳变；终态（COMPLETE/ERROR/CANCELLED）一旦写入**锁死不可回退**，非终态更新覆盖。
5. **幂等键**：平台任务 `task_uuid`（平台生成）+ 机器人返回的 `jcrob_task_id` 建立映射，落库唯一键。重发同一 uuid 时：先查映射，有 id 则查状态，不重复 POST。**机器人侧是否支持客户端幂等键 PDF 没有，所以幂等只在平台侧做，对机器人永远是“先查再发”。** 回调（callback action）带 run token + task_uuid，机器人回调到达时若任务已终态 → 只记审计不改状态。【判断】
6. **并发写闸门**：口径 6 要求 `Free + busyStatus=false`。注意 TOCTOU：查到 Free 到 POST 之间状态会变。**闸门状态必须以“下发后 GET 到的实际结果”闭环**，Free 检查只是前置过滤；一个运动任务的锁放 Redis 是过度，**进程内 asyncio.Lock + 平台任务表唯一“在途运动任务”部分索引**即可（单 worker 下 Lock 有效，这也是单进程的红利）。【判断】

## C5. 60 万行/7 天单表，够吗？

**【事实】** 算一下：8.64 万/天 × 7 = 60.5 万；聚合 26 万；环境 156 万（90 天）。InnoDB 里这种窄表 60 万行大约几百 MB，**单表本身不崩**，B+Tree 三四层，带索引点查毫秒级。你的估算没问题。

**真正会崩的场景：**

1. **没分区时的删除**：7 天清理用 `DELETE` 删 8.6 万行/天 → 大事务、binlog 暴涨、purge 延迟、空间不释放（碎片）。这是头号实际问题。【事实】
2. 历史曲线查询时间范围忘带索引或跨全表扫；`(ts)` 聚簇索引下范围扫描其实还行，但 `WHERE robot_id + ts` 在多设备时必须复合索引（单机器人也先写上，成本为零）。
3. 156 万环境表 + 保留策略变长后，三年就是千万级，开始影响统计类查询。

**更省钱且不过度的方案（推荐）：**

- 原始状态表：**MySQL 按天 RANGE 分区**（`PARTITION BY RANGE TO_DAYS(ts)`），retention 改成 `ALTER TABLE ... DROP PARTITION`（元数据操作、秒级、无碎片）。Alembic 不好管分区，用一次性迁移 DDL + 文档注释，值得。【判断】
- 如果嫌分区麻烦：**每日物理归档** `status_raw_YYYYMMDD` 表 + 视图 union 最近 7 天。更土但更不容易出错。
- 环境 5s 数据：入库前在进程内做**死区降采样**（变化小于阈值不写），156 万大概率能砍掉一半以上，零硬件成本。【判断】
- 不要现在上 TimescaleDB/ClickHouse/TDengine——单机单机器人是过度设计，真到千万级再迁，结构简单迁移不难。

## C6. load 28 的共享宿主机实际风险

**【判断+事实混合，按概率排：**

1. **CPU 饥饿（最高危）**：load 28 取决于核数，若 16 核则长期饱和。风险不在平时，在**演示当天某个模型服务批量推理**，uvicorn 事件循环被调度延迟，WS ping 超时、1s 轮询变 5s。措施：部署前 `nproc && uptime && top` 摸底；docker `--cpus` 申请（比如 2 核）+ `--memory=2g` 上限，**既防邻居也防自己 OOM 拖整机被人骂**；演示前找宿主管理员要当天的“安静窗口”。
2. **磁盘**：52 容器 + CVAT 视频/模型镜像，磁盘满是这台机器最可能的事故。查 `df -h` 和 inode；MySQL binlog、我们的状态数据、镜像层全在同一块盘。措施：独立 docker volume 放数据目录前先确认挂载点空间；binlog 保留设短；应用日志 rotate；**留 20G 红线告警**。
3. **端口**：8099 确认没被占（`ss -tlnp`），并检查 docker-compose 项目名加前缀（版本里“资源加前缀”要包括 project name、network name、volume name、容器名、MySQL schema 名），避免和别人的 `mysql` 容器名/3306 内部服务冲突。**我们的 mysql 容器绝不映射宿主 3306**，只走内部网络。
4. **Docker 网络**：52 容器若有人用 host 网络或自定义网段冲突可能波及；compose 独立 bridge 网络最干净。容器 DNS 偶发解析慢会影响出网调用——机器人调用地址直接用 IP，别依赖容器 DNS 名。【判断】
5. **镜像拉取**：内网 mirror 速率未知，mysql:8 / python / nginx 三个镜像**提前一周拉好并 `docker save` 备份**，交付日不拉镜像。
6. **备份冲突**：宿主机如果有整机 crontab 备份（mysqldump 扫所有 data 目录很常见），凌晨 dump 会撞上我们的 retention_job——retention 放凌晨 3:47 这种错峰时间，并问管理员备份窗口。
7. MySQL 8 默认 `innodb_buffer_pool_size` 在小内存限额下要显式调（默认可能吃到几百 M），配 `--memory` 后不调会 OOM kill。
8. **“将来可能上公网”**：现在就按公网标准做一件事——8099 只绑内网网卡或前置 nginx 加 HTTPS；httpOnly Cookie 的 `Secure/SameSite` 配置按环境区分，现在不留明文 HTTP 的懒习惯。

**B. 产品经理视角**

**A1. 演示观众与必答问题**
观众大概率是厂区负责人和IT运维，他们不关心 Vue 还是 React，甚至不关心你用不用 Redis。
一定会被问到的三个问题：
1. “机器人没电了自己去充，这中间断了网或者卡住了，你们平台能发现并报警吗？”（关注异常兜底）
2. “我以后要加一个‘去A点拍照再去B点’的任务，是不是还要找你们开发？”（关注任务扩展性，虽然本期不做图形化编排，但话术要准备好）
3. “这套系统装在哪？如果机器人厂家更新了接口，你们怎么保证不影响我们使用？”（关注解耦和维护责任边界）

**A2. 3D 落差管理**
【判断】2D 底图的最大劣势是缺乏“空间纵深感”，容易像上位机软件而非“平台”。
低成本补齐手段：
1. 底图不要纯贴 PNG，用 Echarts/gl 简单加一层视差倾斜（伪2.5D），或者给底图加一层半透明拓扑网格。
2. 状态卡片不要用普通表格，用毛玻璃悬浮面板，强化“数据悬浮于场景之上”的观感。
3. 历史轨迹用热力图渐变渲染，而不是单纯的线，增加视觉信息密度。

**A3. 未接入功能的呈现**
【判断】千万不要在 UI 上留“视频 Coming soon”或灰色的 3D 图标，这会显得是个半成品。
取舍方案：
1. 隐藏式：直接不出现这些菜单和组件，只保留当前核心功能。
2. 归档式：在“系统设置-扩展能力”里放一份纯文本的能力路线图，不占主界面。
建议采用 1，演示时如果被问到，回答“架构已预留接口，下一阶段视硬件情况接入”。

**A4. 验收口径风险**
【判断】以下几条客户大概率不认，需提前改口径：
- “3 点位姿一致”：客户只认“地图上小车停的位置和实际位置差多少”，不认后端 JSON 的 X/Y 值。需改为“3 点实际停车误差 < 0.5米”。
- “不支持接口不弹成功”：客户视角是“我点了去A点，它去了就行”，如果没去也不报错，就是平台 BUG。必须改为“任何失败必须有明确中文提示”。

**C. 全栈工程师视角**

**B1. 单进程风险与拆分触发**
【事实】单 worker 风险在于：任何一处同步阻塞（如大表查询、慢 SQL）会卡死全站，包括 WS 心跳。
【判断】触发拆分的条件：
1. 并发 WS 连接数 > 50，或事件推送延迟 > 500ms。
2. 任务对账逻辑导致主事件循环单次执行 > 200ms。
3. 发现由于 GIL 导致高并发下 HTTP 请求排队。
如果 12/01 演示前爆出这些问题，别重构，直接把 `uvicorn --workers 1` 降级为 `fastapi run` 并限制前端并发。

**B2. 双源一致性与 UI 抖动**
【判断】机器人 HTTP 1s 推送和 WS 推送频率不同，如果前端分别监听，地图上的小车会“瞬移”或“倒退”。
必须现在改：
1. 后端作为唯一真相源，WS 收到数据后更新内存缓存，`status_poller` 1s 读缓存推给前端。
2. 前端不要直连后端 WS 与机器人 WS，只接收后端单一频率的 WS。
3. 前端收到位姿后，不要直接 `setState`，使用 `requestAnimationFrame` 做坐标插值动画，平滑过渡。

**B3. Canvas 自绘地图的坑**
【判断】单页 2000 个轨迹点在缩放/拖拽时如果不加优化，帧率会掉到个位数。
1. 必须实现“脏区域重绘”或“双缓存 Canvas”，不要每次 `clearRect` 全量重绘。
2. 拾取坐标时，不要用遍历 2000 个点算距离，必须建立空间索引树（如四叉树）或利用像素碰撞。
3. 缩放时，点位图标要根据缩放级别动态合并或隐藏，否则满屏马赛克。

**B4. 任务对账的灾难**
【判断】“机器人是唯一真相源”在丢包时就是地狱。如果平台发了 `stop`，网络丢了，机器人还在跑，平台库标记为停止，UI 显示停止，实际狂奔。
必须现在改：
1. 引入“看门狗”机制：任务下发后，如果 2s 内没有 WS 回传状态变更，主动调 `/task` 查询。
2. 幂等键设计：不要用时间戳，用 `platform_task_id` + `robot_task_id` 做双键比对。
3. 在任务列表加一个“最后心跳时间”字段，超过 5s 未更新，状态强制显示为“通信中断-状态未知”。

**B5. MySQL 单表 60 万行**
【判断】60万行不大，但如果全放在单表且包含 TEXT/BLOB，7天后的范围查询会引发磁盘 IO 飙升，连累共享服务器上的 52 个容器。
更省钱的方案：
1. 1s 级状态数据根本不落 MySQL，直接存后端内存字典（或写本地 SQLite 文件）。
2. MySQL 只存 1 分钟聚合后的数据，每天 1440 行，180天也就 26 万行，毫无压力。
3. 告警和审计日志落 MySQL，因为这些是低频写入。

**B6. 共享服务器的风险**
【事实】load 28 已经偏高，宿主机 CPU 调度存在严重抢占。
1. 内存：如果宿主机没限制每个容器内存，MySQL 8 可能会吃光内存被 OOM Kill。
2. 网络：52 个容器如果都在同一个 Docker Bridge，广播风暴会导致 WS 丢包。
3. 磁盘：MySQL 默认 `fsync` 策略会与其他数据库容器抢 IO，导致写入延迟。
建议：向运维申请固定 CPU/内存配额，MySQL 容器挂载独立 IO 路径。

**B7. 六周排期关键路径**
【判断】关键路径在 W3（地图点位）和 W4（任务状态机）。
最容易爆的是 W4：`/task` 状态机的 PDF 描述如果有歧义，Mock 数据根本测不出。真机 11/10 上线后，如果发现状态流转不对，W4 直接延期，连带 W5 联调崩溃。
建议：W1-W2 阶段，必须找机器人厂家技术支持拉齐 `/task` 状态流转图，特别是 ERROR 和 CANCELLED 的边界条件。

**B8. 安全设计是否过度**
【判断】纯内网单系统，JWT + CSRF 是过度设计，但这不是主要矛盾，不用改。
真正不够的地方：
1. 【事实】机器 token 落库如果日志打印了明文 URL，内网一抓包就泄露。
2. 【判断】回调 run token 如果没有 IP 白名单，内网任何人都可以伪造回调。
必须现在改：后端日志中间件必须对 `Authorization` 和 `token` 参数脱敏。

**C1. 最值得质疑的 3 个假设**

**C3. 过度设计**
1. **嵌套行为树的解析与降级保留**：既然平台只产出扁平 action，就不需要实现解析器。读取时容错就够了，不用搞复杂的降级策略。砍了会失去对复杂旧任务的兼容性，但新系统没历史包袱，不需要。
2. **CSRF 防护**：纯内网且只有内网 IP 访问，没有跨站风险。砍了失去前端发请求时要带 Header 的麻烦。

**C4. 最可能翻车的单点与提前发现**
【判断】最可能翻车的单点：**真机 WS 连接的不稳定性导致状态机对账崩溃**。
提前三天发现的方法：

**E. 与我方结论冲突的地方**

1. **数据量评估冲突**：你方认为“60万行全部放 MySQL 单表不做分区，不会崩”。我认为你错了，因为在 load 28 的共享宿主机上，磁盘 IO 本来就紧张，MySQL 单表频繁写入 1s 级数据会引发锁等待，且前端查询历史轨迹时的全表扫描会直接打满 IO，连累整个服务器。必须降采样。
2. **任务对账可靠性冲突**：你方认为“2s 对账 + 机器人是唯一真相源”能保证一致性。我认为你错了，因为 2s 对账在机器人重启或断网 5s 的情况下，平台库里就是脏数据。如果前端直接信库，就会显示“任务已停止”但真机在跑。必须引入心跳超时机制，状态不明时绝对不展示确切的“已停止/运行中”。
3. **UI 抖动处理冲突**：你方未提及前后端双源（HTTP 1s + WS）导致的前端渲染抖动对策。我认为如果不做 RAF 插值，地图上的小车会疯狂闪烁。这不是 UI 细节，而是必须现在改的架构设计。
4. **安全设计冲突**：你方认为 JWT+CSRF 在内网是过度设计但“不用改”。我认为在单人六周的开发资源下，实现完整的 CSRF Token 交换会吃掉前后端至少 2 天时间，这是实打实的工期浪费，应该果断砍掉 CSRF，仅保留 JWT。
