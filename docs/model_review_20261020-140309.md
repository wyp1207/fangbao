# 防爆机器人可视化平台 — 全栈架构师评审

## A. 结论先行

1. **选型：Vue3 + FastAPI**，单人6周、协议适配为主、无高并发/事务/多团队约束，Java 栈的增量成本不划算。
2. **最小部署可砍到 Vue + FastAPI + SQLite/MySQL + Nginx 四件套**，ZLMediaKit 仅在海康 RTSP 需 Web 播放时才加；Redis/MinIO/EMQX/TDengine/XXL-Job/ELK 全部后置。
3. xlsx 模块约 **40% 在 JCROB 协议下无法实现或应砍到 P2**：空调控制、充电房设备、BMS 单体、双摇杆车体遥控、AI 识别结果、MQTT/Modbus 接入等均无协议支撑。
4. 最大工程风险不是技术，是**安全授权**：任务下发、IO、充电、遥控在防爆区属于高危操作，必须有二次确认+权限+审计+急停闭环。
5. 巡航方案在协议层成立，但**视觉导航重定位失败**是现场最高频故障，平台必须显式暴露定位置信度/失败态，不能假装"正在执行"。
6. 数据契约缺 8 项真机必探字段，首要的是 loop_task 的点位结构、action 下发的同步/异步语义、错误码表和媒体能力。
7. UI 参考照片是典型"科技蓝大屏"，可借鉴信息密度但不能照搬深色高饱和风格做长时间操作台。
8. 6 周内只保 1 个驾驶舱 + 1 个任务管理 + 1 个地图点位 + 1 个告警列表 + 登录鉴权，其余全部 P2。

## C. 技术栈裁决

### 明确结论：**Vue3 + FastAPI（Python 3.11+）**

| 维度 | Vue3 + Spring Boot 3.2 | Vue3 + FastAPI |
|---|---|---|
| 单人6周开发速度 | 重：DTO/Mapper/三层结构/编译重启，CRUD 成本高 2-3 倍 | 快：Pydantic 模型即文档，热重载，协议代理代码量约为 Java 的 1/3 |
| 本项目本质 | —— | 是**协议适配网关 + 状态面板**：大量 HTTP/WS 透传、字段归一化、规则推导，Python 的 aiohttp/httpx 异步代理天然合适 |
| 实时能力 | Spring WebFlux/原生 WS 可用但样板多 | FastAPI 原生 async + ws，一个进程同时做 REST、WS 代理、静态托管 |
| xlsx 硬指标 | 若合同/验收白纸黑字写明 Java + EMQX + TDengine，则必须遵守 | 仅当 xlsx 是参考性技术建议时可选 |
| 后期团队 | 公司是 Java 团队、后续有人接手迭代 | 全栈一人长期维护或后续招 Python |
| 性能 | 无实质差异（此场景并发 < 50 连接） | 无实质差异 |

**选 Java 的唯一充分条件**：xlsx 是合同附件且验收/招标明确指定，或运维环境只允许 JDK。**"会 Java"不是选型理由。**

### 切换条件（从 FastAPI → Spring Boot）
- 合同合规审计明确要求 Java 技术栈（2 周内必须确认，越晚切换成本越高）。
- 后续要接入多租户、复杂权限、ERP/MES 对接、长期 3+ 人团队维护。
- 出现强事务需求（目前不存在：机器人状态是最终一致的，平台 DB 只存任务/告警/报表）。

### 6 周风险对比
- **选 FastAPI 的风险**：甲方审计质疑（用"接口文档 + 稳定性实测"应对）；后续 Java 团队接手成本（Adapter 分层隔离，核心业务逻辑不绑定框架）。
- **硬上 Spring Boot 的风险**：6 周内大概率交付质量塌方——协议适配 + 状态同步 + 前端页面全部从零，Java 样板代码会吃掉 30-40% 工时，联调时间被挤压，而**本项目最大风险恰恰在真机联调，不在框架**。

前端无论哪条路都用 **Vue3 + TS + Vite + Pinia + ECharts**；Arco 可留可换（Element Plus 组件更全、中文后台模板多），**Leaflet 不需要**：机器人地图是单张室内/厂区 PNG + 米制坐标，用 Canvas/自绘 SVG 层即可，引入 Leaflet 的坐标系和瓦片概念反而是负担。

### 砍掉 / 明确标注"协议不支持"

- **充电房设备状态、门禁、照明、无线充电源控制**：除非 IO 通道映射被书面确认，否则不能做，做了就是现场事故源。
- **BMS 15 串单体电压**：协议只有聚合电量/充电状态，页面禁止出现。
- **点位 AI 识别结果（表计读数、油位、状态识别）**：JCROB 不上报，machine-dog n8n 链路不是实时链路；不做。
- **MQTT 设备接入、EMQX、Modbus、GB28181 级联**：无设备、无需求。
- **TDengine、ELK、XXL-Job、Redis、MinIO**：MySQL + 简单定时任务（APScheduler/系统 cron）+ 本地文件存储即可。
- **SLAM/建图功能**：平台不做，建图用车端/JCROB 自带工具。
- **视频墙多路同时播放**：浏览器 WebRTC 多路上行 + 转流服务器压力，演示阶段无意义。

|---|------|---------|---------|

| 5 | **视觉导航重定位失败被掩盖**：机器人上电/换区后自动定位失败，平台仍显示"任务中"，nav 被静默拒绝或乱走 | 冷启动、光照变化大、场景改造、换地图 | 见 H 节专答；核心：显式定位状态、失败即锁任务、引导人工介入 |

**其他必须点名的风险**：
- **UDP 22002 发现依赖广播**：跨 VLAN/厂区路由隔离时发现不到设备 → 必须支持手工填 IP，发现功能只是锦上添花。

## 智谱 GLM（glm-5.2）

A. 结论先行
1. **技术栈必选 Vue3+FastAPI**。单人6周赶12月交付，Java Spring Boot 是自杀行为。xlsx 只是参考，不要被假硬指标绑架。
2. **方案存在致命前提错误**：JCROB 协议提供的是“底盘执行”能力，xlsx 要求的“AI点位识别结果”、“结构化告警”、“BMS单体电压”完全缺失，若不提前做接口降级，前后端会全部阻塞。
3. **巡航方案存在逻辑跳跃**：视觉导航无 `start_index` 时的“自动定位”依赖现场环境特征匹配，平台直接下发循环任务极大概率在拐角/特征重复区失败，必须引入平台侧的状态校验与重定位干预。
4. **MVP 部署极简到 Vue + FastAPI + SQLite + Nginx**。ZLMediaKit、Redis、MinIO 全部后置或用云服务/本地文件替代。
5. **UI 绝不能照抄参考图**，控制室大屏与后台管理是两种语境，强行堆砌会导致关键操作被隐藏，误操作风险极高。

B. 数据契约缺口
上真机前必须按以下优先级确认接口/字段，否则开发全是空中楼阁：

| 缺口字段/接口 | 为什么需要 | 优先级 |
| :--- | :--- | :--- |
| **任务执行结果与媒体回调** | `/task` 只有状态(WORKING/COMPLETE)，没有“当前在第几个点”、“这个点抓拍的照片URL”。平台无法关联巡检点位和抓拍图像。 | P0 |
| **急停/恢复控制接口** | 方案允许下发任务，但未明确底盘是否接受 HTTP 急停指令。若无，平台任务取消形同虚设。 | P0 |
| **云台控制指令格式** | xlsx 要求双摇杆云台控制，但协议中仅有 `camera_rgb` 信息，缺少 PTZ 的控制接口(`/action` 中的 onvif能否覆盖需验证)。 | P0 |
| **环境传感器阈值与单位** | WS 提供了 `lel` (可燃气体)等数据，但未提供报警阈值接口。防爆场景下，阈值是由平台写死还是底盘下发？ | P0 |
| **电量与充电对接状态** | `charge` 字段存在，但缺少“正在对接充电”、“充电失败”、“电量极低”等复合状态，需要确认能否仅靠 `power` 和 `charge` 推导。 | P1 |
| **地图坐标系与多楼层切换** | 虽有换算公式，但多楼层 `levels` 切换时，前端的 Leaflet 需要知道如何重新加载底图并切换原点。 | P1 |

C. 技术栈裁决
**明确选型：Vue3 + FastAPI**

*   **理由**：
    1.  **单人/6周约束**：Spring Boot 3.2 + MyBatis-Plus + JWT 等全家桶的配置和样板代码量极大；FastAPI 自带 OpenAPI 文档、类型校验，与前端 TS 契约无缝对接，开发效率高出一倍。
    2.  **协议适配优势**：JCROB Adapter 需要大量处理 HTTP/WS/UDP 异步并发，Python 的 `asyncio` 处理这类 I/O 密集型任务比 Java 轻量且直观。
    3.  **xlsx 解读**：客户给的 xlsx 往往是“通用平台模板”而非“硬性技术红线”。在没有强制要求 Java 中间件兼容的情况下，技术选型应服从交付周期。
*   **切换条件**：
    如果客户明确要求“系统必须接入其现有的 Java 微服务集群/必须使用 XXL-Job 调度体系/交付源码必须由 Java 团队后续维护”，则被迫切回 Spring Boot。
*   **6周风险**：
    前端组件量巨大，单人写 Vue3+FastAPI 最大的风险不是后端撑不住，而是前端写不完。必须大量使用 Arco Design Pro 的现成模板进行删减。

D. 模块取舍
在 JCROB 协议下，基于6周单人开发限制：

*   **P0 (必须做)**：首页驾驶舱(状态/地图/视频/环境)、巡检管理(仅任务下发与状态查看)、监控中心(单路视频+基础云台)、设备管理(仅机器人本身)、系统管理(基础RBAC)。
*   **P1 (尽力做)**：数据查询(裸数据表格式导出)、录像管理(仅截图留存，不做流录像)、开发中心(仅保留远程连接与日志查看)。
*   **P2 / 砍掉**：
    *   **人脸识别**：协议无此能力，砍。
    *   **AI盒子/点位AI识别结果**：无数据源，砍。
    *   **自动化规则引擎**：单人开发写规则引擎必死，改为写死几个触发条件（如电量低于20%自动召回）。
    *   **气象站/固定设备/分机**：脱离本次防爆机器人核心，砍。
    *   **15串BMS单体电压**：无接口，砍。
    *   **双摇杆遥控**：HTTP 轮询/WS 延迟无法支撑平滑双摇杆遥控，且防爆现场遥控需物理手柄，平台仅保留“方向步进控制”按钮。

E. 工程风险 Top 5

| 风险 | 触发条件 | 防护措施 |
| :--- | :--- | :--- |
| **1. 自动定位失败导致机器人迷路** | 视觉导航特征丢失，或下发任务时未给 `start_index` 且环境相似度高。 | 平台下发任务前必须检查 `galileo_status` 中的 `navStatus`，非定位成功状态拒绝下发。增加“心跳超时急停”机制。 |
| **2. 云台/车体控制指令阻塞** | HTTP 请求同步等待底盘响应，网络波动导致连接堆积，平台崩溃。 | JCROB Adapter 必须使用异步非阻塞请求，设置 500ms 超时，控制指令采用“发后即忘”或通过 WS 回读状态。 |
| **3. 坐标系换算错位** | Leaflet 原点在左上角，Y轴向下；JCROB 地图原点在左下角或中心，Y轴向上。换算错误导致机器人在地图上“乱飞”。 | 在 Adapter 层做绝对隔离，输出给前端的统一为标准 WGS84/局部像素坐标，由后端写死换算公式并进行打点测试。 |
| **4. 防爆合规越界** | 平台下发的任务导致机器人进入未测绘的危险区域，或环境数据超标仍继续巡检。 | 平台侧必须根据 WS 推送的 `lel` 等气体数据设置硬阻断：浓度超标立即调用 `/action` 暂停或返航。 |
| **5. 视频流无解** | 海康云台只给 RTSP，浏览器无法直接播放，强行引入 ZLMediaKit 导致部署复杂度暴增。 | MVP 阶段使用 `flv.js` +轻量级转流服务(如简单的 Node/Python RTSP 转 WS-FLV)，不上 ZLMediaKit 完整媒体服务器。 |

F. 6周单人 MVP 清单

**页面 (只做这5个)**：
1. **总览大屏**：单张静态/动态地图 + 机器人实时轨迹 + 1路视频 + 4个环境数据仪表盘。
2. **任务管理**：任务列表 + “新建任务”下拉框(选择预设巡航点/路线) + 实时状态表格。
3. **实时监控**：大视频画面 + 云台上下左右/缩放按钮 + 紧急停止按钮。
4. **告警查询**：时间轴 + 告警列表 (只做环境阈值越限和任务异常告警)。
5. **系统设置**：用户管理 + 机器人 IP/端口配置页。

**后端接口 (FastAPI)**：
1. `/api/v1/robot/status` (聚合底盘状态+环境数据，供前端轮询或WS转发)。
2. `/api/v1/robot/map` (获取并转码地图 PNG 及坐标参数)。
3. `/api/v1/task` (CRUD，下发到 JCROB `/task`)。
4. `/api/v1/video/live` (返回转流地址)。

**验收标准**：
能在 1080P 大屏上看到机器人在地图上移动，能看到实时视频，能点一个按钮让机器人去指定点并返回，环境超标有弹窗。其他全部砍掉。

G. 最值得质疑的 3 个假设

1.  **“xlsx 的技术栈和模块是硬指标”**：
    事实是，在工业现场，客户给的 xlsx 往往是销售拿着别家的方案抄来的，包含大量大而全的无效模块。如果你试图满足所有模块，12月绝对交不了。必须拉着客户确认“哪些是演示必须的”。
2.  **“告警由平台规则引擎推导”**：
    判断：过度设计。单人6周写不出可靠的规则引擎。防爆场景的告警（如可燃气体超标）直接硬编码 `if lel > threshold`，不要做可视化拖拽规则。
3.  **“平台不做 SLAM 解算，只做巡航编排”**：
    未验证。JCROB 的 `/navigation/loop_task` 在实际防爆现场（可能有动态障碍物、光线变化）的鲁棒性未知。如果底盘自身的巡航经常断链，平台再怎么编排也没用。必须第一天去现场跑 `loop_task`，验证其闭环成功率。

### 补充：对 UI/UX 及架构目录的审视

*   **UI 参考**：参考图通常是炫技的 3D 大屏，充满了无用的光效和图表。借鉴其配色（深色主题）和卡片布局即可。防爆控制台的核心是**状态一眼可见、急停一键可达**，不要把核心按钮藏在三级菜单里。
*   **Monorepo 目录**：对于单人6周，Monorepo 是灾难。不要分什么 `packages/adapter`、`packages/ui`、`apps/web`。直接一个前端仓库 + 一个后端仓库，扁平化到底，能跑就行，6周后交付了再去搞什么架构演进。
