# 多设备接入与隔离（为什么接一台测试狗不会影响主机型）

> 结论先行：**不会互相影响**。每台设备走独立的适配器、独立的缓存、独立的轮询任务；
> 测试设备默认停用，不参与默认轮询。下面写清楚边界，以及以后接更多型号时怎么做。

## 1. 现在的隔离方式（已实现，代码可查）

| 隔离维度 | 实现 | 位置 |
|---|---|---|
| 连接 | 每台设备一个适配器实例，自己持有 socket/HTTP client | `services/robot_runtime.py` |
| 数据 | 每台设备一份 `StateCache`，互不覆盖 | 同上 |
| 轮询 | 每台设备一个 asyncio 任务，某台卡住不影响别的 | 同上 |
| 告警 | 去重键带 `robot_id`，A 车离线不压 B 车 | `services/alarms.py` |
| 节奏 | 适配器可声明 `poll_interval`（X30 5s / JCROB 1s） | 适配器类属性 |
| 离线判定 | 适配器可声明 `offline_after_s`（X30 30s，避免慢响应误报） | 同上 |
| 启用 | `robot.is_active`，停用的设备不建轮询任务 | 启动时按台账筛选 |
| 配置 | 每台设备自己的 ip/port/adapter/mode | `robot` 表 |

实测（本机）：JCROB-01（mock）与 X30 Pro（真机）**同时在线**，
电量/位姿各自独立：78% Free / 100% 趴下，互不影响。

## 2. 测试设备怎么放（本次处理）

- X30 只作为**测试附属设备**：`is_active=0`（停用），默认不轮询；
- 要用时在「设备管理」里启用，或直接改台账；
- JCROB 主链路始终是默认设备（id=1），不受影响。

## 3. 以后再接新机型：三种模式，按规模选

### 模式 A：同进程适配器（现在这样，适合 1–5 台）

每台设备一个适配器类，平台进程内运行。优点是简单、延迟低；
缺点是某个厂商 SDK 崩了可能拖累进程（Python 层可 try/except，但 C 扩展崩溃挡不住）。

### 模式 B：独立驱动容器（适合 5–50 台、多厂商）

```
平台 (jc-server)  ←HTTP/WS→  驱动容器 A（JCROB）  →  机器人 A
                  ←HTTP/WS→  驱动容器 B（X30）    →  机器人 B
```

每个厂商一个容器，暴露统一的小接口（status / pose / dispatch / cancel），
平台只认这个接口。崩了只影响那一台，升级不用动平台。
业界做法参考：VDA 5050 的"车辆适配器"模式（[VDA 5050 教程](https://flowfuse.com/blog/2026/08/connect-agvs-vda-5050-mqtt/)）、
[MassRobotics AMR 互操作标准](https://embernet.ai/whitepapers/robots-that-take-instructions.pdf)（统一身份/位置/状态语义）。

### 模式 C：标准化协议接入（长期）

机器人/调度系统直接按 VDA 5050（MQTT）或 Open-RMF 上报，平台只做订阅。
适合客户现场本来就有车队调度系统的场景。

## 4. 现在这套离模式 B 有多远

平台的适配器接口已经收得很窄（`get_status/get_info/get_pose/get_galileo/dispatch/cancel`），
抽成独立 HTTP 服务大约 2–3 人天：把 `app/adapters/<vendor>/` 包一层 FastAPI 即可，
平台侧加一个 `RemoteAdapter` 指过去。**但这是二期的事**——一期只有 JCROB 一台。

## 5. 结论

- 接 X30 测试**不影响** JCROB 接入：代码隔离、配置隔离、默认停用；
- 12 月验收以 JCROB 为准，X30 只是验证"多设备并存"这个架构假设；
- 真要多机型规模化，走模式 B（驱动容器），不要在一个进程里堆厂商 SDK。
