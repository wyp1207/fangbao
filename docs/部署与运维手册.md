# 部署与运维手册（内网单机版）

> 目标：一台新机器 30 分钟内起服务；出问题 10 分钟内能定界；数据丢了能恢复。
> 适用：客户内网（无公网）、Linux 发行版（Ubuntu 20.04+ / CentOS 7+）。

---

## 1. 部署（Linux 一键）

```bash
sudo bash scripts/deploy.sh /opt/jc-robot 8099
```

脚本做 6 件事：检查 Python → 同步代码 → venv + 依赖 → `alembic upgrade head`
→ 建 systemd 服务（开机自启、崩溃重拉）→ 健康检查。

**前置条件**：Python 3.11+、能访问数据库（默认 SQLite，可改 `JC_DB_URL`）。

**验证**：

```bash
curl -s localhost:8099/health
systemctl status jc-robot
journalctl -u jc-robot -n 50
```

### 前端构建（如果部署静态前端）

```bash
cd web && npm ci && npm run build      # 产物 web/dist，交给 nginx 或后端静态托管
```

## 2. 配置（环境变量）

| 变量 | 默认 | 说明 |
|---|---|---|
| `JC_ENV` | dev | `prod` 时关文档、加安全头 |
| `JC_DB_URL` | sqlite:///server/data/app.db | 生产建议 MySQL |
| `JC_SECRET_KEY` | dev 占位 | **必须改**，否则 cookie/密码加密可被离线破解 |
| `JC_BIND` | 127.0.0.1:8000 | 监听地址 |
| `JC_DEVICE_AUTH_MODE` | warn | `strict` = 已签发凭证的设备必须带签名上报 |
| `security.idle_minutes` | 5 | 空闲自动退出（系统设置里改） |

## 3. 备份与恢复

```bash
# 每天备份（保留 14 份）
python scripts/backup_db.py backup --keep 14

# 查看
python scripts/backup_db.py list

# 恢复（会先自动备份当前库）
python scripts/backup_db.py restore server/data/backups/app-20261028-110123.db

# 恢复演练（还原到临时库并校验审计链，不动生产）
python scripts/restore_drill.py
```

**推荐 crontab**：

```cron
0 2 * * * cd /opt/jc-robot && .venv/bin/python scripts/backup_db.py backup --keep 14 >> data/logs/backup.log 2>&1
```

**RTO/RPO（当前实现）**：RPO = 24 小时（每日备份）；RTO ≈ 5 分钟（拷回 + 重启）。
如果客户要求 RPO < 1 小时，需要开启 WAL 归档或换 MySQL 做主从。

## 4. 设备接入凭证（一机一密）

1. 系统管理 → 设备接入凭证（或 `POST /api/v1/device-keys {"robot_id": 1}`）
2. **密钥只显示一次**，拷给设备端
3. 设备上报时带四个头：

```
X-Device-Key: dev_1_ab12cd34
X-Timestamp: 1793157347        # 秒级，±300 秒内有效
X-Nonce: 8f3a...              # 一次性随机串
X-Signature: hmac_sha256(secret, key_id\ntimestamp\nnonce\nsha256(body))
```

4. 设备端参考实现（Python 10 行）：

```python
import hmac, hashlib, time, uuid, json, requests
body = json.dumps(payload).encode()
ts, nonce = str(int(time.time())), uuid.uuid4().hex
msg = f"{key_id}\n{ts}\n{nonce}\n{hashlib.sha256(body).hexdigest()}"
sig = hmac.new(secret.encode(), msg.encode(), hashlib.sha256).hexdigest()
requests.post(url, data=body, headers={"X-Device-Key": key_id, "X-Timestamp": ts,
                                       "X-Nonce": nonce, "X-Signature": sig})
```

5. 切到强制模式：`JC_DEVICE_AUTH_MODE=strict`（已签发凭证的设备，无签名上报直接 401）
6. 轮换/吊销：管理页点「轮换」生成新 key（旧 key 立即失效）；设备侧换 key 后重启上报。

## 5. 日常巡检（每天 5 分钟）

| 看什么 | 在哪 | 异常处理 |
|---|---|---|
| 服务活着 | `systemctl status jc-robot` | 挂了看 `journalctl -u jc-robot -n 100` |
| 磁盘余量 | 系统状态页 / `/health` | <15% 时清理 `data/logs`、旧备份、旧录像 |
| 设备在线 | 系统状态页「设备运行时」 | 离线先 ping，再查端口（3546/30000） |
| 视频转码 | 系统状态页「视频转码」 | 没人看还占 CPU → 检查是否有僵尸 ffmpeg |
| 审计链 | 审计日志页「校验审计链」 | `ok=false` 记下 `broken_at`，用 `repair_audit_chain.py` 前先备份 |
| 备份是否成功 | `data/logs/backup.log` | 连续失败查磁盘/权限 |

## 6. 故障定界（三步）

1. **看 request_id**：每个响应带 `X-Request-Id`，日志里 `rid=xxx` 能串起一次请求。
2. **分层判断**：
   - 平台 5xx → 看后端日志堆栈
   - 平台 4xx（`DEVICE_SIGNATURE`/`NOT_LOCALIZED`/`RUN_BUSY`）→ 按提示处理，不是故障
   - 设备超时 → `ping` + `telnet ip port`，再判断是网络还是设备
3. **一键复跑**：

```bash
python scripts/integration_suite.py     # 24 项联调
python scripts/ui_smoke.py              # 34 路由冒烟
python scripts/adversarial_test.py      # 越权 + 审计链
```

## 7. 升级与回滚

```bash
# 升级
git pull && sudo bash scripts/deploy.sh /opt/jc-robot 8099

# 回滚（代码）
git checkout <上一个 tag> && sudo bash scripts/deploy.sh /opt/jc-robot 8099

# 回滚（数据库）：迁移未做 downgrade 的，用备份恢复
python scripts/backup_db.py restore data/backups/app-<升级前>.db
```

**注意**：当前是单机单进程，升级会中断服务约 10–20 秒。客户要求零中断需上多实例 + 负载均衡（未实现）。

## 8. 已知限制（写进验收材料，别隐瞒）

| 项 | 现状 | 影响 |
|---|---|---|
| 单 uvicorn worker | 无水平扩展 | 一台机器扛全部设备；CPU 密集（转码）会拖慢接口 |
| 无 MQ | 上报直接写库 | 高频上报时数据库压力大，无削峰 |
| SQLite 默认 | 并发写有锁竞争 | 多设备高频写建议换 MySQL |
| 无容器化 | systemd 裸机部署 | 环境差异需人工处理 |
| 无短信/电话 | 有企微/钉钉/webhook/邮件 | 夜间无人盯屏时触达不够 |
| 单地图 | 不支持跨区域 | 多厂区/多楼层需扩展 |
| 真机未验 | X30/JCROB 现场未通 | 协议假设未证实 |
