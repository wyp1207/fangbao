# 二、首页地图“建模”方案

## 结论先行

**不建议在本期做完整 Three.js / BIM / 真三维建模。**  
当前只有 2D SLAM PNG、点位、实时位姿，真机到场晚，单开发者交付窗口只有约 1 个月。最优路线是：

> **先把 2D 地图产品化、大屏化、动态化：深色风格 + 发光路径 + 实时位姿 + 轨迹 + 点位状态 + 视频/告警联动。**

视觉提升能达到领导感知的 **70%–80%**，成本只有完整 3D 的 **10%–20%**。

---

## 方案排序

### 1. 深色科技风 2D 地图重绘

**优先级：最高，必须做。**

- **需要数据**
  - SLAM PNG / 瓦片；
  - 地图分辨率、原点、占用阈值，若元数据不全，可先前端配置缩放和原点；
  - nav_points；
  - 实时 `x/y/angle`；
  - 导航状态、当前任务、告警状态。
- **机器人侧改动**
  - 不需要。
- **前端工作量**
  - 2–3 人日。
- **做法**
  - 原始灰图放到 Canvas；
  - 像素后处理：未知区压黑、可通行区深蓝、障碍物青色/白色描边；
  - 叠加 CSS/Canvas 发光网格、扫描线、雷达扇形光圈；
  - 机器人图标按 `angle` 旋转；
  - 点位用不同状态色：待巡检、当前点、异常点、普通点。
- **风险**
  - 低。
  - 主要风险是地图坐标和像素比例不准，但不影响视觉验收；真机到场后校准。
- **投入产出**
  - 极高。单靠这一项就能明显摆脱“灰色迷宫”。

---

### 2. Canvas 动态实时态势层

**优先级：高，建议做。**

- **需要数据**
  - WebSocket 实时位姿；
  - 当前任务；
  - 动作序列或当前目标点；
  - 告警状态；
  - 前端短时缓存轨迹，不依赖历史库。
- **机器人侧改动**
  - 不需要。
- **前端工作量**
  - 2–4 人日。
- **做法**
  - 机器人移动时保留最近 50–200 个位姿点，形成发光拖尾；
  - 当前目标点高亮；
  - 低电量、急停、通信中断时机器人外圈变红/闪烁；
  - 地图边缘加雷达扫描、呼吸光圈；
  - 点击机器人弹出状态卡片：电量、速度、电压、任务、通信。
- **风险**
  - 低到中。
  - 位姿抖动会导致轨迹难看，需要做抽稀、死区过滤、角度平滑。
- **投入产出**
  - 很高。领导最容易感知“活起来了”。

---

### 3. 基于 PNG 的伪 2.5D 立体地图

**优先级：中，作为领导演示增强项。**

- **需要数据**
  - 与 2D 相同：PNG、点位、位姿；
  - 最好有地图元数据；
  - 不需要建筑层高和设备模型。
- **机器人侧改动**
  - 不需要。
- **前端工作量**
  - 4–7 人日。
- **做法有两种：**
  1. **CSS/Canvas 2.5D**
     - 地图倾斜；
     - 障碍物做阴影、厚度；
     - 点位和机器人做悬浮标签；
     - 成本低，推荐。
  2. **Three.js 平面挤出**
     - 把占用栅格中的障碍物像素转成平面块，挤出 0.2–1 米高度；
     - 机器人用锥体/圆柱体表示；
     - 地面使用深色网格材质。
- **风险**
  - PNG 栅格噪声会导致挤出很多碎块；
  - 坐标、分辨率、原点不准则空间感失真；
  - 大面积障碍物挤出可能有性能问题，需要降采样。
- **投入产出**
  - 中等。视觉有提升，但不适合作为本期主交付依赖。

---

### 4. 巡检点位和视频/告警联动图层

**优先级：高，业务价值比纯炫技更强。**

- **需要数据**
  - nav_points；
  - 摄像头列表及流名；
  - 点位与摄像头的手工绑定关系；
  - 告警记录；
  - 当前任务动作序列。
- **机器人侧改动**
  - 不需要。
- **前端工作量**
  - 3–5 人日。
- **做法**
  - 地图上显示巡检点、摄像头图标、告警点；
  - 点击摄像头弹出 MSE 小窗；
  - 当前任务点按执行进度连线；
  - 告警自动定位到地图位置。若告警没有坐标，则定位到机器人当前位置或关联点位；
  - 右侧显示“当前点、下一地点、最近告警、关联视频”。
- **风险**
  - 中。
  - 点位和摄像头的空间绑定需要现场整理一张配置表；
  - 告警目前不一定带坐标，不能承诺精确告警定位。
- **投入产出**
  - 高。它让地图从“背景图”变成“业务入口”。

### 5. Three.js 最小 3D 数字孪生

**优先级：低，只作为有余力的演示版，不进验收主线。**

- **需要数据**
  - 2D 栅格图；
  - 地图分辨率、原点；
  - 点位坐标；
  - 实时位姿；
  - 可选：墙体/区域手工标注 JSON。
- **机器人侧改动**
  - 基础版不需要。
- **前端工作量**
  - 8–12 人日。
- **最小可行版本**
  - 不建工厂 BIM，不建精细机器人模型；
  - Three.js 创建深色地面；
  - SLAM 障碍物降采样后挤出低矮墙体；
  - 巡检点用发光柱；
  - 机器人用圆锥/圆柱 + 方向箭头；
  - WebSocket 驱动模型移动；
  - 固定 45° 俯视角，不做自由漫游；
  - 保留一键切回 2D。
- **风险**
  - 中到高：
    - 栅格转 3D 容易变成“立体迷宫”，不一定更专业；
    - 缺少真实墙线、设备模型、楼层信息；
    - 单开发者调试相机、坐标、性能会吞时间；
    - 真机到场前无法确认真实坐标效果。
- **投入产出**
  - 低到中。适合演示，不适合作为核心验收能力。

- 不做 BIM；

### 第二部分：首页地图"建模"问题

**1. 可落地呈现方案（按投入产出比排序）**

*   **方案A：2.5D 伪3D叠加（Canvas/SVG遮罩）**
    *   **数据**：现有2D栅格图、nav_points坐标、实时位姿。
    *   **改机器人**：不需要。
    *   **工作量**：2 人日。
    *   **风险**：极低。纯前端处理，将灰色PNG转为半透明底图，上层用SVG绘制科技感发光线条连接巡检点，点位用动态呼吸光圈，机器人加方向指示箭头和拖影。
*   **方案B：科技感 UI 框架与动效包装**
    *   **数据**：不需要额外地图数据，利用现有业务数据。
    *   **改机器人**：不需要。
    *   **工作量**：1.5 人日。
    *   **风险**：极低。地图周边用深色毛玻璃面板、霓虹边框包裹，增加扫描线特效、数据滚动动效，通过 UI 组件库（如 DataV）快速提升整体科技感，掩盖单张灰图的简陋。
*   **方案C：轨迹残影与扫描雷达特效**
    *   **数据**：历史位姿记录。
    *   **改机器人**：不需要。
    *   **工作量**：1 人日。
    *   **风险**：低。在机器人当前位置画一个半透明扇形雷达扫描波纹，记录最近100个位姿点画成渐变消失的尾迹，让静态地图产生动态行进感。
*   **方案D：三维点云投影（伪3D俯视倾斜视角）**
    *   **数据**：机器人 SLAM 构建的 2D 栅格图 + 高度信息（若有）。
    *   **改机器人**：可能需要机器人开放地图高程数据接口。
    *   **工作量**：4 人日。
    *   **风险**：中。需处理数据坐标转换，且如果机器人侧拿不到高程数据就是伪需求。
*   **方案E：全景图(Panorama)贴图置换**
    *   **数据**：厂区 CAD/PDF 设计图。
    *   **改机器人**：不需要。
    *   **工作量**：3 人日。
    *   **风险**：低。用客户厂区的平面图作为底图，将栅格图透明度降至20%仅用于坐标对齐，前端需要做一次图纸坐标与机器人坐标的手动仿射变换标定。

**2. 要不要上 Three.js / 3D 建模？**
**明确结论：不要上。**
*   **原因**：单开发者1个月交付周期，引入 Three.js 意味着需要处理 3D 场景构建、相机控制、模型加载、UV 贴图和性能优化，至少耗费 7-10 人日，且真机未到现场前无法调试坐标对齐，风险不可控。
*   **不上会失去什么**：失去“上帝视角”的立体空间感（如管道高低落差、多层厂房楼层切换）。对于单台轮式机器人平面巡检，2.5D 方案完全能满足视觉和功能需求。

**3. 真实产品/开源项目参考**
*   **参考1：Rviz (ROS Visualization)**
    *   怎么做的：它的 2D 导航视图 (`Map` 显示 + `Path` 显示) 就是直接渲染栅格图，但把可行走区域用半透明绿色覆盖，用发光的红色线条画全局规划路径，用蓝色箭头表示机器人位姿，极其直观。
*   **参考2：海康威视机器人调度平台 (ARTEMIS)**
    *   怎么做的：支持 2D/3D 视角切换，但其 2D 视角就是典型的 2.5D 做法，地图灰度化处理，重点强化了 AGV 模型图标、充电桩图标、货位点位的拟物化设计，通过 UI 动效拉升科技感。
*   **参考3：DataV (阿里云数据可视化)**
    *   怎么做的：不纠结底图本身，利用深色科技风边框、飞线图、轮播列表等组件，把一张普通的平面图“包裹”成指挥中心大屏。

### 第三部分：给单开发者的砍单建议

1个月单人交付，且真机11月才到，**必须砍掉以下内容**：

1.  **砍：历史轨迹回放 (M07-F04)**
    *   失去：复盘机器人过去行进路线的能力。原因：需要落库大量高频 pose 数据，且前端播放器调试耗时，验收时看实时轨迹即可。
2.  **砍：录像管理与回放 (M10-F01/F02)**
    *   失去：事后查录像追溯功能。原因：go2rtc 录像配置和存储策略验证极耗时，保留占位页，直接让客户用海康自带的 NVR 客户端看录像。
3.  **砍：环境数据展示 (M12-F01)**
    *   失去：温湿度/气体监测展示。原因：传感器设备未定，无数据源，做了也是假数据，浪费前端工期。
4.  **砍：go2rtc 流注册页面 (M11-F04)**
    *   失去：页面端动态增删视频流的能力。原因：真机未到，接口联调不通。直接在配置文件中写死预置的 15 路海康相机流，降低调试风险。
5.  **砍：复杂的角色权限树 (M11-F02)**
    *   失去：细粒度的按钮级权限控制。原因：单人开发精力有限，改为硬编码三个角色（管理员看所有、操作员看监控和任务、只读看大屏），不做动态权限树分配功能。
