> 依据：`docs/reviews/cruise-multi-robot-benchmark.md`（对标 Open-RMF / VDA5050 / Nav2 / 巡检开源 / 商用）、
> `docs/reviews/model_review_20261027-173507.md`（豆包 + GLM 对草稿的逐条挑错）、
> 以及本仓库现有代码（行号见下）。
>
> 结论先行：**草稿里 6 条有 4 条会被批倒，改为下面的 4 项**。不是缩水，是删掉伪需求。

## 0. 一页纸结论

| 原草稿 | 结论 | 改成 |
|---|---|---|
| P0-1 订单幂等：`order_key = run-{id}-a{n}`，下发后写 external_id | ❌ 并发下防不住；崩溃后不知道车端收没收到 | **先落库再发**：`dispatch_state=pending` + `order_key` 唯一索引，发完置 sent，车端回报置 acked |
| P0-2 `exec_mode = order / waypoint` 二值 | ❌ 混淆"下发粒度"与"控制权"；JCROB 整单模式下到点动作无处安放 | **能力字典**：`supports_batch / supports_inline_actions / supports_pause / cancel_semantics`，缺省全部按逐点 |
| P0-3 七态状态机 | ❌ `accepted` 在单 worker 无 MQ 下不可观测；`paused` 是平行态不是后继态 | **主状态仍是 5 个**，新增 `dispatch_state` 字段与 `cancel_requested` 标志；另建 append-only `task_event` |
| P0-4 到点三值判定（FINISHED + 距离 + 速度） | ⚠️ 方向对，但"速度<0.05"在机器狗上会误判（原地踏步/踏步过坎） | **以底盘原生结果码为准**（1007 Status / HTTP state），距离只做二次复核；三值保留但 `suspect` 不重试 |
| P1-5 资源锁（DB 行锁 + 字典序 + TTL 60s） | ⚠️ 单 worker 下 DB 行锁是过度设计，TTL 60s 可能被误拆 | **进程内锁（asyncio.Lock + key 表）**，DB 只存"占用快照"供展示；TTL 按任务最长点间时间设 |
| P1-6 定位触发（含 odom 位移 > 5m 判被搬动） | ❌ 腿式 odom 漂移大，会误触发 | **只看底盘 `/location_status` 与启动首连**，不看 odom |

## 1. 设计原则（ponytail：先爬梯子再写）

对每一处改动都过了一遍"能不能不做 / 能不能复用"：

| 梯子 | 本次结论 |
|---|---|
| 1. 需要建吗（YAGNI） | 七态状态机、Redis 分布式锁、VDA5050 全量字段、RMF 协商 → **不做** |
| 2. 仓库里已有吗 | `TaskRun.external_id`、`assert_free`、`audit`、`sensor_io`、`task_lock` 全部复用 |
| 3. 标准库能做吗 | 进程内锁用 `asyncio.Lock`；幂等用 `uuid4`/`time_ns`；不用新依赖 |
| 4. 平台特性 | MySQL 唯一索引/`INSERT ... ON DUPLICATE`；SQLite `BEGIN IMMEDIATE` 都不用专门库 |
| 5. 已装依赖 | SQLAlchemy 2.0、Alembic 已装，无需新增 |
| 6. 能一行吗 | `order_key = f"{run.id}-{attempt}"` 一行；不引入 UUID 表 |
| 7. 才写最小实现 | 见 §2，每项都限定文件与函数 |

**结论：需要 ponytail，而且它就是"砍掉 4 条中的 4 条伪需求"的依据。**
不需要新依赖、不需要新服务、不引入消息队列。

## 2. 四项改动（按实施顺序）

### 改动 A：下发幂等（先落库，再发网络）

**问题**
- `orderId = JC-{毫秒}`（`task_dispatch.py:123`）每次调用都变，重发 = 新建车端任务。
- 现在先查 `external_id` 再发，中间有 await 窗口，双击/超时重试/定时任务三路并发都能穿过去。
- 下发成功但进程崩了，`external_id` 为空，重启后不知道该不该补发。

**方案**（VDA5050 的 `orderId + orderUpdateId` 思路的极简版）

新增列（Alembic `0024`，都带默认值，可回滚）：

| 列 | 类型 | 说明 |
|---|---|---|
| `order_key` | String(64), **unique**, nullable | `f"{id}-{attempt}"`，同一 run 的同一尝试唯一 |
| `attempt` | Integer, default 1 | 第几次下发（重发 +1） |
| `dispatch_state` | String(12), default `pending` | `pending / sent / acked / failed` |
| `cancel_requested` | Boolean, default false | 取消已发、未确认 |

写入时序（关键）：

```
1) INSERT/UPSERT TaskRun(order_key=..., attempt=n, dispatch_state='pending')，提交
2) 调适配器下发（网络）
3a) 成功 → dispatch_state='sent'，external_id=车端 id，提交
3b) 超时/异常 → 保持 pending，**不重发**，交给"对账"处理
4) 车端首次回报 → dispatch_state='acked'，主状态 running
```

**对账**（代替盲重试）：启动时 + 每 60 秒扫 `dispatch_state='pending'` 且超过 2 分钟的行：
查车端当前任务列表（`get_order`/`/task`），有对应订单 → 补 `sent`；没有 → 标 `failed` 让人决定。
这是唯一能解"unknown commit"的办法，VDA5050 靠 `orderUpdateId`，我们靠对账。

**并发防重**：靠 `order_key` 唯一索引（数据库层），不再靠"先查再写"。
MySQL 用 `INSERT ... ON DUPLICATE KEY UPDATE`，SQLite 用 `INSERT OR IGNORE`，SQLAlchemy 里用 `session.merge` + 捕获 IntegrityError。

**验收**
- 同一个 run 连发两次 → 第二次 409 `ORDER_IN_FLIGHT`（或返回同一 external_id），车端只有一条任务。
- 下发中途 kill -9 → 重启后对账把 pending 修正为 sent/failed，不会双发。
- 测试：`test_dispatch_idempotent`（并发两次调用只产生一条 pending/sent）。

**替代方案对比**

| 方案 | 为什么不选 |
|---|---|
| Redis 分布式锁 | 单 worker 用不上；多一个组件要运维 |
| 只加 `external_id` 唯一索引 | 崩溃后 external_id 为空，唯一索引也防不住补发 |
| 消息队列 outbox（Kafka/Rabbit） | 规模不到，运维成本 > 收益；用 DB 行做 outbox 已够 |

### 改动 B：能力协商（替掉 `exec_mode` 二值）

**问题**：草稿把"整单/逐点"当成一个开关，实际上它至少是四个正交能力；
而且整单模式下"到点拍照/测温"插在哪，JCROB 协议没确认（真机未到），现在写 `order` 分支就是废代码。

**方案**：适配器上加能力字典（缺省全 False = 逐点，行为与今天完全一致，零风险上线）

```python
class HttpJcrobAdapter:
    capabilities = {
        "supports_batch": False,          # 能否一次收多节点
        "supports_inline_actions": False, # 能否在节点间执行平台动作（拍照/测温）
        "supports_pause": False,          # 暂停/继续
        "cancel_semantics": "async",      # async=发完不一定停；sync=调用返回即停
    }
```

平台侧只读能力，不判断厂商：
- `supports_batch and supports_inline_actions` → 整单下发；
- 否则逐点（今天的行为）。

**为什么这样改**：把"厂商差异"关在适配器里，巡航逻辑不出现 `if 厂商 ==`；
真机联调确认 JCROB 支持节点动作后，只改适配器一个布尔值。

**验收**
- 现有两台设备行为不变（都是逐点）；
- 单元测试：能力字典全 False 时走逐点；全 True 时走整单分支（mock 适配器）。

### 改动 C：到点判定改"结果码优先 + 距离复核 + 三值"

**问题**
- 现在只看 `FINISHED` + 距离 ≤ 1m（`cruise.py:257`），超容差直接 `failed` → 把"该重定位"误报成"任务失败"并盲重试。
- 只看速度会误判：机器狗原地踏步/过坎时速度 > 0.05 m/s，但已经到了。

**方案**

```
判定输入：
  nav_result = 1007 Status（0 成功 / 1 进行 / -1 失败 …）
  pose_dist  = 当前坐标与目标点距离
  dwell      = 连续 N 秒 |Δpos| < 0.05m（位移不再增长，而不是瞬时速度）

判定：
  nav_result 成功 且 pose_dist ≤ 1.0m 且 dwell ≥ 2s      → arrived
  nav_result 成功 且 1.0m < pose_dist ≤ 2.5m             → arrived_suspect（不重试，提示重定位）
  nav_result 失败 / 超时 / pose_dist > 2.5m              → failed
  其它（进行中）                                          → 继续等
```

**`arrived_suspect` 的处置**：把 step 状态记 `suspect`，产生一条 P3 告警"疑似定位漂移"，
**不重启任务、不重试该点**，由人决定是否重置定位后重跑该点（`/task-runs/{id}/steps/{seq}/retry` 已有）。

**先决条件（真机确认，否则不改代码）**：1007 的 Status 枚举要拉全 —— 成功/失败/取消/手动接管/急停/规划失败
各是什么码。这份清单在 `docs/真机取数清单.md` 里补一行，联调第一天就测。

**验收**
- 模拟：距离 1.3m + 成功 → `arrived_suspect`，无重试、无 failed；
- 模拟：距离 3m + 成功 → `failed`；
- 机器狗原地踏步（速度 > 0.05，位移 < 0.05）→ 仍判 `arrived`（用位移不用速度）。

### 改动 D：资源锁 + 定位触发（最小版）

**D1 资源锁**：单 worker 先用进程内锁，DB 只做展示与重启后恢复。

```python
# services/resource_lock.py（约 60 行）
_lock: dict[str, asyncio.Lock] = {}
_holder: dict[str, dict] = {}          # key -> {run_id, robot_id, until}

async def acquire(keys: list[str], run_id: int, robot_id: int, ttl_s: int) -> bool:
    keys = sorted(set(keys))           # 字典序：消灭环路等待
    # 逐个 try-acquire，失败则释放已拿到的
```

| 方案 | 适用 | 我们选吗 |
|---|---|---|
| 进程内 `asyncio.Lock` + 有序 key | 单 worker（现状） | ✅ 选它，零依赖 |
| DB 行锁 / `SELECT FOR UPDATE` | 多进程、多实例 | ❌ 现在不需要；升级路径写在注释里 |
| Redis 分布式锁 | 多实例 + 跨机房 | ❌ 引入新组件，YAGNI |

资源粒度只做三类：`point:<id>`（窄道口/门口点位）、`charger:<id>`、`zone:<name>`。
TTL 取"该资源最长占用时间"（点位 10 分钟、充电桩 2 小时），到期只告警不自动释放（自动释放会撞车）。

**D2 定位触发**：只看底盘信号，**不看 odom**（腿式里程计漂移大，GLM 说得对）

| 触发条件 | 动作 |
|---|---|
| 设备开机后首次连上 | 提示"需要确认定位"（横幅，不自动发） |
| `located == false` 持续 10 秒 | P2 告警 `loc_lost` + 横幅"定位丢失，请重置定位" |
| 切换地图（暂无此功能） | 预留 |
| 重置定位后 3 秒 | 读回 pose 校验：`located==true` 且与目标误差 < 0.5m，否则提示"重置未生效" |

**明确不做**：自动重定位。机器狗在楼梯/斜坡上被自动重定位会姿态崩溃——只提示、由人确认。

**验收**
- 抹掉 `located` 字段 → 10 秒内出 `loc_lost` 告警；
- 重置定位成功 → 3 秒内校验通过；故意给错坐标 → 提示"与期望差 X 米"。

## 3. 明确不做（及理由）

| 不做 | 理由 |
|---|---|
| VDA5050 全量（节点/边/base-horizon） | 我们的车不跑路网，没有"边"的概念；只借 `orderId+updateId` 的幂等思想 |
| Open-RMF 交通协商 | 需要车端支持暂停/改道/让行，X30 与 JCROB 都没有；强行做只能靠"锁" |
| 七态/八态状态机 | 单 worker 下 `accepted` 不可观测；`paused` 是平行态；用字段而非状态解决 |
| Redis / MQ | 单机部署、一台车，YAGNI；升级路径写在代码注释 |
| 自动重定位 | 腿式机器人风险 > 收益；只提示 |
| 点位绑地图版本 | 等"多地图"真上线再说（当前只有 1 张图） |

## 8. 调研落地后的修正（覆盖 §2 的细节）

两份调研（`docs/reviews/idempotency-state-machine-research.md`、`multi-robot-localization-research.md`）
读了 VDA5050 / Open-RMF / Nav2 / slam_toolbox 源码后，有 6 处要按实际实现改：

### 8.1 幂等字段：按 VDA5050 的 `(orderId, orderUpdateId)` 对齐

| 字段 | 类型 | 说明 |
|---|---|---|
| `order_id` | String(64) **unique** | `JC-R{run_id:06d}-A{attempt:02d}`，可读、可对账 |
| `order_update_id` | Integer default 0 | 改单才 +1；本期恒 0（我们不改已下发订单） |
| `dispatch_state` | String(16) default pending | `pending/sending/sent/acked/rejected/unknown` |
| `dispatch_attempt` | Integer default 0 | 旧单终态后才 +1 |
| `dispatch_lease_until` | DateTime null | 发到一半进程崩了的租约（对账用） |
| `cancel_requested_at` | DateTime null | 取消已发、车端未确认 |
| `last_seq` | Integer default 0 | 断点续跑锚 |

**关键实现点（调研结论）**：
- VDA5050 **没有** order 级 status；"还在跑"由 nodeStates/actionStates/paused 共同表达 → 我们不扩主状态是对的。
- 幂等靠**数据库唯一索引 + 条件 UPDATE**，不靠"先查再写"。
- `SELECT ... FOR UPDATE` 在 SQLite 下**直接语法报错**；条件 `UPDATE ... WHERE dispatch_state='pending'` + `rowcount` 在 SQLite/MySQL 语义一致 → 统一用条件 UPDATE。

### 8.2 到点判定：借 VDA5050 的 `allowedDeviationXY`

VDA5050 把容差放在**每个节点**上（`node.allowedDeviationXY`），不是全局一个值。
我们已有 `PointDraft.arrive_radius_m`（默认 1.0），正好对应；只需把判定顺序改成：

```
1) nodeStates/actionStates 的 REACHED/FAILED（车端原生结果，最高优先）
2) 距离 ≤ arrive_radius_m（该点自己的容差）
3) 位移 2 秒内不再增长（dwell，用位移不用瞬时速度——机器狗踏步时速度不为 0）
→ arrived / arrived_suspect / failed
```

### 8.3 定位：三个必须改的细节（都不在草稿里）

1. **下发前加"定位就绪"安全门**：VDA5050 原文规定 `localized=false` 必须报 `LOCALIZATION_ERROR` 且**禁止继续驾驶**。
   我们照做：`located != True` 时下发直接 409 `NOT_LOCALIZED`，而不是让车"带着错位姿跑"。
2. **`localizationScore` 不能当安全判据**（规范原文"仅用于日志和可视化"）→ 我们只用布尔 `located`，不引入分数阈值。
3. **重置定位的 ROS 细节**（将来接 `/initialpose` 时）：
   - `header.stamp` 必须是 **now**，早于 now 会让 AMCL 把 odom 增量乘上去；
   - covariance 用 `diag(0.25, 0.25, 0, 0, 0, 0.0685)`（±0.5m / ±15%），AMCL 只读对角 4 个分量；
   - 校验用 `/request_nomotion_update` —— **不用动车**就能验证位姿是否收敛。

### 8.4 资源锁：改条件 UPDATE（不是行锁）

调研给了硬证据：SQLite 不支持 `FOR UPDATE`；`MySQL GET_LOCK` 不随事务释放、连接池会坑；Redlock 无 fencing token。
单 worker 下最优解是 **进程内 `asyncio.Lock`（主）+ 条件 UPDATE 的 DB 行（观测/重启恢复）**：

```sql
-- 抢锁（SQLite/MySQL 通用）
UPDATE resource_lock
   SET run_id=:run, robot_id=:robot, acquired_at=:now, expires_at=:exp
 WHERE key=:key AND (run_id IS NULL OR expires_at < :now);
-- rowcount=1 → 拿到；0 → 被占
```

按 key 字典序逐个抢，失败回滚已抢的；TTL 90 秒 + 15 秒心跳续租；过期只告警、**不自动释放**。

### 8.5 换图/重定位的真实时序（当前不做，但写进手册避免踩坑）

调研核实：`/map_server/load_map` 只在节点 ACTIVE 时生效，且换图后 AMCL **不清粒子、不清 `initial_pose_is_known_`**。
所以换图的正确顺序是：`load_map` → `reinitialize_global_localization` → `/initialpose`(stamp=now) → `/request_nomotion_update` 校验。
我们目前只有一张图，这条先不实现，写进"多地图上线前必读"。

### 8.6 slam_toolbox 的两个常见误解（避免照抄错方案）

- **没有** `/slam_toolbox/set_pose` 这个服务；重定位是 localization 模式下的 `/initialpose`，或 `deserialize_map` 的 `LOCALIZE_AT_POSE`。
- slam_toolbox（humble）是普通 `rclcpp::Node`，**不是** lifecycle 节点；没有 configure/activate 门。
