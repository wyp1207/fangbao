## 0. 结论先行

**不做"场站白模"，做"数据驱动的程序化 3D"。**

- **A 方案（地图驱动）先上**：把已有的 SLAM 栅格地图当底座拉成 3D，机器人位姿/点位/告警/轨迹全部真数据驱动。
- **B 方案（GLB 白模）后补**：客户能提供 CAD/Blender 模型时再导入，用 3–4 点标定对齐；业务对象不动。
- **C（Astral3D）不采用**：它是 BIM 轻量化框架，吃 IFC/CAD 源数据，我们没有源数据，二次开发成本高于自研。
- **D（继续 2D）放弃**：领导已经看过参考图，回不去了。

一句话卖点，汇报时这么说：

> "参考图是**静态渲染图**；我们做的是**实时数字孪生**——大屏上的机器人、告警、轨迹全是真机数据驱动的，不是贴片动画。"

## 2. 坐标对齐（这是所有孪生项目的真难点）

### 2.1 A 方案为什么天然对齐

平台里所有东西本来就在同一个 **SLAM 米制坐标系**：地图元数据（origin、resolution）、点位 (x,y,θ)、机器人位姿、告警位置。3D 里直接：

```
three.x = x
three.y = 0            // 地面
three.z = y            // SLAM 的 y → three 的 z
robot.rotation.y = -theta   // 符号要实测（我们已按 -theta 实现）
```

像素 → 米（建墙时）：

```
x = origin_x + (col + 0.5) * resolution
y = origin_y + (img_h - row - 0.5) * resolution    // ← 行号必须翻转
```

### 2.2 必须知道的 5 个坑（我们踩过/防过）

1. **PNG 行号向下、SLAM y 向上**：不翻转，整个墙体和点位错位。
2. **像素中心偏移**：用 `col+0.5 / row+0.5`，否则差半像素（0.025m）。
3. **origin 定义**：ROS 的 origin 是地图左下角像素中心；不同厂商工具可能不同，接口里读，不要硬编码。
4. **theta 符号**：Three.js 的 Y 轴旋转与 ROS yaw 方向相反，用 `-theta` 并在页面上实测。
5. **resolution 不要写死**：从 `/maps/library` 返回里取（我们的 demo 是 0.05m/px，别的地图可能 0.1）。

### 2.3 B 方案（将来导入 GLB）的标定

用 **Kabsch + 各向同性缩放**：3 对同名点求 R、s、t，第 4 对验证；残差 > 0.2m 标红，> 0.1m 不允许保存。
UI 左侧 2D 地图点 3 个、右侧 3D 模型点 3 个，实时显示每对点误差；导出 `transform.json`。

## 6. 验收指标（可写进合同，避免"像不像"扯皮）

| 指标 | 值 | 怎么测 |
|---|---|---|
| 帧率 | ≥30fps（核显）/ ≥60fps（独显） | 页面 HUD 的 FPS |
| 位姿端到端延迟 | <300ms | 机器人动 → 大屏动，录屏逐帧 |
| 点位显示误差 | <0.05m（1 像素） | 与 2D 地图同名点对比 |
| 告警上屏 | <1s | 造一条告警 → 3D 出现光柱 |
| 轨迹回放 | 24h，拖动响应 <500ms | 回放页 |
| 同时在线机器人 | ≥2 | 多机时 |

**不要写**"和参考图相似度"——主观指标一定扯皮。

| 客户/领导会问 | 怎么答 |

| "不像我们场站" | "这是**底图+坐标**，白模下阶段按实场叠；现在机器人位置是准的，先保证'准'再追求'像'。" |

| "和参考图差远了" | 第一屏就并排对比，不回避；然后演示**动态**：参考图是死的，我们是活的。 |

## 8. 产品视角：这事的真正价值

1. **不是"多一个炫酷页面"，是把"数据是否可信"可视化**：位姿、点位、告警、轨迹全在一个空间里，客户一眼能看出"车到底在哪、告警在哪"。
2. **边际成本为零**：换场站只换地图，不换代码、不请建模师——这是能复制的产品能力，不是一次性项目交付。
3. **为二期铺路**：GLB 白模、视频融合、多机、路径规划可视化都挂在这套坐标系上，不用推翻重来。
