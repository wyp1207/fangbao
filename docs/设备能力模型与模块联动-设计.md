# 场站 · 设备 · 外设 · 能力：数据模型与模块联动（设计定稿）

> 结论先说：**不要按"设备型号"写页面，要按"这台设备实际挂了什么外设"渲染面板。**
> 事实来源是"外设实例表"，能力由外设派生，型号模板只做初始化的默认值。
> 依据：豆包/GLM 评审 + [Home Assistant Device/Entity Registry](https://developers.home-assistant.io/docs/device_registry_index/)、
> [ThingsBoard Device Profile](https://thingsboard.io/docs/user-guide/device-profiles/)、
> [AAS 资产管理员外壳](https://industrialdigitaltwin.org/)、[Open-RMF Adapter](https://openrmf.readthedocs.io/)。

## 1. 五层概念（从上到下）

```
场站 Station          "实验室" / "泰安厂区-1F"
  └─ 设备 Device      一台机器人（绝影 X30 Pro / JCROB-01 / 未来的轨道机）
       └─ 外设 Peripheral   实际挂上去的硬件：云台相机、热像仪、SF6、噪声、粉尘…
            └─ 能力 Capability  由外设类型派生：video.live / ptz.move / env.sf6 / posture.stand…
                 └─ 面板 Panel     一个能力或一组能力对应一个 UI 组件
```

**关键决定**：
- `Peripheral` 是**唯一事实来源**（现场装了什么就有什么）；
- `Capability` **派生**，不允许手填当事实（可 `enabled=false` 人工禁用）；
- `Profile`（型号模板）只是"新建设备时的默认外设清单"，**不是运行时配置**；
- 面板由能力集合决定，**新增外设不改主页面**。

## 2. 数据模型（最小可用）

```sql
-- 外设实例（核心表，把现在的 sensor / video_source 收口到一起）
peripheral (
  id            PK
  robot_id      FK -> robot.id          -- 属于哪台设备
  kind          varchar                 -- camera / thermal / ptz / gas / env / noise / dust / speaker
  vendor        varchar                 -- hikvision / dahua / deeprobotics / 国产某某
  model         varchar                 -- 型号（可空）
  channel       varchar                 -- 云台通道号 CH101/CH201；串口 /dev/ttyUSB0
  config_json   text                    -- 连接参数（rtsp、modbus 寄存器、账号密码密文）
  sensor_id     FK -> sensor.id  null   -- kind=gas/env/noise 时指向读数实体
  video_id      FK -> video_source null -- kind=camera 时指向视频源
  enabled       bool default 1
  created_at
)

-- 型号模板（可选，二期做管理界面；一期用 seed JSON）
robot_profile (
  id PK, name, vendor, model,
  default_peripherals_json text,        -- [{kind, vendor, channel, config}]
  default_actions_json     text         -- ["navigate","stand_up","lie_down"]
)

-- robot 增加两列（不删除旧字段，兼容迁移）
robot.profile_id        varchar null
robot.capabilities_json 保留，但改为"缓存/覆盖"，由外设派生后写入
```

**能力派生规则（写在代码里，一处）**：

| 外设 kind | 派生能力 |
|---|---|
| camera | `video.live`, `photo.capture` |
| thermal | `video.thermal`, `thermometry` |
| ptz | `ptz.move`, `ptz.preset` |
| gas / env / noise / dust | `env.read.<kind>`, `alarm.rule.<kind>` |
| speaker | `audio.tts` |
| —（设备本体） | `navigate`（适配器支持时）、`posture.stand_up`（X30 类） |

## 3. 接口契约

```
GET  /api/v1/robots/{id}/capabilities
     → { robot_id, station, profile, capabilities:[...], peripherals:[{id,kind,vendor,channel,status}] }

GET  /api/v1/peripherals?robot_id=2       列出外设
POST /api/v1/peripherals                  新增（现场加装传感器就走这里）
PATCH/DELETE /api/v1/peripherals/{id}

GET  /api/v1/stations/{id}/devices        场站下的设备列表（含 capability 摘要）
```

前端只认 `capabilities`，不认型号。

## 4. 前端面板注册表

```ts
// components/panels/registry.ts
export const PANELS = [
  { key: 'video.live',    component: VideoPanel,    props: (p) => ({ src: p.videoUrl }) },
  { key: 'video.thermal', component: ThermalPanel,  props: (p) => ({ src: p.videoUrl }) },
  { key: 'env.read',      component: EnvPanel,      props: (p) => ({ sensors: p.sensors }) },
  { key: 'ptz.move',      component: PtzPad,        props: (p) => ({ channel: p.channel }) },
  { key: 'posture.stand', component: PosturePad,    props: () => ({}) },
]
// 首页：abilities.map(k => PANELS.find(p => k.startsWith(p.key))) 依次渲染
```

新增"粉尘仪"：后端加 `kind=dust` → 派生 `env.read.dust` → 前端已存在的 `EnvPanel` 直接显示，**主页面零改动**。

## 5. 模块职责与产出（做什么 / 产出什么 / 谁用）

| 模块 | 做什么 | 产出 | 依赖 | 被谁用 |
|---|---|---|---|---|
| **设备接入** | 适配器（HTTP/TCP/UDP）把厂商协议转成统一模型 | 状态/位姿/电量/任务 | 厂商协议 | 状态缓存、任务、告警 |
| **外设注册** | 管理 peripheral，派生 capability | 能力清单、面板清单 | 设备台账 | 首页、任务、告警 |
| **状态缓存** | 每设备一份快照 + 新鲜度 | online/age/字段级更新时间 | 接入层 | 首页、告警、报表 |
| **地图点位** | 平台底图 + 点位 + 到点半径 | 点位坐标、动作配置 | 地图库 | 任务模板、巡航 |
| **任务编排** | 模板 → 执行记录 → 步骤 | task_run / step 状态机 | 点位、适配器 | 巡航、报表、消息 |
| **巡航执行** | 逐点下发 + 等到达 + 到点动作 | 每点结果/照片/失败原因 | 任务、适配器 | 消息、报表、告警 |
| **视频** | 视频源、录像分段、回放 | 实时流、录像文件 | go2rtc/ffmpeg | 首页、告警取证 |
| **传感器网关** | Modbus TCP/RTU-SSH/MQTT 采集 | 读数时间序列 | 外设配置 | 环境面板、阈值告警 |
| **告警** | 阈值/离线/升级 + 去重 + 自动恢复 | 告警记录、事件 | 状态缓存、传感器 | 工单、通知、报表 |
| **工单** | 建单/派单/处置/销号 + 手机页 | 工单生命周期 | 告警、用户 | 通知、报表、审计 |
| **通知** | 企业微信/钉钉/Webhook，签名+重试 | 送达记录 | 工单、告警 | 责任人 |
| **录像取证** | 告警时间窗 → 关联录像片段 | 证据包 | 告警、录像 | 工单、追责 |
| **报表** | 巡检/考核/覆盖度/导出 | Excel、PDF | 全部业务表 | 甲方 |
| **审计** | 哈希链、操作留痕 | 不可篡改链 | 全模块 | 审计员、等保 |
| **平台运维** | /metrics、日志、备份、保留策略 | 监控指标、备份 | 全模块 | 运维 |

## 6. 四条关键联动（时序）

### 6.1 传感器超限 → 工单 → 手机闭环

```
网关采集(5s) → sensor_reading → 阈值比较 → AlarmStore.upsert(同设备同指标未解除则更新)
   → 严重告警 → work_orders.ensure_from_alarm（同源只建一张）
   → notify.push_text（企业微信/钉钉，带 /m/wo/{id} 链接）
   → 安全员手机：接单 → 拍照 → 填结论 → 销号
   → 审计留痕 + 报表统计（响应时长/闭环率）
   ← 条件消失 → alarm.resolved（自动恢复，不等人工）
```

### 6.2 任务 → 巡航 → 证据 → 报表

```
模板(点位序列+动作) → task_run(planned) → 巡航线程
   → 逐点：1003/HTTP 下发 → 轮询任务状态 → 到点(位姿误差 ≤ 点位半径)
   → 动作：抓拍/测温（无接口则明确失败，不写假成功）→ step.result
   → 全部完成 → task_run(done/failed) + dispatch_error 原因
   → 报表：按人/车/点位统计完成率、异常率、平均耗时
```

### 6.3 告警/任务结果 → 录像取证

```
告警产生(t0) → 查录像分段索引 [t0-30s, t0+60s] → 生成证据包(片段+快照+告警详情)
   → 工单详情页"看录像"按钮直接跳到该时间点（不是让人自己找）
```

### 6.4 设备上下线 → 在线率/容量

```
状态缓存 age > 阈值(按适配器，X30 30s/JCROB 10s) → offline 事件
   → 告警(一条，持续更新，不每分钟新建) → 在线率统计（按天/按设备）
   → 容量：录像天数、读数行数、磁盘水位（低于阈值停录 + 推送）
```

## 7. 迁移路径（三步，随时可回退）

| 步 | 动作 | 风险 |
|---|---|---|
| 1 | 建 `peripheral` 表；把现有 sensor/video_source 按 `robot_id` 回填成 peripheral 行（kind 由名称/分组推断） | 低（只增不删） |
| 2 | `/robots/{id}/capabilities` 改为"由 peripheral 派生"，`capabilities_json` 降级为缓存 | 低 |
| 3 | 首页改为读 capability 渲染注册表面板；旧 `capabilities_json` 保留兜底 | 中（UI 改动） |

**回退**：任何一步出问题，删 peripheral 表即可回到当前实现（旧字段都保留）。

## 8. 12 月最小集 vs 二期

**现在必须做**（约 3 人日）
- peripheral 表 + 回填 + 派生能力接口
- 首页按能力渲染（可见光/热红外/环境/控制四类面板）
- 告警↔工单↔通知的关联 ID（alarm_id / work_order_id 双向可查）

**二期**
- Profile 管理界面（模板化新建）
- 面板拖拽/自定义布局
- 多实例同类外设（两个气体传感器）分组展示

**明确不做**
- AAS 全量建模（对企业内部系统过重）
- 每型号写一个页面模板（维护成本随型号数线性增长）
- 把能力做成可任意编辑的字符串（会导致"配了但没接"）

## 9. 和开源方案的取舍

| 方案 | 借鉴什么 | 为什么不整体采用 |
|---|---|---|
| Home Assistant Device/Entity | 设备与外设两层 + 按实体渲染 UI | HA 的实体状态机偏智能家居，缺工业告警/工单 |
| ThingsBoard Device Profile | 模板化初始配置 | 偏遥测接入与规则引擎，机器人动作编排弱 |
| AAS Submodel | 能力/属性的规范化命名 | 跨企业交换场景，太重 |
| Open-RMF Adapter | 适配器隔离厂商差异 | 多机调度，一期单机用不上 |

**一句话**：借 HA 的"设备-实体"分层和 ThingsBoard 的"模板"，其余按巡检业务自己做。
