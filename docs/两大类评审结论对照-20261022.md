# 豆包 / GLM / Claude 三方评审结论对照

> 同一份方案给三家看：豆包（ark）、GLM（智谱）、Claude（本地 CLI）。
> 原始输出：`docs/reviews/model_review_20261022-213633.md`、`docs/reviews/critique-claude.md`。

## 一、三家一致同意的（可以直接当结论）

1. **逐点下发在"单机、固定路线、低速"前提下成立**，但不能包装成自主导航/车队调度。
2. **必须补下发前门禁**：急停、手动模式、低电量、已有任务时不允许下发。
3. **到点判定不能只看 FINISHED**，要结合位姿误差、错误码、定位质量；不同点位阈值应可配。
4. **12 月定位要收窄**：叫"机器人配套上位机 / 巡检运营平台"，不叫"平台/调度系统"。
5. **AI 必须改口径**：只承诺"接入第三方识别结果"，不承诺算法与准确率。
6. **该砍**：3D、GB28181/ONVIF 深度接入、多机器人调度、边缘网关、断网续传完整实现。
7. **验收靠闭环演示**：真机 1-2 条固定路线 + 到点拍照 + 告警工单手机闭环 + 报表，不是功能数量。

## 二、三家分歧点

| 议题 | 豆包 | GLM | Claude |
|---|---|---|---|
| 逐点轮询 | "能验收，但要配 WS + 超时兜底" | "最烂设计，必须改 WS 主动上报或整单下发" | "单机 fallback 成立，产品架构不成立" |
| 是否先逼厂家支持整单 | 建议优先整单 | 强烈要求整单/WS，否则半自动 | 12 月首选厂家原生整单 |
| 视频并发 | 砍到 2 路以内 | 砍到 1 路，录像交本体 | 容量问题需 NVR/对象存储 |

**我的判断**：三家其实说的是同一件事——**平台不该承担"确保机器人走到"的责任**。
12 月能做到的是"逐点下发 + 明确失败"，做不到"断网/避障/失联都自愈"。所以口径要写清楚。

## 三、本轮已经落地的（对应评审意见）

| 评审意见 | 落地 |
|---|---|
| 下发前门禁 | `task_dispatch.preflight()`：急停/手动/低电量（<30%）/同机已有任务 → 409 并说明原因 |
| 到点阈值按点位配 | `PointDraft.arrive_radius_m`（默认 1.0m），巡航按点位半径判定 |
| 服务重启不留假状态 | 启动时把残留 `running/dispatched` 标 `failed` + "状态未知，请人工确认" |
| 订单要带坐标 | 下发订单写入 x/y/yaw（原来只有 pointId，机器人会去原点） |
| 到点要执行动作 | 巡航到点调用 `adapter.capture(step)`；没有接口就报错，不写假成功 |
| 取消要停线程 | 通用 `/cancel` 先停巡航线程，再取消机器人目标 |

## 四、还没做、但评审都点名的

- WS 3547 主动上报替代轮询（等真机协议）
- 整单下发（等 JCROB 是否支持一次下发多点的确认）
- 步骤级"跳过/重试/人工接管"（现在只有失败即停）
- 任务状态机细分到 GOTO_RUNNING/ARRIVED/ACTION_RUNNING（现在 5 个状态）
- 断网续传、NVR/对象存储

## 五、对外口径（三家共识）

- **可以说**：设备接入、任务编排、过程监管、告警工单闭环、报表留痕、私有化部署、权限审计。
- **不能说**：自主导航、车队调度、AI 识别（平台侧）、断网续传、50 路视频、等保三级已达标。
- **边界要写进合同/标书**：机器人运动安全由本体负责；平台下发目标点，路径与避障由机器人完成。
